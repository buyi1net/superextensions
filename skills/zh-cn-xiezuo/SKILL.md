> 中文表达好不好就一条：读者一遍读懂，不回头、不猜、不皱眉。本 skill 管中文用户的完整表达链路：外文准确自然地译成中文、中文意图准确得体地转成外语、跟模型的交流说人话、中文写作去 AI 味、代码 i18n 和技术内容不被翻坏。写作、交流、翻译共用同一套纪律。

## 总则

**范围：** 所有写给另一个人读的中文（文档、报告、README、commit、代码注释、对话回复、界面文案、译文），以及用户要求产出的外语成稿（按对外表达模块处理）。对话回复的语气纪律（怎么表态：反讨好、反催促）由各 agent 自己的交流规范管；本 skill 管可懂度和跨语言表达的准确。给用户的解释和汇报永远用中文，外语成稿独立成块。

**保持原文清单**（这些不翻译、不改写）：

- 代码标识符：关键字、变量、函数、类、类型名
- CLI 命令、flag、管道符、环境变量
- 文件路径、URL、正则表达式（只有用户或项目明确要求的本地化链接可以修改，改后必须验证）
- JSON/YAML/TOML/XML/INI 等配置文件的键名、标签常量
- 产品名、平台名
- 技术缩略词：API、HTTP、SQL 等通用缩写（有通行中文定译的领域缩写如 RLHF、RAG 按术语表处理）
- bash 可执行命令本身

## 文档规则

- 所有人类可读文本用简体中文（仅豁免清单可保持原文；用户要求外语成稿时按目标语言输出）。
- 英文专有名词保留原文，不生硬翻译；普通概念有自然中文说法时直接用中文。是否在首次出现时附英文，按下文“术语锁定”判断，不机械中英并列。

推荐：

```md
## 构建流程
使用 `cmake --build` 执行构建，输出目录为 `Support/Build/`。
```

不推荐（标题、正文用英文）：

```md
## Build Process
Use `cmake --build` to build the project.
```

修改已有文档：文档主体是中文则保留已有英文示例、信号词、代码，不翻译；文档主体是英文则不强制翻译，只新增用中文。代码块注释：引用真实源码保留原文，教学示例译成中文，信号词和检查清单保留原文。英文专属规则标注"仅英文适用"。

## 代码注释

注释的语言和编码规则在 [modules/zhushi.md](modules/zhushi.md)，写代码注释时按场景路由先读它；何时写、写什么注释属于工程判断，由项目自己的开发规范管。

## 中英混排

- 英文技术标识嵌入中文句子，前后加空格；已半吸收的常用术语（API、commit、PR 等）不强求。
- 不半中半英、不为中文化翻译代码标识。

```
✅ 使用 `CreateProcessW` 启动子进程，失败时记录 `GetLastError()`。
❌ Use `CreateProcessW` 启动子进程 and log `GetLastError()` when failed.
```

## 写作四原则

任何中文产出先过这四条。

**一、意译原则**——写人话，不写翻译腔也不写 AI 腔。翻译时翻意思不翻句子结构；自己写时不用套话凑格式。判断标准：这句话像不像一个中文母语的人当面说出来的。

**二、信息密度**——每个字都带信息。删废话短语和空话结尾；修饰词换成具体事实更有力时就删掉。不能删的：代码、命令、路径、报错、涉及安全的步骤、读者不知道的关键事实。

**三、术语锁定**——同一概念全文使用同一个名字。优先级：豁免清单和不许译清单里的词保留英文；项目已有惯例的沿用惯例；术语表按具体语境选译法；有稳定中文说法且不会影响理解或模型行为的，直接用中文。只有为了消歧、核对原文、便于搜索，或保留原词对模型行为的作用时，首次使用“中文（English）”；查不到可靠译法的不硬翻，列为待复核。

**四、对象适配**——先问读者是谁再动笔。读者在行就点到为止，不熟就讲透；措辞风格跟随场景（commit 简洁、报告严谨、界面文案口语），但原则和质检一个不豁免。给陌生人写的东西不带私交默契和临时黑话。

## 去 AI 味

二十条检测表（内容、语言、风格、废话四类模式）加废话短语替换表加反模式警示，全部在 [modules/aiwei.md](modules/aiwei.md)。所有写作场景共用，写完对照过一遍：拿不准某句像不像 AI，就看它有没有实质信息、是不是空洞套话。

## 输出前自查

产出物交付前逐项过，发现了先改再交：

1. **语言选择**：所有人类可读文本是中文？豁免清单用对？
2. **文档规则**：修改已有文档时没误翻译示例、信号词、源码注释？
3. **代码注释**：语言用中文了吗？编码对吗（新建 UTF-8 / 改文件跟随原编码；MSVC 中文源需 BOM 或 /utf-8）？
4. **中英混排**：技术标识空格？没半中半英？
5. **去 AI 痕迹**：过 20 条模式（重点：夸大意义/推销语气/互联网八股/空话结尾）。信号词查表：标志着/强大/赋能/抓手/闭环/未来可期。
6. **去行话**：产出物里的抽象名词逐个问「目标读者第一次读到能不假思索地懂吗」；要猜的换大白话。
7. **反模式**：有"英文更专业"类思维偷跑？
8. **推测标注**：没把握的译法、查不到出处的断言，在给用户的回复里列“待复核”清单，不写进交付物本体；没有实际疑点就省略该栏目。翻译和 i18n 场景只报告实际问题与必要的验证证据，不逐项填写形式化结果。

## 用户要求优先级

1. 用户明确指定的语言要求（最高）
2. 项目已有更具体的语言规范（如项目的 `AGENTS.md` 或 `CLAUDE.md`）
3. 文件已有统一语言风格（保持一致，新增仍用中文）
4. 本 skill 默认规则（最低）

冲突不清时向用户确认。

## 场景路由

> 红线：不分场景，看意思不看词。命中触发条件的，先读对应模块再动笔。
>
> 多场景同时命中的裁决：产出物场景优先于交流场景。写一篇给用户看的文档里有英文引文时，文档本体按写作场景处理，引文按翻译模块处理，给用户的口头说明按交流模块处理；各管各的部分，不叠加检查。

### 翻译

**触发条件：** 把外文内容转成中文（文档、文章、邮件、对话、报错、注释）。
**强制措施：** 动笔前完整读取 [modules/fanyi.md](modules/fanyi.md)，出稿前在内部跑完它的翻译质检门——两个卡口一个都不能省；回复只报告实际问题、必要验证证据和仍未解决的疑点。译文同时受 [modules/aiwei.md](modules/aiwei.md) 去AI味检测表约束。

### 对外表达

**触发条件：** 中文翻成外语、按中文意图直接写外语内容、写 GitHub issue/PR/discussion、给国外开发者写邮件或社区回复。
**强制措施：** 动笔前完整读取 [modules/duiwai.md](modules/duiwai.md)——两种任务分流、力度保真、结构保持（含 GitHub 元素）、官方译名核验在那里；反向术语陷阱查 [glossaries/zh-en.md](glossaries/zh-en.md)。

### 代码 i18n

**触发条件：** 翻译或编写用户界面字符串、locale 文件、多语言资源（json/arb/po/strings 等格式）。
**强制措施：** 动笔前完整读取 [modules/i18n.md](modules/i18n.md)——key 保护、插值占位符、复数规则、长度约束的规则在那里。

### 通用写作

**触发条件：** 用中文写作给人读的任何文本（文档、报告、稿子、README、commit、社交内容）。
**强制措施：** 本文件四原则加输出前自查，加必读 [modules/aiwei.md](modules/aiwei.md)（二十条检测表）。写作的病（AI 腔、低密度、术语漂移）是通用病，这套就是药。

### 代码注释

**触发条件：** 写或改代码注释（行注释、块注释、文档注释、docstring）。
**强制措施：** 动笔前完整读取 [modules/zhushi.md](modules/zhushi.md)——注释语言、编码规则、MSVC 中文源处理在那里。

### 对话交流

**触发条件：** 跟用户对话的回复（解释、汇报、方案说明、答疑）。
**强制措施：** 动笔前完整读取 [modules/jiaoliu.md](modules/jiaoliu.md)——术语降级表、深度适配、节奏格式的规则在那里。

### 潜台词与黑话

**触发条件：** 用户问某段话"什么意思"（职场话、社交话、网络黑话、AI 圈黑话），或要把一个意思说得得体、换个语气。
**强制措施：** 动笔前完整读取 [modules/taiji.md](modules/taiji.md)——解码五维分析、速查表和编码规则在那里。

## 与其他规范的关系

本 skill 管一切中文产出的**可懂度**（写得让人看得懂）：产出物的写作与翻译质量、对话回复的术语与深度。对话回复的语气纪律（怎么表态：反讨好、反催促）由各 agent 自己的交流规范管，两边分工不重叠。

使用其它 skill 的模板或示例生成中文产物时，只翻译面向读者的文字；代码、命令、路径、键名和会影响模型行为的英文关键词按产物用途保留。翻译 Agent 规则文档时执行 [Agent 与规则文档翻译](modules/fanyi-agent-wendang.md)；其它 skill 明确要求输出英文时遵循其要求。
