# Agent 与规则文档翻译

> 本模块处理会影响 Agent 执行行为的英文文档，包括 skill、`AGENTS.md`、`CLAUDE.md`、system prompt、Agent 工作流和规则文件。通用翻译要求继续执行 [fanyi.md](./fanyi.md)；本模块补充行为边界、调用机制、关键词和中文可懂度的专门要求。

这类文档不能只追求字面准确。译文既要让简体中文读者直接读懂，也不能改变 Agent 看到的触发条件、执行步骤和约束力度。

## 先确定产物用途

动笔前确定本次要产出哪一种文件：

1. **可执行译本**：中文文件会直接交给 Agent 执行；
2. **中文导读**：只供人理解和吸收，不代替原文件执行；
3. **双轨输出**：可执行译本和中文导读分别成文。

用户没有说明、现有文件也无法判断时，先确认，不得自行选择。

### 可执行译本

可执行译本以行为不变为首要标准：

- 不增加原文没有的规则、建议、解释或适用场景；
- 不删除原文中的概念、因果关系、例外和强调力度；
- 不添加“本文是译文”“为了方便理解”等翻译说明；
- 不把面向人类的理解辅助内容塞进执行文件；
- 不改变 frontmatter 字段名、配置键和调用机制；
- 不扩大或缩小 `description` 的触发范围；
- 不改变步骤顺序、分支条件、停止条件和完成标准；
- 不改变 skill 之间谁能调用谁；
- 不把参考规则误写成执行步骤，也不把执行步骤弱化成背景说明。

### 中文导读

中文导读可以重组讲解顺序、增加中文例子、解释概念关系并分析如何应用，但必须与可执行译本分开。导读不保留会让 Agent 把它识别为正式 skill 的 frontmatter，也不得伪装成行为等价译本。

### 双轨输出

同时需要执行和理解时，分别产出：

- 一份行为边界与原文一致的可执行译本；
- 一份面向中文读者的独立导读。

不能让一份文件同时承担两种职责。面向人的补充说明会增加 Agent 的上下文占用，也可能改变规则权重。

## 翻译前先分析

完整阅读源文件及其强制引用的相关文件，再开始翻译。分析至少覆盖：

1. 这份文件由人阅读还是由 Agent 执行；
2. 它解决什么问题；
3. 哪些内容决定调用时机；
4. 哪些内容决定 Agent 的实际行为；
5. 哪些短词或短语是作者故意反复使用的关键词；
6. 哪些内容是普通说明，哪些是硬性边界；
7. 哪些文件路径、配置和 skill 调用关系必须保持；
8. 哪些英文概念没有自然、通行的中文译法。

长文需要分块时，先完成全文分析和术语统一，再按标题或完整段落切分。各块共享同一套术语、语气和概念判断，不得各自重新翻译核心概念。

## 用中文重新组织，不套英文骨架

先理解完整意思，再用中文自己的句法表达。可以拆句、并句和调整语序，但不能改变信息和力度。

逐句检查：

> 没看过原文的中文读者，第一次读到这句话，能不能直接理解作者要 Agent 做什么、为什么这样做？

不能直接理解就继续修改。以下写法不合格：

- 只把英文单词换成中文字词，保留英文语序；
- 每个概念都写成“英文术语（中文术语）”；
- 为了显得专业而保留大量不必要的英文；
- 把原文比喻逐字搬进中文；
- 用另一个生僻词解释生僻词；
- 本来一句普通中文就能说清，却压缩成一个新造术语；
- 用“赋能、抓手、闭环、范式、对齐、收敛”等抽象词代替具体动作。

## 术语处理

按以下顺序确定译法：

1. 代码标识、配置键、命令、路径、API、环境变量、产品名和版本号保持原样；
2. 已有稳定中文译法的，使用稳定译法；
3. 没有稳定译法，但普通中文可以直接说明的，不另造专名；
4. 原文故意建立的核心概念，首次按“中文（English）”标注；原词承担行为引导时不得只留下中文；
5. 后文使用已确定的中文说法，不反复中英并列。

每拟定一个中文术语，都检查：

1. 这是通行说法，还是临时拼出来的？
2. 中文读者能从字面直接理解吗？
3. 能否不用专名，直接把意思说清楚？
4. 换成中文后，会不会丢失原词对模型预训练知识的调用作用？

### 提示词与关键词

`prompt` 指交给模型的整段提示词，`system prompt` 指系统提示词。原文中的 `leading word` 不是整段提示词，而是提示词里的关键词：

> **关键词（leading word）**：模型在预训练中已经理解的短词或短语，可以用很少的 token 唤起一整套行为。

例如 `red`、`relentless`、`fog of war`。这些词的价值来自模型已有的理解。翻译时不能只为中文整洁而删除，也不要另造需要再次解释的中文术语。首次出现时保留英文和中文定义，后文根据实际行为作用决定继续保留英文还是使用“关键词”。

## 保持行为边界

### 调用范围

逐项核对：

- `description` 是否扩大或缩小了触发条件；
- 用户调用与模型调用的边界是否保持；
- 一个 skill 是否被错误地允许或禁止调用另一个 skill；
- 路由文件是否仍然只负责原来的场景。

### 规则力度

逐项核对原文中的：

- 必须；
- 应该；
- 可以；
- 只有；
- 禁止；
- 默认；
- 例外；
- 先后顺序；
- 停止条件；
- 完成条件。

不得把硬性要求译成建议，也不得把建议升级为硬规定。

### 因果关系

作者解释“为什么这条规则会影响模型行为”的内容必须保留，不能只留下结论。重点检查：

- 哪个条件导致哪个行为；
- 哪种做法只是节省 token，哪种做法会影响执行稳定性；
- 哪些词只是普通术语，哪些词承担行为引导；
- 哪些内容只帮助人理解，哪些内容会改变 Agent 执行。

### 文件和配置

逐字核对：

- frontmatter 字段名；
- 配置键；
- 文件路径和相对链接；
- skill 名称；
- 命令、API 和环境变量；
- 代码块；
- 版本号。

只有用户或项目明确要求本地化链接时，才把原链接改为对应的中文文件。修改后实际检查目标文件存在且链接可达。

## 检查自造词

翻译完成后，单独扫描全文中的中文名词、四字短语和首次出现的概念名称。

译者自行创造、原文没有建立的中文说法，出现以下情况必须重写：

- 查不到通行用法；
- 只有当前译文这样说；
- 读者必须先看定义才能猜出字面意思；
- 一句普通中文本来就能说明，却被压缩成一个术语；
- 为保持英文形式而机械制造中文名词。

原文本身故意建立的概念不按上面的“当前译文是否独有”判断；满足以下条件之一时可以保留稳定名称：

- 已有通行译法；
- 项目已经定义并长期使用；
- 普通中文读者从字面就能理解；
- 原文确实需要一个稳定名称，并且首次出现时已经解释清楚。

仍然没有合适中文名称时，保留英文原词并用普通中文解释，不强行为它安排固定中文名。

## 三轮审校

### 第一轮：逐段对照原文

检查遗漏、增译、概念替换、因果变化和力度变化。每个原文段落都必须在译文中有对应信息。

### 第二轮：只读中文

不看原文，把译文当作中文母语作者写的独立文章阅读，检查：

- 翻译腔；
- 生硬术语；
- 英文堆积；
- 不自然语序；
- 前后称呼不一致；
- 第一次出现却没有解释的概念。

### 第三轮：从 Agent 执行角度检查

核对调用范围、步骤、分支、停止条件、完成标准、文件引用和关键词是否发生变化。

重要文档再安排一次独立审校。审校者只诊断，不直接修改；主 Agent 根据问题清单修订，再逐项复核实际文件。

## 交付说明

上述检查全部在内部完成。回复只报告实际发现的问题、必要的验证证据、仍未解决的疑点，以及用户需要知道的文件或链接变更；没有信息价值的栏目不输出。

不能仅凭文本检查宣称模型行为完全一致。需要说明验证边界时，准确表述是：

> 已完成语义、规则力度、调用边界和文件机制的文本对照；跨语言后的实际触发效果仍需通过 A/B 运行测试验证。
