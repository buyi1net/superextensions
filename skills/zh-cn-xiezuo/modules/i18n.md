# 代码 i18n 场景模块

> 用户界面字符串和多语言资源的翻译与编写规则。SKILL.md 的四原则和输出前自查全部适用，本模块管 i18n 特有的约束。

## i18n 和文档翻译的本质差异

i18n 翻译没有句子上下文——对象是一堆散的字符串；约束比表达自由度多。先看清这些差异再动笔：

| 差异 | 文档翻译 | i18n 翻译 |
|---|---|---|
| 上下文 | 有整篇语境 | 常常没有，只有 key 和字符串本身 |
| 修改自由 | 句子结构随意重组 | key、插值、格式符一个不能动 |
| 长度 | 基本不限 | 受 UI 空间约束（按钮、菜单宽度） |
| 语气 | 跟随原文 | 产品语气统一，全语言一致 |

## key 保护

- 翻译 locale 文件时 **key 一律不动**：`"login.button.title"` 的左边永远原样，只译右边。
- key 的命名语义（button、title、error）是理解上下文的线索，但不许把 key 翻进译文。
- 不新增、不删除、不合并 key；发现原文缺 key 或多 key，停下来报告，不自行修补。

## 插值占位符

- `{name}`、`%s`、`%1$s`、`{{count}}`、`%{count}` 这类占位符**逐字保留**，一个字符不许变。
- 占位符在译文中可以换位置（中文语序需要时），但不许改写、不许复制、不许删除。
- 有多个占位符时逐个核对：译文里每个占位符在原文里都有对应，数量一致。
- 带格式的占位符（`{price:currency}`、`%.2f`）格式说明符不许动。

## 复数规则

- 英文单复数（one/other）在中文里通常塌缩成一种形式（中文的 CLDR 复数类别只有 other），但要按 i18n 框架的规则走：
  - ICU MessageFormat 的 `{count, plural, one {...} other {...}}` 结构：中文按语言规则只需要 other；源文的 one 分支是否保留跟随框架惯例（有的框架要求镜像源结构，有的按目标语言精简），拿不准时保留源结构并在待复核里标注。
  - JSON 扁平结构（`key.one` / `key.other`）两个 key 都要填，内容可以相同。
- 原文有复数分支而目标框架没有的，问用户怎么处理，不自作主张。

## 长度与语境约束

- 按钮文案（"OK"、"Submit"）中文极短："确定""提交"，不加敬语装饰。
- 不确定字符串出现在界面哪里时，先查代码里的使用点（grep key 名）确认上下文，再译。
- 错误消息保持和产品现有同类消息的语气一致；拿不准现有语气，抽查三个已有翻译再动笔。
- 截断风险（长文案撑爆窄 UI）在待复核清单标注，不自行缩短。

## 术语与语气统一

i18n 场景的术语锁定只管同形：同一术语在所有字符串里同一译法。不做首现标注——散字符串没有阅读顺序，用户第一次在哪里看到哪个词无法判断，括号标注没处安放。

- 同一产品内同一动作一个译法：Delete 全是"删除"，不许出现"移除"和"删除"混用。
- 操作动词对照界面惯例：OK 确定、Cancel 取消、Save 保存、Submit 提交、Retry 重试、Dismiss 关闭。
- 产品名、品牌名、被社区保留的英文术语（token、prompt）不译。

## 质检门补充项

翻译质检门（[fanyi.md](./fanyi.md) 的六项）全部适用，i18n 另加三项：

| # | 检查项 | 通过标准 |
|---|---|---|
| 7 | key 完整 | key 列表与原文一一对应，无增删改 |
| 8 | 占位符核对 | 每个插值占位符逐字保留，数量、名称、格式符一致 |
| 9 | 结构保持 | locale 文件的结构与复数规则节选定的策略一致：嵌套、数组不增不减；ICU 类别按该策略核对（保留源结构时同构，按目标语言精简时验证 other 完整） |
