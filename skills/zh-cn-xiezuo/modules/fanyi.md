# 翻译场景模块

> 翻译特有病症的检测和修法（外文译中文方向；中文译外语见 [duiwai.md](./duiwai.md)）。SKILL.md 的四原则和输出前自查全部适用，译文同时受 [aiwei.md](./aiwei.md) 去AI味检测表约束（译文里的 AI 腔和写作里的同罪）；本模块只管翻译比写作多出来的东西。

## Agent 与规则文档

翻译 skill、`AGENTS.md`、`CLAUDE.md`、system prompt、Agent 工作流或其它会影响执行行为的规则文件时，动笔前完整读取并执行 [Agent 与规则文档翻译](./fanyi-agent-wendang.md)。这类任务除了语言准确，还必须保持调用范围、规则力度、步骤、分支、停止条件和文件机制；面向 Agent 的可执行译本与面向人的中文导读不得混成一份文件。

## 意译的执行标准

意译不是翻得宽松，是**中文句子围着意思重新组织，不围着原文骨架填字**。

- 先读懂原句的全部信息，再用中文自己的句法把意思讲出来。
- 允许拆句、并句、换成语、调语序；不允许丢信息、加信息、改变强调程度。
- 情感保真：原文带情绪的词（alarming、haunting、sharp）不许扁平化成中性词；反过来说话人委婉的也不许译成强硬。

## 欧化七症状

从英文翻中文时逐项检查，症状和修正对照：

| 症状 | 表现 | 修正 |
|---|---|---|
| 名词化 | 进行了讨论→讨论了；做出了让步→让步了 | 名词还原成动词 |
| 被动滥用 | 它被认为是、被用来做 | 改主动："大家认为""用它做"；真被动才留"被" |
| 名词堆砌 | 长修饰语链"这种基于预训练语言模型架构的文本生成方法" | 拆短句："这种方法基于预训练模型，用来生成文本" |
| 硬搬"是…的" | It is...that 直译成"…的是…" | 改自然表达，中文不这么强调 |
| 代词冗余 | 他/她/它/我们频繁出现 | 中文能省则省，上下文已指明的删掉 |
| 连词堆砌 | 因此/然而/此外/另外到处都是 | 上下文已暗示逻辑时删连词 |
| 引导句直译 | "格式如下""轮次推进决策树"这类英文引导句式硬搬 | 自问：这句是一个中文母语的人会说出口的话吗？不会就换成直接说事（如"每道题照这个样子写"） |

## 习语和比喻三策略

原文的习语、比喻、文化典故，逐个选策略处理，不许全部直译：

1. **意译**：丢掉源语言意象，直接说含义。"hit the ground running"→"上手就干"，不是"落地就开始跑"。
2. **替换**：用中文里同效果的习语换。"pay off twice"→"一举两得"，不是"付两次报酬"。
3. **保留**：原文意象在中文里同样有效时保留。"fog of war"→"战争迷雾"，目标读者都懂，不必换。

判断依据：目标读者第一次读到能不能不假思索地懂。要猜的，换。

**自造比喻同样过这道关**：译文中你自己新造的比喻（原文没有、你为了生动加的），连败两次就删掉换直说——比喻两次说不通，说明这个位置不需要比喻，直接陈述就是最优解。

## 多义词核对（同一个词在不同行当里意思不同）

多义词按语境定义项再翻，高频陷阱对照：

| 原文语境 | 错译 | 正译 |
|---|---|---|
| prose（泛指行文） | 散文 | 正文、文字 |
| bucket（目录分组） | 水桶 | 分组（或保留英文并配实例说明） |
| harness（运行环境） | 马具、驾驭 | 运行环境（首现加英文对照） |
| argument（函数参数） | 争论、论点 | 参数 |
| contract（接口约定） | 合同 | 约定、契约（技术语境固定译法） |

## 不许译清单

以下内容默认逐字保留；路径和 URL 只有在用户或项目明确要求本地化时才能修改，改后必须实际验证：

- 引用的真实源码、命令、路径、URL
- 教学示例中的代码标识保持原样；面向读者的注释按 SKILL.md 文档规则处理
- 配置键名、API 名、环境变量、版本号
- 产品名和品牌名：GitHub、npm 等原样
- frontmatter 字段名（name、description 等）
- 社区约定俗成保留英文的术语：agent、skill、commit、token、prompt（具体保留哪些跟随目标项目的既有惯例）

## 翻译流程

先锁产物，再锁读者和术语；三项没有确定，不进入翻译：

0. **锁产物**：先判断译文是直接替代源文件使用、只供人阅读，还是需要分别产出两种版本。Agent 与规则文档按专门模块的三类产物处理；普通翻译也不得把译者说明混进正文。现有文件和用户指令足以判断时直接执行，确实拿不准才问。
1. **锁读者**：确认译文给谁看——给用户的说明文档、给执行规则的 agent、给社区的外发文本，读者不同则语域和深度不同。后续所有判断都以这个读者为标准。
2. **锁术语**：翻译前列出真正影响理解或一致性的关键术语，定好译法和必要的首现标注，全文使用同一名称；不为常见、无歧义的词机械建立术语表。优先级按 SKILL.md 术语规则执行；没把握的先查 [glossaries/en-zh.md](../glossaries/en-zh.md)，表里没有的按质检门第 6 项处理。
3. **意译产出**：按上面标准翻完。
4. **内部质检**：逐项执行下方质检门，发现问题先修正。只向用户报告实际问题、关键验证证据和仍未解决的疑点，不逐项填写“通过”。
5. **读者视角通读**：把稿子当成别人写的，第一遍读到卡壳的句子就是病灶，回头查表修；作者视角查不掉读者视角的病。重要译文需要新旧对照时，只在对话回复或独立审校文件中提供，不得写入正式译文或可执行译本。

### 长文分块纪律

原文超过一次能处理的量时分块翻译，纪律：

- 分块前先锁全文术语：术语表和首现标注位置在全文层面定好，每块用同一套。
- 分块在结构边界切：标题边界优先，段落边界次之，不许把段落从中间切断。
- 每块共享同一份分析结果（领域、语气、术语、比喻映射），不是每块重新分析。
- 合并后过全文一致性：术语全文同形、语调全篇一致、块间衔接自然。

### 重要文档的精修流程

译文要出版、长期存档或会影响 Agent 执行时，在质检门外再加审校一轮：

1. **分析**：在当前工作过程中整理概要、核心论点、关键术语、比喻处理和读者理解难点。默认不单独创建分析文件；只有用户明确要求时才成文，并按项目文件治理确定位置。独立审校所需内容直接随审校任务提供。
2. **初稿**：按分析结果翻。
3. **审校**：只诊断不修改，逐段对照原文查准确性、欧化表达、术语一致性、比喻处理和流畅度，形成实际问题清单。
4. **修订**：按问题清单逐项修。
5. **通读**：把修订稿当独立文章读，查衔接、语调一致和残留翻译腔。

## 翻译质检门

| # | 检查项 | 通过标准 |
|---|---|---|
| 1 | 占位符 | 可执行模板和忠实译文中的 `<xxx>` 等变量逐字保留；只有用户明确要求改编内容时才填充或解释 |
| 2 | 原样保留 | 引用源码、代码标识、命令、配置键、API、环境变量和版本号逐字核对；教学示例的注释按文档规则处理；路径与 URL 默认保留，只有明确的本地化要求允许修改，改后实际验证 |
| 3 | 术语同形 | 锁定的术语每次出现完全一致；同一概念没有多个名字 |
| 4 | 信息边界 | 可执行译本和忠实译文不增删信息，因果和强调程度不变；中文导读增加的解释只放在独立文件 |
| 5 | 数字实体 | 数字、日期、单位、金额与原文核对，不做任何未要求的换算 |
| 6 | 推测标注 | 没把握的译法、查不到出处的定译，在回复中列“待复核”清单；没有待复核项时省略该栏目 |

短句、单词、口语片段可以简化分析和审校过程，但保护内容、信息边界和实际疑点仍须内部核对。
