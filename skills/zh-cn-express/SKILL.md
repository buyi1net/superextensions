# 简体中文表达

> 核心标准：让读者一遍读懂，不回头、不猜、不皱眉。

本 skill 是 constitution 路由到的简体中文表达标准。它管表达的准确、可懂和跨语言保真；对话中的反讨好、反催促和表态纪律仍由各 Agent 的交流规范负责。

## 标准框架

所有任务先执行下面五个阶段，再叠加命中的场景制度。

### 一、定义产物

动笔前确定：文本给谁看、要解决什么问题、最终落在哪种载体、使用什么语言。已有文件还要确认它当前统一的语言、术语和格式。现有信息足以判断时直接执行；确实无法判断、不同选择会改变结果时再询问。

混合任务按文本片段分别判断。用户用中文要求一篇英文 GitHub issue，并要求解释措辞时，英文 issue 和中文说明是两个片段，分别进入各自场景。

### 二、锁定边界

忠实翻译不得增删信息，不改变因果、责任、时间、范围、情绪和强调程度。按意图写新稿时不得编造事实、来源、验证结果或承诺；没确认的结论明确标为推测。

除非用户或项目明确要求修改，否则这些内容保持原样：

- 代码关键字、变量、函数、类、类型名和 API 名；
- CLI 命令、flag、管道符、环境变量和正则表达式；
- 文件路径、URL、配置键、标签、常量和插值占位符；
- 真实源码、报错原文、版本号、commit hash、产品名和平台名；
- 会影响模型行为或便于检索核对的英文关键词。

路径和 URL 只有在明确要求本地化时才修改，改后必须实际验证。

### 三、围绕意思和读者组织表达

先理解要传达的完整意思，再用目标语言自己的句法和目标载体的习惯重新组织，不围着原文骨架填字，也不围着模型自己的知识结构堆术语。

对话回复可以使用当前对话已经建立的共识；独立产出物必须脱离聊天上下文仍然成立。交付前假设接收者只能看到产出物本身，看不到用户与模型的对话过程：只有聊天里出现过、但接收者理解正文所必需的背景、决定、对象和术语，必须在产出物中明确写出。

逐项清理聊天残留：没有明确指向的“这个、上面、刚才、按我们说的”，只在对话中成立的简称、临时命名、私交默契和语气，以及正文没有交代来源的结论或约束。需要的改成接收者能直接理解的完整表述，不需要的删除；不得用粘贴整段聊天记录代替必要背景。

同一概念全文只用一个名字。术语按这个顺序确定：用户明确指定 → 项目已有惯例 → 当前文件已有用法 → 对应术语表 → 稳定通行译法。只有为了消歧、核对原文、便于搜索或保持模型行为时，首次使用“中文（English）”；没有可靠译法的不硬翻，在正式成稿外列为待复核。

### 四、加载特殊场景制度

先判断特殊载体，再判断语言方向和表达目的。特殊载体模块取得任务所有权，并按需加载翻译或对外表达制度。

| 文本任务 | 必读模块 | 模块新增的制度 |
|---|---|---|
| 翻译或编写 UI 字符串、locale、多语言资源 | [UI 文案与本地化资源](./modules/i18n.md) | 资源结构、占位符、复数、界面语境，以及翻译与直接编写分流 |
| 写、改或翻译行注释、块注释、文档注释、docstring | [代码注释](./modules/zhushi.md) | 注释语言、文件编码；翻译时由它继续按方向加载制度 |
| 把 Agent skill、规则或 system prompt 译成中文 | [翻译](./modules/fanyi.md) | 先执行译中制度，再由它加载 Agent 规则文档专门制度 |
| 把其它外文内容译成中文 | [翻译](./modules/fanyi.md) | 中文意译、信息核对、术语和译文质检 |
| 把中文译成外语，或按中文意图直接写外语 | [对外表达](./modules/duiwai.md) | 忠实翻译与直接写作分流、力度、结构和官方译名 |
| 解读潜台词、职场话、社交话或网络黑话，或把意思说得得体 | [潜台词与黑话](./modules/taiji.md) | 概率化解读、语气判断和得体表达 |
| 给用户做中文解释、汇报、方案说明或答疑 | [对话交流](./modules/jiaoliu.md) | 术语深浅、解释节奏和对话格式 |
| 写中文文档、报告、README、commit、稿件或社交内容 | [通用中文写作](./modules/xiezuo.md) | 文件语言、信息密度、中英混排和中文成稿质检 |

每个文本片段只从表中选择最具体的入口。场景模块要求的下级制度由它继续加载，主入口不替它跨级调用。

### 五、分层审校

先核对事实、信息边界、受保护内容和规则力度；再不看过程，只读成稿检查自然度、术语一致和读者能否直接理解；最后执行对应场景模块的专门质检。发现问题先改稿，只向用户报告实际问题、必要证据和仍未解决的疑点。

## 继承与例外

场景模块默认继承本文件的全部标准，只写本场景新增的限制、流程和质检，不重复主框架。只有模块明确声明“本场景以此规则为准”时，才能覆盖主框架中的默认处理。

技术正确性与自然表达冲突时，先保证产物可执行且语义正确。例如本地化资源必须先保证结构、占位符和运行时语义正确，再优化自然度和长度。

出现语言、术语或格式冲突时，按以下顺序裁决：

1. 用户对当前产物的明确要求；
2. 项目已有的具体规范；
3. 当前文件已经统一的语言、术语和格式；
4. 对应场景模块和本文件的默认规则。

已有英文文件继续沿用英文，已有中文文件继续沿用中文；新建给中文读者使用的产物默认用简体中文。确实无法从用户要求、项目或文件判断时再询问，不自行猜测。

## 交付前检查

1. 是否定义了读者、目的、载体和目标语言，并按文本片段进入最具体的场景？
2. 信息、力度和事实是否准确，没有擅自增删或把推测写成结论？
3. 代码、命令、路径、URL、配置键、占位符、报错和版本号是否保持原样？
4. 同一概念是否全文同名，术语在当前文本中是否表达清楚？
5. 独立产出物是否清除了对聊天过程的隐性依赖，接收者只看正文也能理解？
6. 是否完成了对应场景的专门质检，并从读者视角通读成稿？
