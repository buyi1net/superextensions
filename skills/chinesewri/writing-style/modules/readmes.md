# README 治理

> 本文件是 `README.md` 的通用骨架与治理规则,覆盖项目内各级目录的 `README.md`.使用方式与场景底稿一致:文件复制对应形态的骨架,再按当前目录的实际内容精准修改;保留章节结构,替换占位内容,删除不适用的章节说明.
>
> 占位内容用 `<尖括号>` 标出,填写时全部替换为实际内容;没有对应内容时删除整行,不要留下无意义的占位符或死链.

## 形态判定

写 `README.md` 前依次回答六个问题,答案确定形态:

1. **读者是谁？** 项目维护者/接手者,还是外部用户?
2. **位置在哪？** 项目根,一级子目录,交付目录,还是对外公开的仓库?
3. **仓库是私有还是公开？** 同样是仓库根:私有研发仓的根 `README.md`按项目根 `README.md`写(服务维护者);公开仓的根按对外仓库形态写(服务陌生访客,骨架见下文「交付相关的 README」);
4. **给人看还是给 agent 看？** `README.md`给人;agent 规则在 `AGENTS.md`,`README.md`只留提醒入口;
5. **能否引用项目内部路径？** 给项目外读者的 `README.md`必须自包含;
6. **单语言还是多语言？** 语言跟随项目主生态,不跟随当前对话语言.

## 常用形态

**项目根目录：**
**位置：**当前项目的根目录
**读者：**维护者 + 接手者
**要点：**项目介绍 + 快速开始 + 根目录清点(双重身份:项目介绍 + 根目录索引)

**项目子目录：**
**位置：**项目一级目录
**读者：**项目维护者
**要点：**分类表 + 索引,让人一眼掌握目录现状

**交付目录：**
**位置：**存放最终交付物的目录
**读者：**维护者(仓内)/ 用户(包内)
**要点：**仓内记交付清单与重建方式;包内自包含

**对外仓库：**
**位置：**对外公开的仓库根(GitHub 等)
**读者：**外部访客
**要点：**第一屏决定别人要不要用:价值主张,演示,License(骨架见下文「交付相关的 README」)
**注意：**对外仓库与项目根 `README.md`的分界:私有研发仓库的根说明文件按「项目根目录」写,公开仓的根才按本形态写

**形态外还有两个不构成独立形态的属性：**

1. **字段变体**:同为子目录 `README.md`,不同目录的索引字段不同,比如 archive 记恢复条件;骨架不变,字段不同;
2. **公开子目录**:monorepo 子产品目录对外公开时,按项目根 `README.md`骨架写但换外部读者视角;低频,实战撞见再升级为独立形态.

**形态判定不了的 Novel 情形：**

1. 按六问往最近形态靠,并在 `README.md` 开头用一句话注明当前定位与读者.
2. 确实放不进任何形态时,停下来向用户确认,不得自创无边界新形态.

## 维护原则

**通用规范：**

1. 只写当前实际存在的内容,不预写计划中的分类,条目或完成状态;内容消失或状态变化后,立即更新当前状态,分类和条目;内容新增,移除,职责或状态变更时,在同一次提交里同步更新所有登记它的 README 索引和清单(包括对外发布仓的说明文件).
2. 写结构,不写快照:不写测试数量,提交数,进度百分比这类很快过期的信息;项目阶段,进展,发布记录属于 docs/ 的内容,`README.md` 最多链接过去,不在正文维护.
3.  `README.md` 面向人类导航:不写 Agent 操作步骤,工作记录,日志;Agent 规则在 `AGENTS.md`, `README.md` 只留提醒入口;对 Agent 而言  `README.md` 中的链接是按需导航不是必读清单,禁止无差别读取.
4. 每个  `README.md` 开头附近固定携带 Agent 提醒行:本文件为用户导航,请按需选读,禁止无差别读取,浪费上下文,如需修改,先读 `AGENTS.md`;面向项目内读者的形态一律带上,不省略.交付包内和公开仓根的 `README.md` 面向外部读者,不带这一行.

**语言规范：**

1. 语言跟随项目的主要使用场景和工具链:上 GitHub 或英文工具链项目用英文,本地中文业务项目用简体中文;同一项目内保持一致;对外项目面向国际受众时英文优先.
2. 统一使用大写 `README.md`:GitHub 会把小写 `readme.md` 也渲染成首页,Windows 不分大小写会撞名,统一大写避免歧义.
3. 双语言或多语言  `README.md` 用主文件+链接(如 `README.zh-CN.md`)或语言切换行,不在同一文件里机械对照翻译.

**链接规范：**

1. 链接必须真实且同步维护:目标存在才做链接;目标被移动,重命名或删除后,在同一次提交里更新或清理指向它的链接;没有本地副本时注明「未获取」或「无」,避免留下死链接.
2. 链接路径规范:项目内一律用相对路径(如 `./docs/架构.md`),目录链接末尾加 `/`(写 `./docs/` 不写 `./docs`,部分显示 Markdown 的工具对无斜杠目录链接处理不稳定);禁止盘符绝对路径(`C:\...`),`file://` 前缀和 `../` 跳出项目根的路径;外部资源用完整 URL(`https://...`).
3. 链接文字要有辨识度:写「见 [架构设计] (路径 ./docs/架构.md)」这种带名字的链接,不写「点这里」;链接显示文字本身就是导航信息;链接目标含中文时直接写中文路径,不做百分号编码(编码由显示工具处理,人写易错);页内跳转(`#xxx`)只用于同一文件内部,中文标题的跳转标记在不同工具里规则不一,跨文件容易断;不链接到 temp/ 等临时内容:临时内容说没就没,索引指向它就是制造死链.

## 项目根目录

```md
# <项目名>

> 本文件为用户导航,请按需选读,禁止无差别读取,浪费上下文;如需修改,先读 [AGENTS.md](./AGENTS.md).

<一段话:是什么,给谁用,解决什么问题.>

## 快速开始

<环境要求,安装,构建,运行,测试的命令块;细节链接到 docs/ 对应文档.>

## 目录结构

| 目录 | 职责 |
|---|---|
| [<目录名>](./<目录名>/) | <一句话职责> |

## 从哪开始读

<docs/ 中的阅读起点,3-5 篇,按接手者的问题组织;docs 刚建立时删掉本节.>

- 想跑起来 → [快速开始详情](./docs/<文件>)
- 想懂结构 → [架构说明](./docs/<文件>)
- 想知道为什么这样设计 → [关键决策](./docs/<文件>)

## 维护

Agent 工作规则见 [AGENTS.md](./AGENTS.md).
```

## 交付目录

维护者清点交付物或面向其它用户的 `README.md`,骨架见下文「交付相关的 README」.

## 对外仓库

常规的项目目录,大概率会包含太多研发测的东西,不利于开源共享,所以在GitHub发布环节,一般会分为研发仓库和公开仓库(开源仓库):

1. 研发仓库:`README.md` 文件按照项目根目录的 `README.md` 文件执行即可.
2. 开源仓库:骨架见下文「交付相关的 README」.

## 交付相关的 README

仓内交付目录,交付包内 `README.md`,公开仓根 `README.md` 三种骨架见下.

### 仓内交付目录骨架

交付树内的 `AGENTS.md` 属于交付内容,怎么建见 writing-agents 的 [入口规则](../../writing-agents/modules/AGENTS-ENTRY.md).

```md
# <目录名>

<一两句话:本目录存放已验证的最终交付物;暂存和半成品在 temp/,不进本目录.>

> 本文件为用户导航,请按需选读,禁止无差别读取,浪费上下文;如需修改,先读 [AGENTS.md](./AGENTS.md).

## 当前交付物

<交付物名> <版本>:

**形态：** <目录 / ZIP / 安装包 / 镜像>
**内容：** <一句话:包里有什么,面向谁>
**校验：** <SHA256 或校验文件路径>
**验证：** <怎么确认它可用:命令或步骤链接>
**重建：** <从哪个脚本或流程重建>
**依赖：** <可选:被依赖交付物及版本;无则删本行>
**渠道：** <可选:外部发布地址(Release 链接/镜像 tag);未发布删本行>
**日期：** <转正为最终交付物的日期>

## 交付记录

<可选:历史版本,撤回与灰度状态;只有当前版本时删掉本节.>
```

### 交付包内 `README.md` 骨架

读者是拿到包的最终用户,没有项目上下文,一切信息自包含:说明文档独立编写,只引用交付包内实际存在的目录和文件,不引用项目根或其它开发路径.

```md
# <产品名> <版本>

<一两句话:这是什么,给谁用.>

## 安装

<按发布渠道写;命令块为主;渠道不明时问用户.>

## 运行

<怎么启动,最小示例.>

## 配置

<可选:配置文件说明;没有就删节.>

## 求助

<问题反馈渠道;内部版写支持边界与授权范围.>

## License

<开源版写许可证;内部版写版权与使用限制.>
```

### 对外仓库骨架(公开仓根 `README.md`)

公开仓库根本身的 `README.md`,是外部访客看到的第一屏,决定别人要不要继续了解这个项目.与项目根 `README.md` 的判定分界在仓库属性:私有研发仓的根按项目根形态写(服务接手者,怎么跑起来);公开仓的根按本骨架写(服务陌生访客,值不值得看,能不能信任).

```md
# <项目名>

<一两句话:是什么,解决什么问题;一句话说清与众不同之处.>

<徽章/版本/平台支持等一行式信号,可选.>

<演示图或 GIF,可选但有图远胜千言.>

## 功能

- <面向用户价值的功能点,不是实现细节>

## 安装

<最短可用路径;按发布渠道写;详细文档链接.>

## 使用

<最小示例或入口.>

## 文档与社区

[完整文档](<链接>), [报告问题](<链接>)

## License

<许可证与一句话声明.>
```

要点:

- 第一屏(标题+首段+配图)必须独立成立:多数人只看这一屏;
- 开源项目面向国际时英文优先,可附中文版链接;内部项目面向内部用户时中文;
- 贡献指南可链接独立 `CONTRIBUTING.md`,不在首页 `README.md` 里展开;
- 公开仓与研发仓同根时合并:项目根章节在前,对外要素(配图,徽章,License)融入,不维护两份 `README.md`;双仓模式下两仓各按各的写,不互相复制.
