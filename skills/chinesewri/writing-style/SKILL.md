只要产出书面内容(文档,报告,说明,README,commit,周报,skill,规则),就必须加载本 skill.日常聊天交流,纯代码实现,即时答疑不走本 skill.新建文件或目录且看不出该放哪,或者移动,重命名,删除文件和目录时,走 [project-layout](../../productivity/project-layout/SKILL.md).

给 Agent 读的文档另加载 [writing-agents](../writing-agents/SKILL.md).

写或改 `README.md` 时,先读 [README 规则](./modules/readmes.md):按读者和位置判定形态,再复制对应骨架.

## 写前四件事

1. 想清楚读者带着什么问题来,按问题组织段落,不按自己知道的顺序排.
2. 第一段先给定位或核心结论,不写客套铺垫.
3. 解释抽象概念时,给一个具体例子.
4. 对齐下方范文的密度,节奏和语言质感,不追字数.

第 1,2 条针对从头读到尾的给人文档;给 Agent 的文档怎么组织,按 [writing-agents](../writing-agents/SKILL.md) 的信息层级来.范文一到三是给人看的文体,范文四是给 Agent 的指令,按要写的文档挑对应的范文对齐.

## 语感基准

写出来的文字要读着像中文母语工程师在跟同事当面讲事情.落笔前先想一句:如果当面跟同事交代,我会怎么说?嘴上怎么说,笔下就怎么写.

对方懂技术,常见技术术语放心用:接口,接缝,回归,兜底,这些词同事天天挂嘴边,读者也懂.描述是否精准靠概念,判断条件和因果,不靠大词,不端架子.端着架子写文档不会更精确,只会更难读.

「当...时」「对...进行」「在...的基础上」这种腔调,正常聊天没人会说,写出来也别这么写.

## 通用原则

- **无歧义优先于简短.** 读者会停下来猜断句或猜指代,就把删掉的成分补回来.句子写完整,自然连词,长短搭配.标题,表格单元格,代码注释这类标签不是句子,可以写短.
- **要删就删整句,留下的句子写完整.** 精简的单位是句子.一句话要么整句删掉,要么整句留下;留下的句子把谁做什么,对什么做,在什么条件下都写出来,跟当面说话一样.
  - 求简短有三条路:
    - 删掉整条没用的句子.
    - 换一个更精准的词.
    - 把啰嗦的说法换成更短但仍然完整的说法,比如读者认得的简称.
  - 把句子的主语,宾语,连接词砍掉压成三四个字,会变成电报体:读者得自己猜省掉了什么,模型也会学着用又短又硬的腔调说话.例如「A,B 互引,成环.」要写成「A 和 B 互相引用,形成了循环依赖.」;「都是构建脚本生成的,不手改.」要写成「这些文件是构建脚本生成的,要改就改源文件,再重新生成.」
  - 把几件事挤进一个段落,省不下篇幅,反倒把主干埋掉,该分段就分段.
- **术语统一.** 同一概念全文用一个词,可能歧义时首次出现标「中文(English)」.中文叫法拿不准时,查 [中英术语表](./modules/terms.md).
- **受保护内容分两类处理.**
  - 代码,命令,路径,配置键,报错原文:一个字都不改.
  - 事实,数据,来源,限制,风险,前置条件,依赖关系,步骤和操作指令:内容和力度都不能变,但措辞可以改写,可以翻译.
- **口头称呼不进正文.** 口头称呼,寒暄和情绪交流只留在对话里,不写进长期文档;人物引语,示例和界面称谓除外.
- **引用带链接.** 提到文件或资源的地方必须给可访问链接.仓库内用相对路径,外部资源用完整 URL,不用反引号代替链接.代码标识,配置键,命令,调用 skill 与示例可用反引号.
- **力度跟原文走.** 「必须」「绝对」这类力度词不算禁用词,改写时不增不减,按原义保持力度.
- **规则正向陈述.** 交代前置条件,依据和动作.条件写在动作前面,写成「如果 X,就 Y;否则 Z」,每种情况都有去处.平视陈述,不夹训诫.

## 排版

- **一段只说一件事.** 写着写着冒出第二件事,就另起一段.围绕同一个论点的连续论述,照常成段.
- **有先后顺序的步骤,用编号列表.** 每一步只做一个动作,用动宾短语开头,比如「读取配置」「比对两份清单」.英文提示词习惯用一个动词开头(「Inline helpers」),中文照搬成「内联辅助」就成了机翻腔,要写成完整的动宾短语.
- **并列的规则,判断依据,检查项用无序列表.** 有两条以上就列,每条单独一项.
- **原因跟在规则后面.** 规则需要讲为什么,就紧跟着一两句讲完;原因写长了才另起一段,别和步骤搅在一起.
- **强调靠结构,不靠堆符号.** 真正的硬约束单独成一项,写在它管的那一步旁边,不用一串感叹号或满篇加粗.流程很长的文档,可以在末尾放一份交差前的自查清单,只列要核对的项,规则本身仍写在原处.
- **段落衔接看读者怎么读.** 给人看的文档从头读到尾,段间靠内容过渡(前一段抛出问题,后一段接着回答,不靠堆过渡词);给 Agent 的文档按小节查阅,段间靠标题和段首一句点题.

## 范文

### 范文一:说明文档体

> 本目录保存用于研究,比较,核验和借鉴的外部材料.项目自有规则,正式 skill,工作记录和交付内容不放在这里.
>
> 收录先做归属判断:外部收集,只用于理解和借鉴的材料进本目录;当前工作要直接采用或随成果交付的正式输入,按它在项目中的实际职责进入源码或交付目录,判断不了的先确认用途再归位.

说明文开头明确用途,边界与收录分类标准.

### 范文二:报告体

> 本周完成三件事:
>
> - 语言类 skill 拆分为四个:翻译,给人写,给 Agent 写,写后检测,各自独立加载,互不污染.
> - 记忆制度按「能不写就不写」重写,项目记忆退役,存量转档到 docs.
> - 总纲交流规范精简为两句,对话不再受写作规则干扰.
>
> 遗留两个问题:
>
> - 长文档的范文还没有,报告写作缺对齐样本.
> - 本机缓存仍是旧版,需要走一次发布同步.
>
> 下周计划:
>
> - 补齐报告体范文.
> - 观察这四个 skill 的实际触发情况,决定是否路由进总纲.

三段式结构:先列成果,再摆遗留问题,最后给下一步.每段开头一句点题;成果和问题每件一条,说清改了什么,为什么.段落之间靠内容自然过渡,不堆过渡词.

### 范文三:commit 体

> constitution 交流规范精简、obra 参考降级为定点参考

一行写清动词加对象,说明这轮改了什么;多处改动用顿号并列,不用长句解释,细节留在正文和 diff 里.

### 范文四:指令文档体(给 Agent)

> 用户一旦选定某个候选方案,就用 Skill 工具加载 `grilling`,陪他走一遍决策树:理清约束条件和依赖关系,看清深化后的模块长什么样,接缝后面藏着什么,哪些测试还能跑通.
>
> 决策过程中冒出的事,用 Skill 工具加载 `domain-modeling`,让领域模型随时跟得上最新进展:
>
> - 深化后的模块用了 `GLOSSARY.md` 里没有的概念来命名?把这个概念补进去.文件还没建,就按 `domain-modeling` 的约定建一个.
> - 聊着聊着把某个模糊说法敲定了?立马更新 `GLOSSARY.md`.
> - 用户因为某个硬理由把方案否了?主动问一句要不要记成 ADR.可以这么说:「要我把这条记下来吗?以后做架构评审,省得别人再提一遍.」但理由得是真的值得后人知道才记.临时性的(比如「现在顾不上」)或者不说也明白的,就算了.
> - 想给深化后的模块另找接口方案?用 Skill 工具加载 `codebase-design`,用它的「Design It Twice」模式:并行拉起多个子代理,给每个发不同的设计约束,各出一版接口设计.

看四处拆解:

- 「理清约束条件和依赖关系,看清深化后的模块长什么样,接缝后面藏着什么」:几个并列说法长短不齐,双字词和口语短语混着用,读着自然.刻意凑成一样长,反倒显得假.
- 「文件还没建,就按 domain-modeling 的约定建一个」:条件和动作一句说完,具体细节交给对应 skill,不要直接抄它的规则.
- 「省得别人再提一遍」:动机要说人话.同一个意思写成「以避免后续重复提议」,就显得机械又呆板.
- 「不说也明白的,就算了」:边界条件用口语收尾,精确度一点没丢.

## 自查三方向

写完通读一遍.读着卡壳,要回头重读的句子就是写坏的,重写它.对照三个滑走方向自查:

- **端起来**:书面腔,翻译腔,被动句,「进行」类动词,定语从句套头.
- **表演**:俏皮词连排,动词用力过猛,读着像抖机灵,换平实说法.
- **偷懒**:压缩到推不回全称,名词短语连排成电报体,几件事挤在一个段落里.

## 写完

写完后用 Skill 工具加载 `writing-check` 查一遍再交稿.
