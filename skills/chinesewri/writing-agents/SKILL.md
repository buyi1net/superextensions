给 AI 读的文档,写法都相通:skill,`AGENTS.md`,`CLAUDE.md`,指针指向的那些,都一样.AI 每次跑的是同一套流程,不是照搬固定输出.结构对了,换哪种载体,行为都可预测.

动笔前先加载 [writing-style](../writing-style/SKILL.md),通用文风规则以它为准,本 skill 不复述.

写 skill 另有一套机制规范:frontmatter 怎么填,调用方式怎么选,路由 skill 怎么用.这些单独放 [`SKILL-MECHANICS.md`](./modules/SKILL-MECHANICS.md) 里讲.

## 常驻与按需

给 AI 读的文档分两类,读者一样,计费与加载方式不同:

- **规则文档**:skill,`AGENTS.md`,`CLAUDE.md`,constitution 这类.入口常驻在上下文里,每轮对话都占 token 并分散注意力;一旦触发读入正文,正文同样进入窗口.这类文档值得精简提炼,后面「两种开销」和「提炼」两节专为此设计.
- **工作物料**:spec,工单,ADR,交接文件这类.按需加载,给冷启动的窗口当唯一上下文.它没写的,读者永远不知道,完整优先:背景,约束,判断依据不砍,只砍真废话.判删信息的标准是「冷启动的窗口还能不能照着干活」,不是「删了 Agent 的行为变没变」.

各节的适用范围:

- 两类都适用:上下文指针,信息层级(含同地放置),排版,完成标准,引导词.
- 只管规则文档:两种开销,提炼,什么时候拆分,外文 skill 并轨流程.

写工作物料时跳过后面这四节;真要删句,用上面那条冷启动判据.

## 上下文指针

上下文指针就是你在 AI 的上下文里写一句话,提一下某个东西的名字,顺便告诉它什么时候需要去读.skill 的 `description` 就是这种指针;`AGENTS.md` 里面提到的某个文档,也是一种上下文指针.

指针的关键不在于材料本身有多重要,而在于你这句话写得够不够精确.AI 什么时候需要读,读了有没有用,全看你指针怎么写.

一份文件哪怕再重要,只要指针没写好,AI 就可能该读的时候不读,不该读的时候乱读.所以先把指针写好.

路由实在说不清楚,可以考虑直接把文档内容写进去,这时候就别用链接的方式做路由了.

一个好的指针就干两件事:

1. 说清楚「这是什么」.
2. 列出**什么情况**下该去读它.比如:用户说 A 就看这一段,用户说 B 就看那一段.

指针指向文件或资源时,引用格式与可访问链接要求按 [writing-style](../writing-style/SKILL.md) 执行.

对于常驻入口(如 skill 的 description,`AGENTS.md`),它会一直占着 Agent 的上下文,每轮对话都要花 token,所以它更值得好好提炼:

- **最重要的话放最前面**.AI 第一眼看到的就是触发条件.
- **一个场景只写一条**.如果两个词是一个意思(比如「退款」和「退钱」),那就给指针合并,重复的指针就是浪费 token.
- **正文里说过的身份信息,指针里别再写**.正文已经是《退款流程指南》了,指针里就不用再说「这是退款流程」.

## 两种开销

每加一份文档或一条指针,都要花两种预算.这笔账按实际加载方式算:入口常驻的每轮都在付,正文被读进上下文以后也一直占着.

- **上下文开销**:`AGENTS.md` 里的一句话,skill 的 `description`,不管这轮用不用得上,都一直占着上下文窗口,既花 token,也分散 Agent 的注意力.
- **认知开销**:用户脑子里记「项目内有哪些文档,什么情况下该看哪份」,还有审稿时亲自读文档花的精力.用户是索引:建了哪些文档,该读哪份,靠他的记忆导航,所以这份开销是人还在做判断的代价,不用拼命压.比如 spec 必须用户亲自审,审稿的工夫不能省;工单是给 Agent 施工的,不占这份开销.

需要通过指针去翻的材料,在尚未加载正文前只花指针那一行的 token 和注意力;一旦加载,正文开销按实际载入内容计算.没指针的材料,全由认知开销扛着.

## 信息层级

一份文档,内容就两种:**步骤**和**参考资料**.步骤是 Agent 按顺序干的事.参考资料是定义,规则,事实这些,用到再查.两种可以自由混用:全是步骤,全是参考资料,或者两个都有,都行.

核心问题就一个:每块内容放哪一层?

1. **步骤写在主文件里**.首选,Agent 该干什么,直接写清楚.
2. **参考资料写在主文件里**.用到再翻就行.经常是一堆平级内容,每条一样重要,这么安排也没问题.
3. **参考资料外置**.单独放一个文件,用指针挂着,触发了才加载.可以放同文件夹,也可以放别处,谁想指都可以.

难在拿捏分寸.压得太少,主文件臃肿;压得太多,Agent 真要用的东西又找不着.

**渐进式披露**就是往下沉:把内容挪出主文件,放到指针后面,单独挪进一个文件,主文件只留一行话指过去,保持清爽.这主要不是为了省 token,是为了保住层级结构本身.

该不该下沉,看**分支**:所有分支都用的,写主文件里;只有部分分支用得上的,放指针后面.带步骤的文档尤其要注意:该外置的参考资料混在主文件里,会把步骤埋了,Agent 看没看到全凭运气.分支越多,混在一起的变数就越大.

**同地放置**是主文件里的配套原则.层级决定一块内容往下放多远,同地放置决定它到了那儿跟什么放一起.一个概念的解释,规则,注意事项,尽量收在同一个标题下,别东一句西一句.读到其中一块,旁边的自然带出来.

检验标准很简单:这文档读起来像不像专门给 Agent 写的说明书?归好类的就像,到处乱放的不像.(这不同于重复.重复是一个意思写两遍,分散是一个意思拆碎在各处.)

**膨胀**是最容易踩的坑.文档太长,哪怕句句有用,句句不重复,上下文也撑得太长,模型注意力被稀释.每多一行,就多一行要管.解法还是层级那套:参考资料往指针后面塞,按分支或流程拆开,每条路径只带自己需要的东西.

## 排版

Agent 读规则时,不光学内容,也学写法.skill 里一段装着三件事,它写出来的文档也会一段装三件事;skill 通篇大段文字,它交的报告也会通篇大段文字.所以排版本身就是规则的一部分.通用排版规则按 [writing-style](../writing-style/SKILL.md) 执行.

在给 Agent 的文档里,额外注意以下几点:

- **一段的中心意思通常是点题,下定义,讲原因,交代一条事实.**
- **条件里写清楚是谁的情况.** 比如「命令执行失败」和「用户拒绝授权」是两回事,别都写成「失败了」.
- **段首点题比连接词管用.** 段间衔接的规矩见 [writing-style](../writing-style/SKILL.md).Agent 按小节查着读,「另外」「接下来」这类连接词加了也没用.
- **产出有固定格式要求时,给输出骨架.** 用代码块写出格式.检索,筛选,检查这类可能什么都找不到的任务,再单独写一句「什么都没找到时输出什么」;少了这句,Agent 找不到东西时容易编一段凑数.

一个排版合格的小节长这样:

````markdown
## 查重复

先读 issue 全文,再在同一个仓库里找相似的 issue.

1. 用 `gh issue view <编号> --comments` 读取 issue 正文和全部评论.
2. 用标题里的关键词搜索还没关闭的 issue.
3. 逐个比对:报的是同一个根因,才算重复;现象相似但原因不同的,不算.

输出:

```text
可能重复:
- #<编号> <标题>:<一句话理由>
```

一个都没找到,就回复「没有找到重复 issue」.
````

## 步骤与完成标准

每一步都有个**完成标准**,就是告诉 Agent「这事干完了」的条件.这个标准有两个关键点:清晰度和要求高低.

### 清晰度

Agent 能不能分得清到底是「做完了」还是「没做完」?如果这个标准比较模糊,比如「理解了就行」,Agent 就容易提前收工.

它的行为是被上下文推着走的:上下文里能看到后面还有活,它就惦记着往下赶.所以完成标准就像一道闸门:闸门没开(标准没满足),它迈不到下一步.闸门标准越清楚,Agent 越难蒙混过关,没法用「差不多得了」糊弄过去.

改法分两步:

1. **先改标准本身,这是首选.** 把「理解了就行」改成能判断真假的条件,比如「能复述出三个要点」「产出文件 X 且通过检查」.成本低,见效快,不用动结构.
2. **标准实在改不清楚,而且确实出现过抢跑,再拆步骤.** 把后面的步骤挪出当前上下文,让 Agent 看不见.看不见,就没法「惦记着完事」,只能老老实实把当前这步干完.

藏起来只有跨过真正的上下文边界才管用.有效的隔离有两种:

- 当前这步干完了交给用户,下一段由用户重新发起.
- 派子代理去干,它有自己独立的上下文,看不到主流程后面的步骤.

如果只是在主流程里直接调用下一个 skill,后面的步骤就还在上下文里,等于没藏.

### 要求高低

标准的轻重会直接决定 Agent 投入多大精力.比如写「每个用户反馈的信息都回复过了」,Agent 就必须逐条处理;写「列个改动清单」,Agent 就可以随便列列.标准就是力度的刻度盘,你定得越重,它就得越拼.

要求高的标准,不用明确写「你要去翻查,核实」.Agent 为了满足高标准,自己就会去下笨功夫,比如逐条核对,翻查原始材料,反复验证有没有遗漏.这些工作量藏在措辞里,不用单独写成一个步骤.

标准绑定的范围可大可小:

- 「每一条规则都用到」→ 绑的是一整份参考资料(横跨所有规则).
- 「每一步都做完」→ 绑的是一整串步骤(横跨整个流程).

一份文档可能通篇都是参考资料,没有明确的操作步骤,看起来「没法卡完成标准」.但只要你在某处写一句「必须做彻底」,这个要求就横跨整份材料生效,Agent 面对每一份资料时,都被这根标准压着.

最强的完成标准,既**能检查**(做完没做完一看便知),又**全覆盖**(没有漏网之鱼).

## 什么时候拆分

把一个文档拆成两个,本质是在「上下文开销」和「认知开销」之间做取舍.**只有在拆分带来的收益大于成本时,才值得动手.**

常见的拆法有两种:

- **按流程拆**:后面的步骤会诱使 Agent 急着做完当前这一步,就把后面的步骤拆出去藏起来.看不见后面的步骤,Agent 才会老老实实把手头的活干透.反过来也要小心:把拆开的流程合回去,每一步都能看到后面的步骤,就会诱导 Agent 提前收工.
- **按调用方式拆**:skill 专用,详见 [`SKILL-MECHANICS.md`](./modules/SKILL-MECHANICS.md).

## 引导词

引导词(Leading words)是 LLM 在预训练阶段就学过的词,比如 `lesson`,`fog of war`,`tracer bullets`.这个词一出现,LLM 就会按它背后的一整套意思去想问题.它借用了 LLM 本身就有的知识,可以花最少的 token,锚定一整套 Agent 行为.

能不自造词就不要自造词.自己造的词,定义足够清晰也能用,但借不到模型在预训练里已经学过的意思:你定义一个词所花的 token,比预训练里学到的词贵得多,何况不同 LLM 预训练学到的东西也不一样.实在需要自造词,必须先在 `GLOSSARY.md` 给出权威定义并持续使用.

它分两个层面:

- **执行任务时**:每当某个词出现,Agent 都会执行相同的行为.
- **指针层面**:它把 LLM 的注意力集中到某一事物上,让 Agent 知道该找什么.同一个词同时出现在你的提示词,文档和代码库里,Agent 就会把这种共享语言和那份材料关联起来,翻资料也更稳,更准.

所以要找机会用引导词来重构文件.比如同一个意思反复解释了好几遍,一个指针写了一整句话才说清楚,这些都能压成一个词:

- 「又快又准,还不费什么资源」→ **tight**(一个 _tight_ 循环)
- 「一个你信得过的循环」→ **红**(把模糊的门槛变成一个可观测的状态,bug 出现时循环变「红」,否则不变)

这个方法可以一箭双雕:不仅 token 花得少,Agent 的想法也不跑偏.

**反过来,否定式表达是引导词旁边最容易翻的车.** 用「禁止」来引导,等于把禁止的行为拽进上下文,它反而可能更容易被想起来.就像「别想大象」,结果满脑子都是大象.

所以优先把目标行为正面说出来(比如「写一行注释」).只有实在没法正面写的硬护栏才用否定式;用了,就紧跟着写出正面目标,再举个正面例子,让注意力落在「该做什么」上.

## 提炼

> **优先级**:本节管规则文档;工作物料(spec,工单,ADR,交接)不走这里的底线,判据见「常驻与按需」.
>
> 想删句子,想压缩措辞,先过两条底线,两条都过才谈得上提炼,拿不准就保持原样:
>
> 1. 删了这句,Agent 干的事一模一样.
> 2. 压缩之后还是一句完整的话(规则按 [writing-style](../writing-style/SKILL.md) 执行),用到的简称读者能从字面推出全称.引导词不受这条限制,它靠的是模型本来就懂的词,见「引导词」.

- **要删就删整句,留下的句子写完整.** 规则与改写示例按 [writing-style](../writing-style/SKILL.md) 执行,本 skill 不复述.
- **每个意思只放一处.** 这样有个好处,想修改 Agent 行为只需要修改这一处.同一个意思出现在多个地方不但维护成本高,费 token,还会把一个意思在信息层级上的权重抬到它不该有的位置.这和引导词正好相反:引导词刻意重复同一个词,但从来不重复含义.
- **环境本身就是个可靠的信息源.** 比如 `package.json` 里的脚本,配置文件,目录结构,`--help` 的输出.文档把环境里的东西抄一遍,本质是**缓存**:把查一下就有答案的东西复制了一份.只有当场查起来成本很高,才值得写进文档.

  该写进文档的是 Agent 自己查不到的东西:没写下来的惯例,某个决定背后的原因,配置文件里看不出来的坑.那种「一个文件,一条命令」就能查到的,让 Agent 自己去环境里查就行.
- **每一行都检查一下还有没有用.** 有用 = 对这份文档要干的事还有帮助.没用的分两种:一种是从来就没帮上忙(比如纯解释性的废话,或者本来该外置的分支);另一种是以前有用,但它描述的行为或环境已经变了.

  文档越短,越容易保持有用.不管不顾地往里堆,迟早会**积灰**:过时的内容一层盖一层,因为往里加东西觉得安全,往外删东西觉得冒险.直到有一天,你想找条还有用的信息,得先把好几层灰扒开.
- **标点符号用半角.** 写给 Agent 的文档,代码块和命令以外的正文也用半角标点.
- **逐句排查「废话指令」.** 一条 LLM 默认就会遵守的指令,写了等于白写,还占篇幅.判断标准是「它相对默认行为有没有改变」,这看的是 LLM 而不是用户.两个审稿人要是对某条是不是废话指令有分歧,那就是他们对默认行为有分歧.

  判断办法只有一个:假想把这句删掉,Agent 干的事有没有变化?如果没有变化,那么这一整句就是废话,按上面「要删就删整句」把它整句删掉.这套标准也管引导词,如果一个词的效果还不如 Agent 的默认行为,那就是废话指令,解决办法是换一个更有效的词来表达,比如换成「死磕到底」.

## 外文 skill 并轨流程

跟随上游更新或引进外文 skill 时,按四步并轨处理:

1. **定目标形态**:按本 skill 规范确定产物结构,层级,完成标准和指针.
2. **两段式转述**:先理清原文完整信息点,再合上原文按中文母语自然表达重说,不逐词英式直译.
3. **删改原文结构先问用户**:去重,合并清单,调整流程超出单纯翻译范畴,属于重构.改动前必须向用户说明要改什么,点头后再动.
4. **体系并轨**:外文机制逐项对到目标项目体系.如词汇表文件(`CONTEXT.md` 对到 `GLOSSARY.md`),决策门槛(ADR 准入归 `domain-modeling`,不在译文抄第二份),跨 skill 调用统一写「用 Skill 工具加载 `skill名`」.拿不准时,先查目标体系里对应的规范怎么定,以它为准.
