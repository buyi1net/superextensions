任何中文成稿（文档、报告、commit、翻译产物、skill 正文）交稿前必须过检。本检查只约束本次交稿，交稿后的对话与其他产出不受约束。新写或大改（动了结构、加了新概念）的稿件：先过视角检查 → 机械检查 → 逐项检查 → 翻译腔检查，改完复查闭环，最后过冷读终审。小改（措辞、替换、删冗余）：自查视角检查 + 机械检查 + 逐项检查（波及范围），改完复查对应维度即可，不必冷读。

## 视角检查

读者没有你写作时的背景（对话共识、本机环境、项目路径、刚查过的事实）。交稿前换三个视角扫一遍：

- **陌生读者视角**：读者只带自己环境里本来就有的东西（项目总纲、同包 skill，或自己的常识），不带这次对话的背景。查：有没有暗语（靠对话背景才懂的词）、悬空指代（读者读完能不能照做、能不能读懂）。
- **环境视角**：对每个引用问一句“在读者的环境里存在吗”。
    - 给 Agent 的文档：同包内容（skill 名、模块名）可以互引，包是成套安装的；项目路径只能出现在项目级文档，分发出去的 skill 不写“本仓库”这类项目自称；环境设施（如某个 MCP、本机路径）只能作为举例，不把“当前是 X”写成事实。
    - 给人的文档：项目内路径对有仓库的读者可达，本机路径和内网地址不可达。
- **人类视角**：任何人从头读都没有自动加载的上下文。查：自造词有没有当场定义、句子有没有删掉关键限定词、结构能不能扫一眼定位。

新写或大改三个视角全过；小改自查陌生读者视角即可。自查盲区由冷读兜底。

## 机械检查（必过）

- 破折号“，”和单字“—”全文搜一遍，一处不留。
    - 引出解释 → 用冒号
    - 补充说明 → 用括号
    - 前后两个意思 → 拆成两句

## 逐项检查

下面的词作普通修饰时替换；是术语或项目固定用法时保留（如工程语境的“闭环”“回归”）。

- “值得注意的是”“不难发现”“我们可以看出”“正如我们所知” → 删，直接说结论
- “为了更好地”“在…的基础上”“对…进行（分析/评估/处理）” → 换成直接动词
- “标志着”“见证了”“奠定了” → 删意义评判，只留事实
- “赋能”“抓手”“闭环”“深耕”“沉淀”“矩阵”“生态”“赛道” → 换成具体动作
- “不仅…更是…”“既…又…还…” → 有实质对比才用，否则拆开
- “蓬勃发展”“日新月异”“举足轻重”“不可或缺” → 换成具体事实（如“2024 年增长 40%”）
- 任何“展望未来”“机遇与挑战并存”“前景广阔” → 有下一步写下一步，没有就停
- 三连排比（“高效、稳定、可靠”） → 有几点写几点，不硬凑三个
- 副词加形容词堆砌（“全面提升了整体性能表现”） → 删修饰，留事实（如“读操作变快，写入不受影响”）
- 连续被动句（“被”“得到了”堆叠） → 改主动语态，中文能主动就主动
- 一句话里超过两个限定词（“通过这套机制可以基本上比较有效地…”） → 精简到不产生歧义为止，一句一个重点

## 翻译腔检查

译文和原创中文都查，原创中文也会染上英文句法，读着别扭。

- **代词悬空**：“它/他”没有先行词，或先代词后出现名词 → 补先行词，或重复名词（中文重复名词即清晰）
- **隐性被动**：“X 已经由 Y 做好” → “Y 已经做好 X”，不带“被”字的英译被动也改主动
- **抽象名词直译悬空**：“从一种状态搬到另一种状态” → 落到具体场景（如“换服务商、换数据库这类整体切换”）
- **动宾不完整**：“点什么、复制什么” → “点什么地方、复制什么信息”
- **英文功能词直译**：“它可能用来配置…”（It might…） → “典型场景是配置…”
- **动词用力过猛**：俏皮词连排、处处抖机灵，读着像表演 → 换平实说法，平实也能有画面（如“翻一段提交历史”）
- **长句不拆、前置定语“的”字链超两层** → 拆成流水短句，一句一个重点，或改话题句
- **名词化堆叠**：“X 的实现”“对 Y 的使用” → 还原成动词句
- **显化连接词堆叠**：“因为…所以…”“当…时”逐个译出 → 语序能暗示就删
- **泛指量词滥用**：“点击一个按钮” → “点击按钮”

## 复查闭环

改稿不是终点，改完可能引入新的不一致。按改动规模复查：

- **小改**（措辞、替换、删冗余）：对本次改动触及的维度全文重扫（改人称重扫人称，改术语重扫术语）。
- **大改**（动结构、整段重写）：全套检查重过一遍。
- 本次修改新写入的句子，无论大小改，都过一遍机械检查和逐项检查。

## 冷读终审

**为什么需要冷读**
作者自查存在天然盲区，自我感受往往偏乐观，自己读着顺的句子，冷读者未必认同。因此，高风险稿件在完成自查、改稿、复查全部流程后，交稿前必须经过冷读验证，未通过冷读不算终审完成。

**哪些稿需要冷读**
交稿前先做风险评估：稿件出错是否会产生扩散影响？

- **需冷读**：进公开仓、对外发布、长期供所有 Agent 阅读的正文，凡新写或大改必做冷读。
- **可免冷读**：仅供本地参考、一次性使用的小稿，自查完成后可直接交稿。
- **拿不准的，按高风险处理**。

**如何执行冷读**

1. **冷读者选择**：安排一个不带写作背景的子 Agent，只提供稿件和读者真实会携带的上下文（按视角检查标准），不提供对话历史或改稿过程。若无子 Agent 可用，则开启一个不带历史记录的全新会话充当冷读者。
2. **冷读提问方向**：重点收集，哪里读不懂、哪个引用不明确、哪句表达不流畅；翻译稿额外标注“哪句像翻译腔”。
3. **冷读职责**：仅挑毛病，不负责改稿，问题逐条列出。

**反馈处理原则**

- 冷读反馈须逐条回应：要么改稿，要么核实后判定为误报，不可整批忽略。
- 修改后按复查流程重扫；整段重写的部分，需再冷读一轮。
- 小范围调整（措辞、替换、删减冗余）自查即可，无需重复冷读。

**特殊情形**
若运行环境无法启用子 Agent 或新会话，交稿时须备注“未经冷读”，并请用户抽查语言质量，不静默跳过。

## 受保护内容

- 事实、数据、来源
- 代码、命令、路径、配置键、报错原文
- 限制、风险、前置条件、依赖关系
- 步骤、操作指令
- 链接（必须是可访问的完整路径）
