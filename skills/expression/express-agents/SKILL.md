给 AI 读的文档,写法都相通:skill,`AGENTS.md`,`CLAUDE.md`,指针指向的那些,都一样.AI 每次跑的是同一套流程,不是照搬固定输出.结构对了,换哪种载体,行为都可预测.

写 skill 另有一套机制上的事:frontmatter 怎么填,调用方式怎么选,路由 skill 怎么用.这些单独放 [`SKILL-MECHANICS.md`](./modules/SKILL-MECHANICS.md) 里讲.

## 常驻与按需

给 AI 读的文档分两类,读者一样,计费不同:一个每轮都付钱,一个只在被读时付一次.

- **规则文档**:skill,`AGENTS.md`,`CLAUDE.md`,constitution 这类.常驻上下文,每轮对话都占一次 token,省一行就是每轮都省,所以删压有理.后面「两种开销」和「提炼」两节,是为这类文档设计的.
- **工作物料**:spec,工单,ADR,交接文件这类.按需加载,给冷启动的窗口当唯一上下文.它没写的,读者永远不知道,完整优先:背景,约束,判断依据不砍,只砍真废话.判删信息的标准是「冷启动的窗口还能不能照着干活」,不是「删了 Agent 的行为变没变」.

两类通用:语感,信息层级(含同地放置),完成标准,引导词.只管规则文档:两种开销,提炼,什么时候拆分.写工作物料,跳过后三节;真要删句,用上面那条冷启动判据.

## 语感

给 Agent 写文档,无歧义为最高优先级.

语感上只有一个场景:**跟技术部同事聊怎么干活**.对方懂技术,懂术语,但是没耐心听铺垫.

写之前先想一下:这话如果两个简体中文母语者当面会怎么交流?俩人当面怎么交流,文档就应该怎么写.

描述是否精准靠的是术语和判断条件,而不是靠端着给人一种看似专业的感觉.比如「这个 ADR 必须真的需要后续的维护者知道,才值得记录」,它比「该理由须具备跨周期的决策参考价值」强,既精确又易读.端着架子写文档不会更精确,只会更难阅读.

技术术语可以放心用,接口,接缝,回归,兜底,技术同事天天挂嘴边的词,Agent 肯定也懂.倒是「当...时」「对...进行」这种腔,正常聊天没人会这么说话.

下面这段是真实 skill 指令,看它的口气:

> 用户一旦选定某个候选方案,就用 Skill 工具加载 `grilling`,陪他走一遍决策树:理清约束条件和依赖关系,看清深化后的模块长什么样,接缝后面藏着什么,哪些测试还能跑通.决策过程中冒出的事,要及时调用 `domain-modeling`,让领域模型随时跟得上最新进展:
>
> - 深化后的模块用了 `GLOSSARY.md` 里没有的概念来命名?把这个概念补进去.文件还没建,就按 `domain-modeling` 的约定建一个.
> - 聊着聊着把某个模糊说法敲定了?立马更新 `GLOSSARY.md`.
> - 用户因为某个硬理由把方案否了?主动问一句要不要记成 ADR.可以这么说:「要我把这条记下来吗?以后做架构评审,省得别人再提一遍.」但理由得是真的值得后人知道才记.临时性的(比如「现在顾不上」)或者不说也明白的,就算了.
> - 想给深化后的模块另找接口方案?用 Skill 工具加载 `codebase-design`,用它的「Design It Twice」模式:并行拉起多个子代理,给每个发不同的设计约束,各出一版接口设计.

看四处:

- 「理清约束条件和依赖关系,看清深化后的模块长什么样,接缝后面藏着什么」:几个并列的说法长短不齐,双字词和口语短语混着来,这样显得自然.刻意凑成一样长,反倒显得假.
- 「文件还没建,就按 domain-modeling 的约定建一个」:条件和动作一句说完,具体细节交给对应的 skill,不要直接抄它的规则.
- 「省得别人再提一遍」:动机要说人话.同一个意思写成「以避免后续重复提议」,就显得机械又呆板.
- 「不说也明白的,就算了」:边界条件用口语收尾,精确度一点没丢.

写完之后先自己读一遍;「滑走三方向」的自查手法见 [express-writing 文风节](../express-writing/SKILL.md).翻译其它语言的 skill 是另一回事:先走 `express-translate` 的「翻译外文 skill」流程,翻译期间它和本 skill 一起加载.

## 上下文指针

上下文指针就是你在 AI 的上下文里写一句话,提一下某个东西的名字,顺便告诉它什么时候需要去读.skill 的 `description` 就是这种指针;`AGENTS.md` 里面提到的某个文档,也是一种上下文指针.它的关键不在于材料本身有多重要,而在于你这句话写得够不够精确.AI 什么时候需要读,读了有没有用,全看你指针怎么写.

一份文件哪怕再重要,只要对应的路由没写好,AI 就可能该读的时候不读,不该读的时候乱读.所以首先就要把路由说明写好,实在说不清楚,可以考虑直接把文档内容写进去,这时候就别用链接的方式做路由了.

一个好的指针就干两件事:

1. 说清楚「这是什么」.
2. 列出**什么情况**下该去读它.比如:用户说 A 就看这一段,用户说 B 就看那一段.

指针指向文件或资源,就必须带可访问的链接:如果在仓库内就用相对路径,如果是外部资源就用完整 URL.千万不能拿反引号代替链接.(「用 skill 工具加载 `skill名`」这类调用句和摘录的示例不算指针,不受这条管.)

指针会一直占用 Agent 的上下文,每轮对话都需要花费一定的 Token,所以它更值得好好提炼.

**至于怎么提炼?**

- **最重要的话放最前面**.AI 第一眼看到的就是触发条件.
- **一个场景只写一条**.如果两个词是一个意思(比如「退款」和「退钱」),那就给指针合并,重复的指针就是浪费 Token.
- **正文里说过的身份信息,指针里别再写**.正文已经是《退款流程指南》了,指针里就不用再说「这是退款流程」.

## 两种开销

每加一份文档或一条指针,都要花两种预算(这笔账按常驻文档算,工作物料按次付,见「常驻与按需」).

- **上下文开销**:数据始终加载在 Agent 的上下文窗口里,不管是 `AGENTS.md` 里面的一句话,还是 skill 的 `description` 描述信息,无论这轮对话是否用到这些东西,它们都会占用 Agent 的上下文窗口,这样既消耗 Token,也消耗 Agent 的注意力.
- **认知开销**:用户脑子里记「项目内有哪些文档,什么情况下该看哪份」,还有审稿时亲自读文档花的精力.用户是索引:建了哪些文档,该读哪份,靠他的记忆导航,所以这份开销是人还在做判断的代价,不用拼命压.比如 spec 必须用户亲自审,审稿的工夫不能省;工单是给 Agent 施工的,不占这份开销.

需要通过指针去翻的材料,只花指针那一行的 Token 和注意力.没指针的材料,全由认知开销扛着.

## 信息层级

一份文档,内容就两种:**步骤**和**参考资料**.步骤是 Agent 按顺序干的事.参考资料是定义,规则,事实这些,用到再查.两种可以自由混用:全是步骤,全是参考资料,或者两个都有,都行.

核心问题就一个:每块内容放哪一层?

1. **步骤写在主文件里**.最优先,Agent 该干什么,直接写清楚.
2. **参考资料写在主文件里**.用到再翻就行.经常是一堆平级内容,每条一样重要,这么安排也没问题.
3. **参考资料外置**.单独放一个文件,用指针挂着,触发了才加载.可以放同文件夹,也可以放别处,谁想指都可以.

难在拿捏分寸.压得太少,主文件臃肿;压得太多,Agent 真要用的东西又找不着.

**渐进式披露**就是往下沉:把内容挪出主文件,放到指针后面,单独挪进一个文件,主文件只留一行话指过去,保持清爽.这主要不是为了省 Token,是为了保住层级结构本身.该不该下沉,看**分支**:所有分支都用的,写主文件里;只有部分分支用得上的,放指针后面.带步骤的文档尤其要注意:该外置的参考资料混在主文件里,会把步骤埋了,Agent 看没看到全凭运气.这不只是清不清晰的问题,还是个「不确定性杠杆」:分支越多,混在一起的变数越大.

**同地放置**是主文件里的配套原则.层级决定一块内容往下放多远,同地放置决定它到了那儿跟什么放一起.一个概念的解释,规则,注意事项,尽量收在同一个标题下,别东一句西一句.读到其中一块,旁边的自然带出来.检验标准很简单:这文档读起来像不像专门给 Agent 写的说明书?归好类的就像,到处乱放的不像.(这不同于重复.重复是一个意思写两遍,分散是一个意思拆碎在各处.)

**膨胀**是最容易踩的坑.文档太长,哪怕句句有用,句句不重复,上下文也撑得太长,模型注意力被稀释.每多一行,就多一行要管.解法还是层级那套:参考资料往指针后面塞,按分支或流程拆开,每条路径只带自己需要的东西.

## 步骤与完成标准

每一步都有个**完成标准**,就是告诉 Agent「这事干完了」的条件.这个标准有两个关键点.

- **清晰度**:Agent 能不能分得清到底是「做完了」还是「没做完」?如果这个标准比较模糊,比如「理解了就行」,Agent 就容易提前收工.它的行为是被上下文推着走的,如果它知道后面还有活,就不会停在半路上.所以完成标准就像一道闸门:闸门没开(标准没满足),它迈不到下一步.闸门标准越清楚,Agent 越难蒙混过关:它没法用「差不多得了」糊弄过去.至于怎么搞?分两步走,先修改标准本身,这是首选.把「理解了就行」改成能判断真假的条件,比如「能复述出三个要点」「产出文件 X 且通过检查」.成本低,见效快,不用动结构.如果标准实在改不清楚,且你确实见过它抢跑,那就拆步骤.把后面的步骤挪出当前上下文,让 Agent 看不见.看不见,就没法「惦记着完事」,只能老老实实把当前这步干完.但这里有个关键限制:藏起来只有跨过真正的上下文边界才管用.比如当前这步干完了,交给用户,下一段由用户重新发起,或者派个子代理去干,它有自己独立的上下文,且看不到主流程后面的步骤,如果只是在主流程里直接调用,后面的步骤还在上下文里,那等于是没藏.
- **要求高低**:标准的轻重会直接决定 Agent 投入多大精力,比如「每个用户反馈的信息都回复过了」,Agent 就必须逐条处理用户的反馈信息,如果你说「列个改动清单」,那 Agent 就可以随便列列.标准就是力度的刻度盘,你定得越重,它就得越拼.要求高的标准,不会明确写「你要去翻查,核实」,但 Agent 为了满足高标准,自己就会去下笨功夫,比如逐条核对,翻查原始材料,反复验证有没有遗漏,这些工作量藏在措辞里,并不用单独写成一个步骤.标准绑定的范围可大可小,「每一条规则都用到」→ 绑的是一整份参考资料(横跨所有规则),「每一步都做完」→ 绑的是一整串步骤(横跨整个流程).一份文档可能通篇都是参考资料(没有明确的操作步骤),看起来「没法卡完成标准」,但只要你在某处写一句「必须做彻底」,这个要求就横跨整份材料生效.Agent 面对每一份资料时,都被这根标准压着.

最强的完成标准,既**能检查**(做完没做完一看便知),又**全覆盖**(没有漏网之鱼).

## 什么时候拆分

把一个文档拆成两个,本质是在「上下文开销」和「认知开销」之间做取舍.**只有在拆分带来的收益大于成本时,才值得动手.**

常见的拆法有两种.一种是**按流程拆**:后面的步骤会诱使 Agent 急着做完当前这一步,就把后面的步骤拆出去藏起来.看不见后面的步骤,Agent 才会老老实实把手头的活干透.反过来也要小心:把拆开的流程合回去,每一步都能看到后面的步骤,就会诱导 Agent 提前收工.另一种是**按调用方式拆**,skill 专用,详见 [`SKILL-MECHANICS.md`](./modules/SKILL-MECHANICS.md).

## 引导词

引导词(Leading words)是个简洁的概念,它已经存在于 LLM 的预训练阶段,当这个词出现时,LLM 会根据这个词来思考问题,比如 `lesson`,`fog of war`,`tracer bullets`.它借用了 LLM 本身就有的知识,可以花最少的 Token,锚定一整套 Agent 行为.如果非要自己造词,定义足够清晰也可以,但是你造的词调用不了模型既有的知识,你在定义一个词所花的 Token,比预训练中所学到的词贵得多,更别提不同 LLM 预训练中得到的知识也不同,所以能不自造词就不要自造词汇.

它分两个层面.在执行任务时,每当某个词出现时,Agent 都会执行相同的行为.在指针层面,它会将 LLM 的注意力集中到某一事物上,让 Agent 知道该找什么.同一个词同时出现在你的提示词,文档和代码库里,Agent 就会把这种共享语言和那份材料关联起来,翻资料也更稳,更准.

所以要找机会用引导词来重构文件.比如同一个意思反复解释了好几遍,一个指针写了一整句话才说清楚,这些都能压成一个词:

- 「又快又准,还不费什么资源」→ **tight**(一个 _tight_ 循环)
- 「一个你信得过的循环」→ **红**(把模糊的门槛变成一个可观测的状态,bug 出现时循环变「红」,否则不变)

这个方法可以一箭双雕:不仅 Token 花得少,Agent 的想法也不跑偏.你可以假设每份文档里都有很多能用引导词替换的重复表述,找出来,换掉.

**反过来,否定式表达是引导词旁边最容易翻的车.** 用「禁止」来引导,等于把禁止的行为拽进上下文,让它**更容易**被触发,不是更难.「别想大象」,结果满脑子都是大象.「别」这个否定词太弱,压不住已经被激活的核心概念,所以「不许做 X」在 Agent 那儿差不多等于「做 X」.要写就写**正面的**:把目标行为说出来(比如「写一行注释」),被禁的那个连提都别提.只有实在没法正面写的硬护栏,才用否定式;就算用,也得同时把正面目标写出来,让注意力落在「该做什么」上.如果必须要禁止,就在禁止后面举个正面的例子,让 Agent 知道为什么禁止,以及禁止后该怎么做的正确示例.

## 提炼

> **优先级**:本节管规则文档;工作物料(spec,工单,ADR,交接)不走这里的底线,判据见「常驻与按需」.想删句子,想压缩措辞,先过两条底线.① 删了这句,Agent 干的事一模一样;② 压缩之后,读者还能从字面推出全称.两条都过,才谈得上提炼.拿不准,就保持原样.

- **每个意思只放一处**:这样有个好处,想修改 Agent 行为只需要修改这一处.同一个意思出现在多个地方不但维护成本高,费 Token,还会把一个意思在信息层级上的权重抬到它不该有的位置.这和引导词正好相反:引导词刻意重复同一个词,但从来不重复含义.
- **环境本身就是个可靠的信息源**(比如 `package.json` 里的脚本,配置文件,目录结构,`--help` 的输出).文档把环境里的东西抄一遍,本质是**缓存**:把查一下就有答案的东西复制了一份.只有当场查起来成本很高,才值得写进文档.该写进文档的是 Agent 自己查不到的东西:没写下来的惯例,某个决定背后的原因,配置文件里看不出来的坑.那种「一个文件,一条命令」就能查到的,让 Agent 自己去环境里查就行.
- **每一行都检查一下还有没有用**:有用 = 对这份文档要干的事还有帮助.没用的分两种:一种是从来就没帮上忙(比如纯解释性的废话,或者本来该外置的分支);另一种是以前有用,但它描述的行为或环境已经变了.文档越短,越容易保持有用.不管不顾地往里堆,迟早会**积灰**:过时的内容一层盖一层,因为往里加东西觉得安全,往外删东西觉得冒险.直到有一天,你想找条还有用的信息,得先把好几层灰扒开.
- **Token 计算**:模型用来表示自然语言文本的基本单位,也是计费单元,可以直观理解为「字」或「词」.通常 1 个中文词语,1 个英文单词,1 个数字或 1 个符号,计为 1 个 token.
  - 1 个英文字符 ≈ 0.3 个 token
  - 1 个中文字符 ≈ 0.6 个 token
  - 结论很明显:写给 agent 的文档,所有符号用英文小写.
- **逐句排查「废话指令」**:一条 LLM 默认就会遵守的指令,写了等于白写,还占篇幅.判断标准是「它相对默认行为有没有改变」,这看的是 LLM 而不是用户.两个人要是对某条是不是废话指令有分歧,那就是他们对默认行为有分歧.判断办法只有一个:假想把这句删掉,Agent 干的事有没有变化?如果没有变化,那么这一整句就是废话,那就整句删掉,而不是只删除某个词汇.这套标准也管引导词,如果一个词的效果还不如 Agent 的默认行为,那就是废话指令,而解决方案是换一个更有效的词来表达,比如「死磕到底」而不是换个手法.

写完用 Skill 工具加载 `express-check` 做验收.
