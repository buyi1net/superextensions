写任何给 AI 读的文档，写法都是相通的。不管是 skill、`AGENTS.md`、`CLAUDE.md`，还是通过指针指向的文档，用的都是同一套写法。AI 每次执行的是同一套流程，不是照搬固定的输出。所以只要把结构做对，无论哪种载体，行为都可预测。

但写 skill 有额外的机制：frontmatter 怎么填、调用方式怎么选、路由 skill 怎么用。这些在 [`SKILL-MECHANICS.md`](./modules/skill-mechanics.md/) 里单独讲。

> **语言基调**：给 Agent 的文档以无歧义为先，原创写作不加载 `express-translate`；翻译外文 skill 时两个都加载，那边管语言转换，这边管文档形态。

## 上下文指针

**上下文指针**说白了就是:你在 AI 的上下文里写一句话,提一下某个东西的名字,同时告诉 AI 什么时候该去翻它。skill 的 `description` 就是这种指针,`AGENTS.md` 里提到某份文档的那一行也是。关键不是材料本身有多重要，而是**你写的这句话准不准**：AI 什么时候该看、看了顶不顶用，全看你怎么写。

如果一份文档很重要，但你写在前面那句"引子"没写对，AI 就可能该翻的时候不翻，不该翻的时候瞎翻。所以先把这句话改准，实在改不清楚，再把文档内容直接写进去（别用链接了）。

一个指针就干两件事：

1. 说清楚"这是什么"。
2. 列出**什么情况**下该去看它（比如用户说 A 就看这一段，用户说 B 就看那一段）。

指针指向文件或资源时带可访问的链接：仓库内用相对路径，外部用完整 URL，不用反引号代替链接。

指针会一直占着 AI 的上下文，每轮对话都要花 Token ，所以比正文更需要使劲删。

至于怎么删？

- **最重要的话放最前面**：AI 第一眼看到的就是触发条件。
- **一个场景只写一条**：如果两个词是一个意思（比如"退款"和"退钱"），就合并成一条，别重复。
- **正文里已经说过的身份信息，指针里别再写一遍**（比如你正文已经是《退款流程指南》了，指针里就不用再写"这是退款流程"）。

## 两种开销

每加一份文档或一条指针，都会消耗以下两种预算：

- **上下文开销**：指始终加载在 Agent 上下文窗口中的材料所消耗的资源。例如 `AGENTS.md` 中的一行、skill 的 `description`，无论当前轮次是否触发，都占用上下文窗口、消耗 Token 和注意力。

- **认知开销**：指人脑子里记得"有哪些文档、什么情况该看哪份"这件事消耗的精力。人是索引，这种开销不用拼命往低压，它是"人还在做判断"的代价。花在该花的地方，没必要的地方就省掉。

通过指针去翻的材料，只消耗指针那一行的 Token 和注意力；没指针的材料，全部由认知开销扛着。

## 信息层级

一份文档就两种内容：**步骤**和**参考资料**。步骤就是 Agent 按顺序干的事，参考资料就是定义、规则、事实这些，用到再查。两种可以自由混用，全是步骤、全是参考资料或者两个都有也是可以的。

核心问题就一个，每块内容放在哪一层：

1. **步骤写在主文件里**：最优先，Agent 该干什么直接写清楚。
2. **参考资料写在主文件里**：用到再翻就行。经常是一堆平级的内容，每条都一样重要，这样安排也完全没问题。
3. **参考资料外置**：单独放一个文件，用指针挂着，触发了才加载。可以在同文件夹，也可以放别处，谁想指都可以。

难就难在拿捏分寸：压下去的东西太少，主文件就会臃肿；压下去太多，Agent 真要用的东西反而找不着。

**渐进式披露**就是往下沉，把内容挪出主文件、放到指针后面，也就是单独挪到一个文件里，主文件只留一行话指过去，让主文件继续保持清爽。这主要不是为了省 Token，而是为了保住层级结构本身。至于怎么判断该不该下沉？那就看**分支**。所有分支都用的，就写主文件里；只有部分分支才用得上，就放指针后面。尤其是带步骤的文档，该外置的参考资料如果混在主文件里，会把步骤埋了，Agent 看没看到全凭运气，这不只是清不清晰的问题，更是个"不确定性杠杆"：分支越多，混在一起的变数就越大。

**同地放置**是主文件里的配套原则：层级决定一块内容往下放多远，同地放置决定它到了那里之后跟什么放一起。一个概念的解释、规则、注意事项，尽量收在同一个标题下，别东一句西一句。这样读到其中一块，旁边的自然就带出来了。检验标准也很简单：这文档读起来像不像专门给 Agent 写的说明书？归好类的读着就像，到处乱放的就不像。(这不同于重复，重复是一个意思写两遍，分散是一个意思拆碎在各处)

**膨胀**是最容易踩的坑：文档太长，哪怕句句有用、句句不重复，也会把上下文撑得太长，模型的注意力被稀释。每多一行，就多一行要管。解法还是层级那套：参考资料往指针后面塞，按分支或流程拆开，每条路径只带自己需要的东西。

## 步骤与完成标准

每一步都有一个**完成标准**：也就是告诉 Agent"这事干完了"的条件，这个标准有两个关键点：

- **清晰度**：Agent 能不能分清楚"做完了"和"没做完"？如果标准很模糊，比如"理解了就行"，Agent 就容易**提前收工**，步骤还没真正干完，注意力就已经跑到了"完事了"上头去了。后面还有步骤等着，会推着 Agent 往前走；完成标准就是挡在面前的一道闸门，闸门没开，它就没办法走到下一步。这道闸门的标准越清楚，Agent 就越不容易蒙混过关。至于怎么修？**先改标准本身**，成本低、见效快。如果实在模糊到改不清楚，而且你确实观察到了 Agent 抢跑的现象，那就把后面的步骤拆出去藏起来。但藏起来只有跨过真正的上下文边界才管用，比如交接给人，或者派个子 Agent 去干。如果只是在主流程里直接调用，后面的步骤还在上下文中，等于没藏。
- **要求高低**：标准定得多重，决定了 Agent 要下多大力气。比如"每一个用户反馈都回复了"，就可以让 Agent 必须逐条处理；而"列个改动清单"就没那么使劲。要求高的标准会逼着 Agent 下**笨功夫**，干活过程中自己翻查、核实。这些工作量都藏在措辞里，不用单独写成一步。而且要求不局限在单一步骤里。"每一条规则都用到"绑的是一整份参考资料，就像"每一步都做完"绑的是一整串步骤。这就是为什么全篇都是参考资料的文档，仍然能有一个"必须做彻底"的硬杠杠。

最强的完成标准，既是**能检查的**（做完没做完一看便知），又是**全覆盖的**（没有漏网之鱼）。

## 什么时候拆分

把一个文档拆成两个，本质是在"上下文开销"和"认知开销"之间做取舍。**只在拆分带来的收益大于成本时，才值得动手。**

两种常见的拆分方式：

- **按流程拆**：如果后面的步骤会诱使 Agent 急着做完当前这一步，就把后面的步骤拆出去、藏起来。看不见后面的步骤，Agent 才会老老实实把手头的活干透。反过来也要小心：如果把拆开的流程合回去，每一步都能看到后面的步骤，就会诱导 Agent 提前收工。
- **按调用方式拆**：skill 专用，详见 [`SKILL-MECHANICS.md`](./modules/skill-mechanics.md/)。

## 引导词

**引导词**就是一个现成的、模型预训练里已经有的概念（比如 `lesson`、`fog of war`、`tracer bullets`），Agent 跑文档的时候拿它来想问题。用这个词的时候，重复出现的只是这个词本身，不用每次都解释一遍。它每出现一次，就在 Agent 脑子里把"这个词指什么"的边界再画清楚一点；同时它借用了模型本来就有的知识，花最少的 token 锚定一整块行为。自己造词如果定义清晰也能用，但造出来的词调用不了先验知识：你在定义上花的 token 比预训练词白送的要贵；优先用已有的词。

引导词管两个地方。在正文里，它管**执行**：这词每次出现，Agent 都会调用同样的行为；放在平铺的参考资料里，它把注意力集中到某类东西上，让 Agent 知道该找什么。在指针里，它管**触发**：同一个词如果同时出现在你的提示词、文档和代码库里，Agent 就会把这种共享语言和那份材料关联起来，翻材料也更稳、更准。

找机会用引导词来重构。同一个意思反复解释了好几遍、一个指针写了一整句话才说清楚，这些都可以被压缩成一个词：

- "又快又准，还不费什么资源" → 可以用 **tight**（一个 _tight_ 循环）
- "一个你信得过的循环" → 可以用 **红**（把模糊的门槛变成一个能看得见的状态，bug 出现时循环变"红"，否则就不变）

这样可以一箭双雕：token 花得少了，又可以让 Agent 的想法不跑偏。你可以假设每份文档里都有很多可以用引导词替换的重复表述，找出来，收掉。

**反过来，否定式表达是引导词旁边最容易翻的车。** 用"禁止"来引导，等于把禁止的行为拽到上下文里，让它**更容易**被触发，而不是更难。"别想大象"，结果满脑子都是大象，"别"这个否定词太弱了，压不住已经被激活的核心概念，所以"不许做 X"在 Agent 那里差不多等于"做 X"。要写就写**正面的**：把目标行为说出来（比如"写一行注释"），被禁的那个连提都别提。只有实在没法正面写的硬护栏，才用否定式；就算用，也得同时把正面的目标写出来，让注意力落在"该做什么"上。

## 精简

- **每个意思只放一处**，一处改了，全盘都改。重复（同一个意思在多个地方出现）既费维护又耗 token，还会把一个意思在信息层级上的权重抬到它不该有的位置。这和引导词正好相反，引导词是刻意重复同一个词，但从来不重复含义。
- **环境本身就是个可靠的信息源**（比如 `package.json` 里的脚本、配置文件、目录结构、`--help` 的输出）。文档里把环境里的东西抄一遍，本质上是**缓存**，把查一下就有答案的东西复制了一份。只有当场查起来成本很高的时候，才值得写进文档。应该写进文档的是 Agent 自己查不到的东西：没写下来的惯例、某个决定背后的原因、配置文件里看不出来的坑。至于那种"一个文件、一条命令"就能查到的东西，让 Agent 自己去环境里查就行。
- **每一行都要检查一下还有没有用**。有用 = 对当前文档要干的事还有帮助。没用的分两种：一种是从来就没帮上忙（比如纯解释性的废话、或者本来该外置的分支）；另一种是以前有用，但现在它描述的行为或环境已经变了。文档越短，越容易保持有用。如果不管不顾地往里堆东西，迟早会**积灰**，过时的内容一层盖一层，因为往里加东西会觉得安全，往外删东西会觉得冒险。直到有一天，你想找条还有用的信息，得先把好几层灰扒开。
- **逐句排查，专治"废话指令"**。模型默认就会做的事，你写成指令也白写，白占上下文，不改变任何行为。怎么判断是不是废话指令？就一句话：加了这句，跟没加这句，模型干的事一样不一样？如果一样，整句删掉，别只删几个字。这个判断标准是跟着模型走的，不是跟着人走的。两个人对“某句是不是废话”有分歧，其实争的不是这句话本身，争的是“模型默认会怎么干”。别吵，跑一遍文档看结果。这个标准也适用于引导词。比如模型本来就已经挺认真了，你还写“要认真”，这就是废话。解决方案不是换一种写法，是换个更狠的词，比如“死磕”。

写完后用 skill 工具加载 `express-check` 做验收。
