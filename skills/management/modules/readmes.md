# README 治理

> 本文件是 `README.md` 的通用骨架与治理规则，覆盖项目内各级目录的 `README.md`。使用方式与场景底稿一致：文件复制对应形态的骨架，再按当前目录的实际内容精准修改；保留章节结构，替换占位内容，删除不适用的章节说明。
>
> 占位内容用 `<尖括号>` 标出，必须全部替换；没有对应内容时删除整行，不得留下占位符或不存在的链接。

## 形态判定

写 `README.md` 前依次回答六个问题，答案确定形态：

1. **读者是谁？** 项目维护者/接手者，还是外部用户？
2. **位置在哪？** 项目根、一级子目录、交付目录，还是对外公开的仓库？
3. **仓库是私有还是公开？** 同样是仓库根：私有研发仓的根 `README.md`按项目根 `README.md`写（服务维护者）；公开仓的根按对外仓库形态写（服务陌生访客，属交付场景，骨架见 [交付目录治理](./delivery.md)）；
4. **给人看还是给 agent 看？** `README.md`给人；agent 规则在 `AGENTS.md`，`README.md`只留提醒入口；
5. **能否引用项目内部路径？** 给项目外读者的 `README.md`必须自包含；
6. **单语言还是多语言？** 语言跟随项目主生态，不跟随当前对话语言。

## 常用形态

**项目根目录：**
**位置：**当前项目的根目录
**读者：**维护者 + 接手者
**要点：**项目介绍 + 快速开始 + 根目录清点（双重身份：项目介绍 + 根目录索引）

**项目子目录：**
**位置：**项目一级目录
**读者：**项目维护者
**要点：**分类表 + 索引，让人一眼掌握目录现状

**交付目录：**
**位置：**存放最终交付物的目录
**读者：**维护者（仓内）/ 用户（包内）
**要点：**仓内记交付清单与重建方式；包内自包含

**对外仓库：**
**位置：**对外公开的仓库根（GitHub 等）
**读者：**外部访客
**要点：**第一屏决定别人要不要用：价值主张、演示、License（骨架在 [交付目录治理](./delivery.md)）
**注意：**对外仓库与项目根 `README.md`的分界：私有研发仓库的根说明文件按「项目根目录」写，公开仓的根才按本形态写

**形态外还有两个不构成独立形态的属性：**

1. **字段变体**：同为子目录 `README.md`，不同目录的索引字段不同（见①内说明）；temp 记清理责任、archive 记恢复条件，骨架不变、字段不同；
2. **公开子目录**：monorepo 子产品目录对外公开时，按项目根 `README.md`骨架写但换外部读者视角；低频，实战撞见再升级为独立形态。

**形态判定不了的 Novel 情形：**

1. 按五问往最近形态靠，并在 `README.md` 开头用一句话注明当前定位与读者。
2. 确实放不进任何形态时，停下来问用户，不得自创无边界新形态。

## 维护原则

**通用规范：**

1. 只写当前实际存在的内容，不预写计划中的分类、条目或完成状态；已消失的内容不得继续写成当前状态，分类、条目、状态变化后立即更新本文件；内容新增、移除或职责变更时，同一次提交里同步更新所有登记它的 README 索引和清单（含对外发布仓的说明文件）。
2. 写结构，不写快照：不写测试数量、提交数、进度百分比这类很快过期的信息；项目阶段、进展、发布记录属于 docs/ 的内容，R `README.md`最多链接过去，不在正文维护。
3.  `README.md` 面向人类导航：不写 Agent 操作步骤、工作记录、日志；Agent 规则在 `AGENTS.md`， `README.md` 只留提醒入口；对 Agent 而言  `README.md` 中的链接是按需导航不是必读清单，禁止无差别读取。
4. 每个  `README.md` 开头附近固定携带 Agent 提醒行：本文件为用户导航，请按需选读，禁止无差别读取，浪费上下文，如需修改，先读 `AGENTS.md`；全部形态统一，不省略。

**语言规范：**

1. 语言跟随项目的主要使用场景和工具链：上 GitHub 或英文工具链项目用英文，本地中文业务项目用简体中文；同一项目内保持一致；对外项目面向国际受众时英文优先。
2. 统一使用大写 `README.md`：GitHub 会把小写 `readme.md` 也渲染成首页，Windows 不分大小写会撞名，统一大写避免歧义。
3. 双语言或多语言  `README.md` 用主文件+链接（如 `README.zh-CN.md`）或语言切换行，不在同一文件里机械对照翻译。

**链接规范：**

1. 链接必须真实且同步维护：目标存在才链接；目标被移动、重命名或删除后，同一次提交里更新或清理指向它的链接，不得留到下次；没有本地副本写「未获取」或「无」，不造死链。
2. 链接路径规范：项目内一律用相对路径（如 `./docs/架构.md`），目录链接末尾加 `/`（写 `./docs/` 不写 `./docs`，部分显示 Markdown 的工具对无斜杠目录链接处理不稳定）；禁止盘符绝对路径（`C:\...`）、`file://` 前缀和 `../` 跳出项目根的路径；外部资源用完整 URL（`https://...`）。
3. 链接文字要有辨识度：写「见 [架构设计]（路径 ./docs/架构.md）」这种带名字的链接，不写「点这里」；链接显示文字本身就是导航信息；链接目标含中文时直接写中文路径，不做百分号编码（编码由显示工具处理，人写易错）；页内跳转（`#xxx`）只用于同一文件内部，中文标题的跳转标记在不同工具里规则不一，跨文件容易断；不链接到 temp/ 等临时内容——临时区随时会清，索引指向它就是制造死链。

## 项目根目录

```md
# <项目名>

<一段话：是什么、给谁用、解决什么问题。>

## 快速开始

<环境要求、安装、构建、运行、测试的命令块；细节链接到 docs/ 对应文档。>

## 目录结构

| 目录 | 职责 |
|---|---|
| [<目录名>](./<目录名>/) | <一句话职责> |

## 从哪开始读

<docs/ 中的阅读起点，3-5 篇，按接手者的问题组织；docs 刚建立时删掉本节。>

- 想跑起来 → [快速开始详情](./docs/<文件>)
- 想懂结构 → [架构说明](./docs/<文件>)
- 想知道为什么这样设计 → [关键决策](./docs/<文件>)

## 维护

Agent 工作规则见 [AGENTS.md](./AGENTS.md)。
```

## 项目子目录

```md
# <目录名>

<一两句话：这个目录放什么、边界在哪。>

## 当前分类

| 分类 | 用途 |
|---|---|
| [<分类目录名>](./<分类目录名>/) | <这个分类放什么> |

<没有分类时写：当前没有分类内容；新分类在实际内容产生时建立并更新本表。>

## <分类名>索引

<索引条目的字段由该目录自己的场景规范或项目实际确定，本骨架只定格式：>

<字段 ≤2 个时可用表格；≥3 个字段一律用行式。>

<分类名>/<条目名>：

**<字段一>：** <值>
**<字段二>：** <值>
**<字段三>：** <值>
**<字段四>：** <值>

<本段仅定格式，场景规范对字段或格式另有约定时，按照对应场景规范执行。>

## 约定

- <本目录特有的维护约定，一两行；没有就删掉本节。>
```

## 对外仓库

常规的项目目录，大概率会包含太多研发测的东西，不利于开源共享，所以在GitHub发布环节，一般会分为研发仓库和公开仓库(开源仓库)：

1. 研发仓库：`README.md` 文件按照项目根目录的 `README.md` 文件执行即可。
2. 开源仓库：骨架与规则见 [交付目录治理](./delivery.md)。
