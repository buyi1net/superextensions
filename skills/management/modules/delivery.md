> 把项目已经验证、准备对外交付的最终产物集中存放在 `delivery/` 一级目录，让用户和 Agent 能从一个入口知道有哪些交付物、什么版本、怎么验证、怎么重建。交付物经暂存验证后正式收入本目录（下称「转正」），并持续维护。

仅在首次建立交付场景、现有交付治理存在具体缺口，或用户明确要求整理、迁移和审计时使用本规范。已经能够自治的交付目录日常转正、更新和移出旧版本直接执行项目内规则，不用本规范反复对照。

## 为什么是 delivery/，不是 release/ 或 build/

- `build/`、`dist/`、`release/` 在各类构建工具里几乎都被用作「可再生的编译输出」（target/release、VS 的 Release/、npm 的 dist），大模型看到这些名字会条件反射地把编译产物丢进去；
- `delivery/` 没有被任何构建工具占用，语义直指「最终交付物」，模型没有第二联想；
- 交付目录是已验证、转正后的成果：删除或变更需要重新走验证流程，与可再生的构建产物生命周期相反。

## 收录边界

放入 `delivery/`：

- 已完成验证、确认可直接分发的最终交付物：版本目录、压缩包、安装包、插件包、镜像清单；
- 与交付物同源的校验文件（如 SHA256SUMS）；
- 交付目录自己的治理入口（`README.md`、`AGENTS.md`）。

不放入 `delivery/`：

- 构建暂存、待验证候选、半成品（放 `temp/` 构建暂存区，见「转正流程」）；
- 交付物的源材料和组装输入（发布说明素材、LICENSE 模板）——放 `docs/` 或项目专用材料目录；
- 运行实例、运行数据、日志；
- 同一份内容的多份重复副本：ZIP 与目录共存时必须同源同版本，校验文件统一管理。

## 目录结构与分层

`delivery/` 是唯一交付目录，永不因交付物增多而新建其他交付一级目录。层级判定：

1. **单一渠道**：交付物平铺 `delivery/产品名-版本/` + 同名压缩包 + 校验文件，不建渠道层；
2. **多渠道**：先按渠道建二级目录（如 `npm/`、`docker/`、`直发包/`），渠道内按版本组织；
3. 同版本同源的 ZIP 放在条目旁边，不入子目录，由统一校验文件覆盖；
4. 禁止三级：渠道/版本之外再按年份、日期、平台拆目录属于过度组织，需要区分时用文件名（如 `产品-版本-win-x64.zip`）；
5. 渠道再怎么新增（新包管理器、新镜像仓库），只加二级目录或渠道适配行，不动一级结构。

`delivery/` 不是开发项目根，也不是运行实例根；开发侧交付说明放在 `docs/`。

## 交付声明

构建前必须在 `README.md` 或交付说明中记录交付类型。可运行包与完整源码交接包的内容边界不同，必须在交付说明中写明面向对象和包含范围（是否包含完整源码、测试与开发脚本）。

每种最终交付物必须有对应的随包使用说明、更新日志和校验信息，并说明适用环境、入口、运行方式和验证命令。开发项目的构建、发布和重建方法写入 `docs/` 下的交付说明；交付目录内的说明只描述当前交付物，不复制开发项目根说明。

交付包内说明不得索引交付包中不存在的 `tests/`、`scripts/`、`temp/`、`delivery/` 或开发项目外部路径；不得把开发项目根当成交付包根。

## 转正流程

交付物从暂存区进入 `delivery/` 必须经过转正（验证通过、正式收入），顺序固定：

1. 在 `temp/` 的构建暂存区组装候选，生成文件清单；
2. 在解压副本或临时副本中完成运行和交付验证；验证后复查暂存候选与 `delivery/` 内交付物未被运行过程改变；复核清单；
3. 验证通过后，同一份清单整体转入 `delivery/`，同源生成压缩包与校验文件；
4. 立即更新 `delivery/README.md` 的当前交付物索引和交付记录。

转正后任何对交付物的修改、重建或替换都使先前验证失效，必须重新走 1-4。不得在 `delivery/` 内直接开发、修补或追加文件。运行数据库、日志、截图、缓存、锁、进程文件、上传文件和 `__pycache__` 等运行时生成物不得进入构建暂存区或初始交付包。

## 组装与验证细则

- 交付目录和 ZIP 同时存在时，二者必须来自同一份文件清单，逐文件一致；待打包目录、半成品和待验证目录留在构建暂存区，不得出现在 `delivery/`；
- 最终交付物应能根据同一份源码和构建脚本整体删除后重建，`delivery/` 不得保存开发侧唯一源文件；
- 启动交付副本或外部程序进行验证时，记录本次创建的准确进程、端口和临时位置，验证后只清理这些目标；不得用按程序名称结束全部进程的方式代替精确清理；
- 校验文件必须能在目标环境直接校验：注意行尾与路径格式兼容（Windows 下生成校验文件固定 LF，避免 sha256sum -c 把 `\r` 并入文件名报错）。

## 版本策略与不可变

- 交付物命名 `产品名-版本`；版本号变更即新条目，不覆盖旧条目；
- **已转正版本不可原地修改**：同版本号的任何内容变更都等于覆盖已分发物，外部可能已持有旧版本。修复、补丁、重新打包一律按新版本号重新转正；「改完还是同一版」属于违规；
- **同时保留策略**：默认只保留当前版本和上一个版本（回滚保险），更早版本转入交付记录或移出；项目有特殊需要（多版本并行支持、长期支持版）时由用户指定保留策略并写入 `README.md`；
- 版本号遵循项目既定规则（如语义化版本），不因渠道不同而各自发明。

## 撤回与灰度

- 发现已转正版本存在严重问题需要撤回时：交付记录中标记「已撤回 + 原因 + 日期」，实体移入交付记录归档或删除（删除属破坏性操作，先向用户确认），当前交付物索引不再列出；
- 撤回不等于从外部渠道抹除：已发布到 GitHub/插件市场的版本无法真正回收，撤回记录的是本项目不再背书该版本；外部渠道的下架、删除由用户决定；
- 灰度发布（部分渠道先发）时，`README.md` 交付记录中标注各渠道的发布状态；全部渠道就绪后补全记录，不重复转正。

## 依赖关系

交付物之间存在依赖（插件包依赖运行时、包 B 依赖包 A 某版本）时，在行式索引中增加可选字段：

`**依赖：** <被依赖交付物及版本，无则删本行>`

依赖变更随新版本转正同步声明；依赖的旧版本被移出前，确认没有目录内其他交付物仍然依赖它。

## 外部发布记录

推送到 GitHub、插件市场、镜像仓库后，交付记录中登记发布记录（远端 commit、Release 链接、镜像 tag），使本地交付物与外部发布可以互相核对：

`**渠道：** <GitHub Release 链接 / 市场版本页 / 镜像 tag>`

本地移出旧版本不影响外部已发布版本；外部出现了本地没有登记的版本，说明两边不一致，发现时先补登记，再查原因。

## 更新日志正本

`CHANGELOG` 正本在开发仓维护（`docs/` 或项目指定的材料目录），构建时从正本带入交付包；交付包内的 `CHANGELOG` 是快照，不在包内独立编辑。多渠道发布共用同一份正本，渠道差异写渠道适配表。

## 移出旧版本

- 按「当前 + 上一版」默认策略例行移出的旧版本：转入交付记录即可，无需额外确认；
- 超出默认策略的移出、或外部流程仍依赖旧版本时：先确认没有被外部流程依赖、没有目录内其他交付物依赖它，再移出；删除实体属破坏性操作，先向用户确认；
- 校验文件随转正与移出整体重建，覆盖当前全部交付物，不留过期条目；行尾与路径兼容要求见「组装与验证细则」。

## 交付目录 `README.md`

仓内交付目录、交付包内 `README.md`、公开仓根 `README.md` 三种骨架见下；字段与分层规则同章。

### 仓内交付目录骨架

```md
# <目录名>

<一两句话：本目录存放已验证的最终交付物；暂存和半成品在 temp/，不进本目录。>

> Agent 注意：本文件为用户导航，请按需选读，禁止无差别读取，浪费上下文，如需修改，先读 [AGENTS.md](./AGENTS.md)。

## 当前交付物

<交付物名> <版本>：

**形态：** <目录 / ZIP / 安装包 / 镜像>
**内容：** <一句话：包里有什么、面向谁>
**校验：** <SHA256 或校验文件路径>
**验证：** <怎么确认它可用：命令或步骤链接>
**重建：** <从哪个脚本或流程重建>
**依赖：** <可选：被依赖交付物及版本；无则删本行>
**渠道：** <可选：外部发布地址（Release 链接/镜像 tag）；未发布删本行>
**日期：** <转正为最终交付物的日期>

## 交付记录

<可选：历史版本、撤回与灰度状态；只有当前版本时删掉本节。>
```

### 交付包内 `README.md` 骨架

读者是拿到包的最终用户，没有项目上下文，一切信息自包含：不得复制项目根 `README.md`，不得引用包内不存在的目录或项目内部路径。

```md
# <产品名> <版本>

<一两句话：这是什么、给谁用。>

## 安装

<按渠道适配表写；命令块为主。>

## 运行

<怎么启动，最小示例。>

## 配置

<可选：配置文件说明；没有就删节。>

## 求助

<问题反馈渠道；内部版写支持边界与授权范围。>

## License

<开源版写许可证；内部版写版权与使用限制。>
```

### 对外仓库骨架（公开仓根 `README.md`）

公开仓库根本身的 `README.md`，是外部访客看到的第一屏，决定别人要不要继续了解这个项目。与项目根 `README.md` 的判定分界在仓库属性：私有研发仓的根按项目根形态写（服务接手者，怎么跑起来）；公开仓的根按本骨架写（服务陌生访客，值不值得看、能不能信任）。

```md
# <项目名>

<一两句话：是什么、解决什么问题；一句话说清与众不同之处。>

<徽章/版本/平台支持等一行式信号，可选。>

<演示图或 GIF，可选但有图远胜千言。>

## 功能

- <面向用户价值的功能点，不是实现细节>

## 安装

<最短可用路径；按渠道适配表写；详细文档链接。>

## 使用

<最小示例或入口。>

## 文档与社区

[完整文档](<链接>) · [报告问题](<链接>)

## License
<许可证与一句话声明。>
```

要点：

- 第一屏（标题+首段+配图）必须独立成立——多数人只看这一屏；
- 开源项目面向国际时英文优先，可附中文版链接；内部项目面向内部用户时中文；
- 贡献指南可链接独立 `CONTRIBUTING.md`，不在首页 `README.md` 里展开；
- 公开仓与研发仓同根时合并：项目根章节在前，对外要素（配图、徽章、License）融入，不维护两份 `README.md`；双仓模式下两仓各按各的写，不互相复制（见公开仓渠道条款）。

### 渠道适配表

发布渠道只影响包内 `README.md` 的安装节和特有要求，不产生新形态；新渠道出现时加一行。

| 渠道 | 安装节写什么 | 特有要求 |
|---|---|---|
| 压缩包直发 | 解压路径、运行入口 | 附校验值；内部授权说明 |
| 公开仓·闭源 | Release 下载链接 | License 写所有权保留类声明；禁止逆向等条款 |
| 公开仓·开源 | Release 下载或 clone 构建 | 开源 License + 贡献方式 |
| 源码交接包（任意渠道） | 同渠道要求 | 白名单发布：只含接收者获得完整功能、能正常编译所需的内容；非必需部分（治理文件、内部脚本、任务记录、参考材料等）一律不进。研发仓的 `AGENTS.md`、`CLAUDE.md` 属非必需，不随源码交付；公开仓需要 `AGENTS.md` 服务 GitHub 自动化（自动处理 PR、issue）时，按 [public-agents.md](./templates/public-agents.md) 标准底稿单独写一份面向贡献者与自动化 bot 的操作规则（代码标准、验证命令、提交格式、PR/issue 处理纪律），不复用研发仓版本；设贡献门槛时配套 [public-contributing.md](./templates/public-contributing.md) 底稿建 `CONTRIBUTING.md`，两者互相引用，小项目或不设门槛时不建 |
| 包管理器/插件市场 | 一条安装命令 | 清单文件（package.json / plugin.json 等）与 `README.md` 版本同步 |
| 容器镜像 | pull 命令 + 挂载卷 + 环境变量 | 镜像地址与标签策略 |
| 在线服务 | 访问 URL + 浏览器/客户端要求 | 部署说明单独面向运维，不混入用户 `README.md` |

### 公开仓渠道条款（双仓模式）

项目以「私有研发仓 + 公开仓」双仓模式分发时（研发仓维护源稿，公开仓对外发布），公开仓就是交付渠道本身，规则：

1. **单向发布**：公开仓内容只能从本地交付目录经发布流程推送，不得在公开仓直接编辑内容再倒灌回研发仓；发布只能经项目确定的构建入口执行，禁止手工拼装上传；
2. **内容核对**：推送后重新克隆公开仓并核对整体摘要（digest），远端与本地交付树逐文件一致才算发布完成；摘要不一致立即停止发布并报告；
3. **不承担备份**：公开仓内容随时可从本地交付目录整体重建；研发仓的版本管理与备份职责不经过公开仓，两条线不交叉；
4. **两仓 `README.md` 各司其职**：研发仓根按项目根 `README.md` 形态写（面向接手者），公开仓根按对外仓库形态写（面向访客/用户），不互相复制；公开仓 `README.md` 的安装节按本渠道适配表写；
5. **版本发布记录**：正式发布打版本标签（原子推送同时更新分支与标签），发布信息登记进交付记录（见「外部发布记录」）。

项目内已有成熟发布脚本的（如发布 skill），本条款只约束行为边界，不复述脚本用法。

## `AGENTS.md`

`delivery/` 的 `AGENTS.md` 是该目录的直接维护入口，沿用项目内已有结构；当前场景没有经过实战验证的标准底稿，首次建立时按 [Agent 入口治理](./agent-entry.md) 的通用骨架创建，只写交付目录特有的边界与转正红线。将来本场景在实战中稳定后，由用户拍板固化为标准底稿。

## 验收

1. `delivery/` 内只有已验证转正的最终交付物、同源校验文件和治理入口，没有暂存、半成品、源材料或运行数据；
2. 每个交付物可从明确的构建入口整体重建，`README.md` 索引与磁盘一致，校验文件覆盖当前全部交付物；
3. 同版本目录与压缩包同源；渠道与版本分层符合分层规则，没有三级目录；
4. 转正顺序（暂存组装 → 副本验证 → 整体收入 → 更新索引）有操作记录可查，不是事后补齐；
5. 目录内任何变更后 `README.md` 已同步更新；移出与删除记录可追溯，删除经过用户确认；
6. 交付物可整体重建，交付区没有开发侧唯一源文件；运行验证产生的进程、端口和临时资源按准确目标清理，没有影响本任务之外的同名程序或用户环境；
7. 没有对已转正版本的原地修改；修复走新版本号，保留策略符合「当前 + 上一版」或用户指定策略；
8. 依赖声明完整：目录内交付物依赖的旧版本没有被移出；撤回与灰度状态在交付记录中可查；外部发布记录已登记，本地与外部没有未核对的版本差异。
