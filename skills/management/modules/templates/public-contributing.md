# 贡献指南

本指南的存在是为了给双方节省时间。

## 理念

<本项目的核心理念，一到三段：项目接受什么样的方向、拒绝什么样的方向。跟着项目实际情况写，没有硬性要求。示例（来自源仓）：核心保持最小，不属于核心的功能应该做成扩展，让核心膨胀的 PR 大概率被拒绝；即便是对扩展的钩子点也应经过充分考量和讨论，避免加入无法维护的膨胀和复杂交互。没有可写的理念时删除本节。>

## 唯一规则

**你必须理解你的代码。** 如果你解释不了你的改动做了什么、和系统其余部分如何交互，你的 PR 会被关闭。

用 AI 写代码没问题。提交自己都不理解的 AI 生成物不行。

如果你使用 agent，从 <仓库根目录> 运行它，这样它会自动读取 `AGENTS.md`。你的 agent 必须遵守该文件中的规则和指引。

## 贡献门槛

<新贡献者的 issue 和 PR 默认自动关闭。维护者每天审查被自动关闭的 issue，并重新打开有价值的。不达到下方质量标准的 issue 不会被重开或回复。>

通过维护者在 issue 上的回复完成批准：

- `<lgtmi>`：你今后的 issue 不再被自动关闭；
- `<lgtm>`：你今后的 issue 和 PR 都不再被自动关闭。

命令必须写在回复的开头（前面可以有一个或多个 `@用户名` 提及）或结尾。`<lgtmi>` 不授予提交 PR 的权利，只有 `<lgtm>` 授予。

<紧急问题的求助渠道，如 Discord/讨论区链接。>

## issue 的质量标准

打开 issue 时，<必须使用两套 GitHub issue 模板之一，如仓库未设模板则删除本句>。

issue 要短、具体、值得读：

- 保持简短；一屏放不下的太长了；
- 用自己的话写（不要用 LLM 生成文本；如果必须用，跟一条明确标注 AI 的评论）；
- 清楚陈述 bug 或请求；
- 解释它为什么重要；
- 如果你想自己实现这个改动，说出来。

issue 属实且写得好，维护者可能重开它，或在上述命令位置回复 `<lgtmi>` 或 `<lgtm>`。

## 封禁

如果你两次无视本文档，或用 agent 生成的 issue 刷屏，你的 GitHub 账号会被永久封禁。

如果你通过自动化大量发送 issue，你的 GitHub 账号会被永久封禁。没有商量。

## FAQ

### 为什么新 issue 和 PR 会被自动关闭？

<项目收到的 issue 超过维护者能实时负责任审查的量。很多报告达不到本指南的质量标准或不遵守 CONTRIBUTING.md，有些是未经人审查和打磨、由 agent 盲目甩给仓库的。自动关闭制造了缓冲，维护者可以按自己的节奏审查，重开达到质量标准的 issue。>

### 为什么 <低优先级时段，如周末> 的 issue 优先级低？

<维护者在工作时间分拣；<低优先级时段> 积累的 issue 可能在 <下一批次审查> 中被遗漏或排后。紧急问题走 <求助渠道>，附短描述、复现步骤和相关日志。>

### 为什么有些 issue 得不到回复？

回复也是维护工作。低信息量、不清晰、重复、不遵守本指南的 issue 可能不经讨论直接关闭。这为可复现的 bug、深思熟虑的请求和把报告做到可执行的贡献者保留了时间。

### 为什么不让 AI 分拣一切？

AI 可以帮助归类重复、总结报告、发现缺失信息，但不被信任做最终的维护者决策。打磨过的 AI 生成 issue 仍可能错误、误导或调查成本高昂。人类审查仍是最终关卡。

### 这对贡献者不友好吗？

不。这是对抗倦怠和 tracker 刷屏的护栏。短、具体、可复现的 issue 受欢迎；深思熟虑的贡献受欢迎。自动化垃圾、理所当然感和大量低努力报告不受欢迎。
