# 开发规则

> 本模板是公开仓库根目录 `AGENTS.md` 的标准底稿，面向贡献者与自动化 bot（自动处理 PR、issue）。使用方式：文件复制本模板，删除不适用的章节和条目，把尖括号占位替换为项目实际内容。来源：earendil-works/pi 的 AGENTS.md（社区验证的开源仓标杆）。

## 交流风格

- 回答简短直接；
- commit、issue、PR 评论和代码中不使用 emoji；
- 不写客套和填充文字（写「谢谢 @用户」不写「太感谢啦 @用户！」）；
- 只写技术内容，直接了当；
- 用简洁、清晰、简单的语言；无法避免的术语先定义再使用；
- 解释非平凡的设计和问题时按「问题 → 具体示例或简短追踪 → 方案」组织；说明方案为什么必要，区分必要复杂度和可选复杂度；
- 用具体行为和小示例代替抽象总结、密集术语和无解释的变更清单；
- 用户提问时，先回答问题，再做修改或执行实现命令；
- 回应反馈或分析时，先明确说同意还是不同意，再说改了什么。

## Git 纪律

<本仓可能有多个 agent 会话同时工作，各自修改不同文件。触碰自己改动之外的未暂存、已暂存或未跟踪文件，会破坏其他会话的工作。>

提交：

- 只提交本次会话中你自己改过的文件；
- 显式暂存路径（`git add <路径1> <路径2>`）；禁止 `git add -A` / `git add .`；
- 提交前运行 `git status`，确认只暂存了自己的文件；
- <允许随自己文件一起提交的特殊路径，如生成文件>；
- 提交信息格式：`{feat,fix,docs}<(范围)>: <信息>`（可多行）；信息有内容、简洁。

禁止运行（会破坏其他 agent 的工作或绕过检查）：

- `git reset --hard`、`git checkout .`、`git clean -fd`、`git stash`、`git add -A`、`git add .`、`git commit --no-verify`。

rebase 冲突：

- 只解决自己修改过的文件中的冲突；
- 冲突在自己没改过的文件里时，中止并询问用户；
- 禁止 force push。

## Issue 与 PR

<贡献者门槛与质量标准见 CONTRIBUTING.md（落地时替换为真实链接；其底稿为 [public-contributing.md](./public-contributing.md)，与本文配套）；项目不设贡献门槛时删除本行。>

审查 PR：

- 未经用户明确要求，不运行 `gh pr checkout`、`git switch`，不把工作树切到 PR 分支；
- 用 `gh pr view`、`gh pr diff`、`gh api`、本地 `git show`/`git diff` 查看PR 元数据、提交和补丁，不切换分支；
- 需要 PR 文件内容时，取到临时文件读取或用 `git show <ref>:<path>`，不切换分支。

创建 issue：

- <按受影响包加标签的规则，如 `pkg:模块名`，可多选>。

发 issue/PR 评论：

- 评论写到临时文件，用 `gh issue/pr comment --body-file` 发表（不用 `--body` 传多行内容）；
- 评论简洁、技术性，符合仓库语气；
- 每条 AI 发布的评论末尾带 AI 生成声明行（按发起提示词中的指定措辞）。

通过 commit 关闭 issue：

- 提交信息中包含 `fixes #<编号>` 或 `closes #<编号>`，合并时自动关闭；多个 issue 逐个写关键字（`closes #1, closes #2`）；共用一个关键字（`closes #1, #2`）只会关闭第一个。

位置：`<CHANGELOG 文件位置，如各包各一份>`。
