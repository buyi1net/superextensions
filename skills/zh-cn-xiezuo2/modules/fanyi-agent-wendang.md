# Agent 与规则文档翻译

> 本模块只补 Agent 可执行规则文档相对于主框架和译中制度新增的约束。它只能由译中模块在确认文本会影响 Agent 行为时加载，不反向要求重读上游文件。

## 先确定产物用途

动笔前确定本次产出：

1. **可执行译本**：中文文件会直接交给 Agent 执行；
2. **中文导读**：只供人理解和吸收，不代替原文件执行；
3. **双轨输出**：可执行译本和中文导读分别成文。

用户没有说明、现有文件也无法判断时先确认，不得自行选择。

### 可执行译本

可执行译本以行为不变为首要标准：

- 不增加原文没有的规则、建议、解释或适用场景；
- 不删除概念、因果关系、例外和强调力度；
- 不添加“本文是译文”等翻译说明；
- 不把面向人的理解辅助内容塞进执行文件；
- 不改变 frontmatter 字段名、配置键和调用机制；
- 不扩大或缩小 `description` 的触发范围；
- 不改变步骤顺序、分支、停止条件和完成标准；
- 不改变 skill 之间谁能调用谁；
- 不把参考规则误写成执行步骤，也不把执行步骤弱化成背景说明。

### 中文导读与双轨输出

中文导读可以重组讲解顺序、增加中文例子、解释概念关系并分析如何应用，但必须与可执行译本分开。导读不保留会让 Agent 把它识别为正式 skill 的 frontmatter，也不得伪装成行为等价译本。

同时需要执行和理解时分别产出一份行为等价的可执行译本和一份面向中文读者的导读，不能让一份文件同时承担两种职责。

## Agent 文档分析

完整阅读源文件及其强制引用后，额外分析：

1. 文件由人阅读还是由 Agent 执行；
2. 哪些内容决定调用时机和实际行为；
3. 哪些短词是作者故意反复使用的关键词；
4. 哪些内容是说明，哪些是硬性边界；
5. 哪些路径、配置和 skill 调用关系必须保持；
6. 哪些英文概念没有自然、通行的中文译法。

## 术语与关键词

代码标识、配置键、命令、路径、API、环境变量、产品名和版本号保持原样。已有稳定译法的使用稳定译法；没有稳定译法但普通中文能直接说明的，不另造专名。

原文故意建立的核心概念，首次按“中文（English）”标注；原词承担行为引导时不得只留下中文，后文根据实际作用决定继续保留英文还是使用中文名称。

`prompt` 指交给模型的整段提示词，`system prompt` 指系统提示词。`leading word` 是提示词里的关键词：模型在预训练中已理解、能用很少 token 唤起一整套行为的短词或短语，例如 `red`、`relentless`、`fog of war`。翻译时不能只为中文整洁而删除这类词，也不要另造需要再次解释的中文术语。

译者自行创造、原文没有建立的中文名词或四字短语，如果查不到通行用法、读者必须看定义才能理解，或普通中文本来就能直接说明，必须重写。仍没有合适名称时保留英文并用普通中文解释。

## 行为边界核对

### 调用范围

- `description` 是否扩大或缩小触发条件；
- 用户调用与模型调用的边界是否保持；
- 一个 skill 是否被错误地允许或禁止调用另一个 skill；
- 路由文件是否仍只负责原来的场景。

### 规则力度与流程

逐项核对“必须、应该、可以、只有、禁止、默认、例外”，以及先后顺序、停止条件和完成条件。不得把硬性要求译成建议，也不得把建议升级成硬规定。

### 因果关系

保留作者解释行为原因的内容，特别区分：哪个条件导致哪个行为、哪些做法只节省 token、哪些会影响执行稳定性、哪些词承担行为引导，以及哪些说明只帮助人理解。

### 文件和配置

逐字核对 frontmatter 字段、配置键、文件路径、相对链接、skill 名称、命令、API、环境变量、代码块和版本号。只有用户或项目明确要求本地化链接时才修改，改后实际检查目标存在且可达。

## 专门审校

在主框架的分层审校中增加 Agent 执行视角：

1. 逐段对照原文，检查遗漏、增译、概念替换、因果和力度变化；
2. 只读中文，检查生硬术语、英文堆积、不自然语序和首次出现却未解释的概念；
3. 从 Agent 执行角度核对调用范围、步骤、分支、停止条件、完成标准、文件引用和关键词。

不能仅凭文本检查宣称模型行为完全一致。需要说明验证边界时，准确表述是：已完成语义、规则力度、调用边界和文件机制的文本对照；跨语言后的实际触发效果仍需通过 A/B 运行测试验证。
