# 开发规范

> 写代码时额外遵守。
> 通用行为红线见主文件工作纪律,全程适用、不分阶段;本规范只列代码独有的纪律。

## 简洁优先

**用最少的代码解决问题,不过度推测。**

- 不加要求之外的功能。
- 不为一次性代码造抽象。
- 不加没要求的"灵活性 / 可配置性"。
- 不为不可能发生的场景写错误处理。
- 不搞多余的兼容分支 / 双路径。
- 如果 200 行代码能写成 50 行,就重写。
- 写新代码前先搜本项目有没有现成的可复用轮子,禁止重复造轮子。
- 简洁的下限:信任边界的输入校验、防数据丢失的错误处理、安全相关、用户明确要求的,再怎么精简也不能省。"用最少代码"砍的是多余,不是这些。
- 检验:资深工程师会觉得这过于复杂吗?会就简化。

## 精准修改

**只碰必须碰的,只清理自己造成的混乱。**

- 不"改进"相邻的代码 / 注释 / 格式;不重构没坏的;匹配现有风格,即使你更想换个写法。
- 注意到无关死代码,提一下,别删。
- 你的改动产生孤儿代码(没用的 import / 变量 / 函数)→ 删掉;预先存在的死代码不删。
- 检验:每一行修改都能追溯到用户请求。

## 代码注释

> 注释的语言和编码(用中文、改已有注释、源文件编码、MSVC 编中文源的处理)见 `../../zh-cn-xiezuo/SKILL.md`·代码注释。本节只管工程判断:何时写、写什么。

### 何时必须写注释

判据:光看代码本身读不出意图、或读不出"为什么这么写",就加注释。常见的几类:

- 复杂逻辑、算法或非显而易见的行为
- 关键约束、边界条件或兼容性处理
- 平台差异、协议约束或性能考量
- 生命周期管理、错误恢复或安全相关代码

另外两种也必须加:

- 功能实现、Bug 修复、重构时,主动检查新增逻辑有没有上面那种说不清的复杂点,有就加。
- 刻意做的简化 / 走的捷径:标出它的上限和升级路径,免得后面看的人分不清是漏了还是故意。

例:

```cpp
// 简化:先用全局锁,所有账号共用一把;高并发下会串行、成为瓶颈,等吞吐吃紧再换按账号加锁。
```

### 何时不应写注释

以下情况**不要**添加注释:

- 代码本身已经足够清晰、命名自解释
- 注释只是重复代码内容,没有提供额外信息

噪声注释示例:

```cpp
// ❌ 只重复代码,无额外信息
// 调用函数清理临时目录。
ScheduleTempDirectoryCleanup(tempPath);
```

有效注释示例:

```cpp
// ✅ 提供了代码里没有的信息
// Windows Installer 在卸载阶段可能仍持有文件句柄,这里延迟删除临时目录。
ScheduleTempDirectoryCleanup(tempPath);
```

## 测试驱动

代码任务的成功标准,用测试来定(目标驱动的代码版,见主文件工作纪律·目标驱动):

- "加验证"→"为无效输入写测试,再让它们通过";"修 bug"→"写复现 bug 的测试,再让它通过";"重构 X"→"确保重构前后测试都通过"。
- 最低线:有易错逻辑的代码(分支 / 循环 / 解析 / 涉及钱或安全的路径),至少留一个能跑的自检,一个 `assert` 的 `__main__` 块,或一个小测试文件。不为它装测试框架、不造夹具、不给每个函数单独写一套(除非用户要)。一眼能看出对错、没有易错逻辑的一行,不用测。
