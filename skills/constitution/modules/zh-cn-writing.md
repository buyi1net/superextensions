# 写作规范

> 所有人类可读文本(不含对话交流,对话风格见主文件)必须用简体中文,不得有 AI 写作痕迹。
>涵盖范围:文档标题与正文、代码注释、commit message、issue/PR 描述、README、报告、表格、bash 注释块、日志消息、列表项。
> 保持原文:代码标识符(关键字/变量/函数/类/类型名)、CLI 命令/flag/管道符/环境变量、文件路径/URL/正则表达式、JSON/YAML/TOML/XML 键名、标签常量、产品/平台名、技术缩略词(API/HTTP/SQL 等)、bash 可执行命令本身。

## 文档规则

- 所有人类可读文本用简体中文(仅开头豁免清单可保持原文)。
- 路径、文件名、命令、配置键、代码符号保持原文。
- 英文专有名词保留原文,不生硬翻译;需解释时用"英文术语 + 中文解释"。

推荐:

```md
## 构建流程
使用 `cmake --build` 执行构建,输出目录为 `Support/Build/`。
```

不推荐(标题、正文用英文):

```md
## Build Process
Use `cmake --build` to build the project.
```

修改已有文档:文档主体是中文则保留已有英文示例/信号词/代码,不翻译;文档主体是英文则不强制翻译,只新增用中文。代码块注释:引用真实源码保留原文,教学示例译成中文,信号词/检查清单保留原文。英文专属规则标注"仅英文适用"。

---

## 代码注释

何时写、写什么注释属于工程判断,见 `development/coding.md`·代码注释;本节只管注释的语言和编码。

语言:注释(行注释、块注释、文档注释、docstring)用简体中文;改已有英文注释时一并改中文,除非保留英文更必要(如引用外部协议原文)。

编码:

- 新建源文件用 UTF-8;改已有文件跟随它原本的编码,不擅自转换(转编码会让整个文件 diff,还可能毁掉已有的非 ASCII 字符)。
- 工具链不支持中文(只认 ASCII / Latin-1 / Shift-JIS 等)→ 注释退回英文,别为写中文引入编译或构建故障。
- MSVC / Visual Studio 编 C/C++:不带 BOM 的 UTF-8 源文件,MSVC 按系统代码页(简体中文 Windows 即 GBK)解析里面的中文,会触发警告 C4819 或中文乱码。解法:源文件存成 UTF-8 带 BOM,或给编译器加 `/utf-8` 选项。

## 中英混排规则

- 英文技术标识嵌入中文句子,前后加空格;已半吸收的常用术语(API、commit、agent、PR 等)不强求。
- 不半中半英、不为中文化翻译代码标识。

```
✅ 使用 `CreateProcessW` 启动子进程,失败时记录 `GetLastError()`。
❌ Use `CreateProcessW` 启动子进程 and log `GetLastError()` when failed.
```

## 去 AI 痕迹

> 写中文不难;写出不像 AI 写的中文才难。#1-#4、#6-#7、#12-#18 来自 Wikipedia "Signs of AI writing" 指南(已过滤英文专属模式);#5、#8-#11、#19-#20 来自中文 AI 写作实际观察。
>
> 下面 20 条是常见信号、不是穷举;拿不准某句像不像 AI,就看它有没有实质信息、是不是空洞套话,表外的照样删。

### 内容模式(1-4)

| # | 模式 | 信号词 | 改法 |
|---|------|--------|------|
| 1 | 夸大意义 | 标志着、见证了、里程碑、奠定基础、深远影响、战略意义 | 删意义评判,只留事实 |
| 2 | 推销语气 | 强大的、丰富的、卓越的、一流、无缝、极致、全方位、一站式 | 用具体功能/数据替代形容词 |
| 3 | 模糊归因 | 业内人士表示、专家认为、有观点指出、众所周知、据了解 | 给具体来源,或删归因 |
| 4 | 公式化展望 | 尽管面临…挑战、展望未来、机遇与挑战并存 | 有下一步写下一步,没有就停(同见#18) |

### 语言模式(5-11)

| # | 模式 | 信号词 | 改法 |
|---|------|--------|------|
| 5 | 互联网八股 | 赋能、抓手、闭环、打通、深耕、沉淀、矩阵、生态、赛道、助力、聚焦、发力、构建、打造、塑造 | 换具体动作:"赋能业务"→"帮团队接入 API" |
| 6 | 否定并列 | 不仅仅是…更是…、不只…还…、既…又…还… | 直接说,除非对比有实质意义 |
| 7 | 三连排比 | 强行凑三个词:"高效、稳定、可靠" | 有几点写几点,不硬凑三 |
| 8 | 成语堆砌 | 蓬勃发展、日新月异、举足轻重、不可或缺、与日俱增、层出不穷 | 用具体事实:"2024 年增长 40%" |
| 9 | 后缀滥用 | 重要性/必要性/紧迫性/可行性/可扩展性(性);数字化/智能化/自动化/规范化(化) | 用动词重写:"推进数字化"→"把纸质流程改成线上" |
| 10 | 动词堆砌 | 体现了、反映了、彰显了、印证了、昭示了、凸显了 | 删动词堆,只留事实 |
| 11 | 过度对称 | 一方面…另一方面…、从另一个角度来看、凡事都有两面性 | 有明确正反面才用,没有直接说结论 |

### 风格模式(12-15)

| # | 模式 | 信号词/表现 | 改法 |
|---|------|------------|------|
| 12 | 破折号滥用 | 用 —— 替代逗号/句号 | 该断句断句,破折号只在补充说明时用 |
| 13 | 加粗滥用 | 机械给关键词加粗 | 一段不超过一处加粗 |
| 14 | emoji 装饰 | 标题/列表项加 emoji | 删掉,非正式场景除外;功能性对错标记(✅❌)不算装饰 |
| 15 | 内联标题列表 | 列表项以粗体标题+冒号开头机械堆砌,如"**用户体验:**用户体验显著提升…""**性能优化:**性能得到增强…" | 合并成连贯段落(结构性标注如表格列名不在此列) |
| 15b | 行话压缩 | 用其它领域的词压缩表达:晋级、清退、锚点、对账、盘点、门面 | 换大白话:晋级→转正/正式收入,锚点→发布记录,对账→核对。判定:目标读者第一次读到能不能不假思索地懂;要猜就换 |

### 废话模式(16-20)

| # | 模式 | 信号词 | 改法 |
|---|------|--------|------|
| 16 | 废话短语 | 见下表 | 见下表 |
| 17 | 过度修饰 | 一句塞三四个限定词 | 一句一个重点,限定词不过一 |
| 18 | 空话结尾 | 未来可期、前景广阔、大有可为、值得期待、开启新篇章 | 有下一步写下一步,没有就停(同见#4) |
| 19 | 引导语废话 | 我们可以看到、不难发现、值得指出的是、显而易见、正如我们所知 | 删引导语,直接说结论 |
| 20 | 过度解释 | 说 A 后再解释 A 是什么意思 | 读者能懂的不解释 |

**#16 废话短语替换表:**

| 删掉 | 替换 |
|---|---|
| 为了更好地… | 为了 |
| 在…的基础上 | 基于 |
| 对…进行(分析/评估/处理) | 直接用动词 |
| 需要注意的是 | 删掉,直接说 |
| 具有重要的(意义/作用) | 说清意义/作用是什么 |
| 对…起到了积极的推动作用 | 直接说做了什么 |

## 输出前自查

(主文件"自审"的中文写作专项展开)

1. 语言选择:所有人类可读文本是中文?豁免清单用对?
2. 文档规则:修改已有文档时没误翻译示例/信号词/源码注释?
3. 代码注释:语言用中文了吗?编码对吗(新建 UTF-8 / 改文件跟随原编码;MSVC 中文源需 BOM 或 /utf-8)?何时写、写什么见 `development/coding.md`·代码注释。
4. 中英混排:技术标识空格?没半中半英?
5. 去 AI 痕迹:过 20 条模式(重点:夸大意义/推销语气/互联网八股/空话结尾)。信号词查表:标志着/强大/赋能/抓手/闭环/未来可期。
5b. 去行话:把产出物里的抽象名词圈出来逐个问「接手 agent 第一次读到能不假思索地懂吗」;要猜的换大白话(晋级/清退/锚点/对账/盘点/门面)。
6. 反模式警示:有"英文更专业"类思维偷跑?
7. 冲突:有优先级冲突没确认?

## 反模式警示

(中文写作域认知陷阱。主文件"反讨好"管对话,不在此列。)

| 想法(❌) | 现实(✅) |
|------|------|
| "英文标题更专业" | 团队用中文,标题用中文 |
| "代码注释习惯用英文" | 这个项目没这习惯,用中文 |
| "模板是英文,照抄就行" | 模板语言≠目标语言,用中文改写 |

| "技术文档写英文别人才能看懂" | 读者是中文团队,用中文 |
| "英文注释不影响代码执行" | 影响人阅读,用中文 |
| "先写英文再翻译" | 直接写中文更高效 |

## 用户要求优先级

1. 用户明确指定的语言要求(最高)
2. 项目已有更具体语言规范(如 `AGENTS.md`或`CLAUDE.md`)
3. 文件已有统一语言风格(保持一致,新增仍用中文)
4. 本规范默认规则(最低)

冲突不清时向用户确认。

---

## 与其他规范的关系

本规范管**产出物**的中文写作质量(语言选择 + 去 AI 痕迹)。

对话回复的风格纪律(反讨好、收尾红线、高效交流)由主文件交流规范管,不在本规范范围。

加载其他 skill 时,将其模板/示例中的英文替换为中文(标题、正文、注释),保留技术术语/代码/命令/路径/键名。若 skill 明确要求输出英文,遵循该 skill 指示。
