# Git 管理

> Git 操作纪律：同目录多会话并行时，只动自己的文件。

## 并发前提

- 同一个目录里可能同时跑着多个 agent 会话，各自改各自的文件。
- git 操作碰到自己改动之外的工作树内容（未暂存、已暂存、未跟踪），会踩坏别的会话正在进行的工作。

## 起点检查

- 接手涉及 git 的任务，先跑 `git status`。
- 工作树有未提交改动：先弄清是谁的、属于什么任务；与当前任务无关或弄不清来源，先报告用户、确认处理方式。

## 检查点

- 大改动、实验性改动、可能要回退的操作，动手前先留检查点：
  - 要保留的工作 → 直接 `git commit`；
  - 一次性实验 → `git stash create` 拿快照引用（只建快照，不动工作树），恢复用 `git stash apply <ref>`。
- 回退就是恢复到检查点（`git stash apply`、回到对应提交）。
- 实验结束清掉检查点（`git stash drop`）。

## 永不运行

以下命令会毁掉其他会话的工作或绕过仓库检查，任何情况都不运行：

`git reset --hard` · `git checkout .` · `git clean -fd` · `git stash` · `git add -A` · `git add .` · `git commit --no-verify`

确有批量清理或重置的需要，停下报告用户，列影响面，等确认。

## 提交纪律

- 每次提交只含本会话自己改的文件：显式路径暂存（`git add <路径1> <路径2>`），暂存前跑 `git status` 核对暂存区里只有自己的文件。
- 提交信息说清这轮做了什么，遵循项目已有的提交风格。
- 任务收尾时工作树回到干净状态；确有遗留改动，告知用户是什么、为什么留着。

## 合并与冲突

- 发起 merge、rebase、pull 前工作树必须干净。
- 自己改过的文件冲突：逐块看冲突标记，弄清 ours 和 theirs 各自想做什么，追溯到两侧的来源提交再决定怎么合。整块取 `--ours` / `--theirs` 会丢掉一侧的意图。
- 没改过的文件出现冲突：撞上了别的会话或别的来源的改动，abort 并报告用户，由用户决定怎么处理。
- 永不 force push。
- 解完冲突自查：文件里没有 `<<<<<<<` / `=======` / `>>>>>>>` 残留标记，`git diff --name-only --diff-filter=U` 没有未合并路径。

## 与既有红线的衔接

- `git push`、`rebase` 等高影响操作走 constitution「破坏性操作」协议：先标影响、确认再动；「永不运行」清单里的命令不适用该协议，确认了也不跑。
- 发布流程走项目自己的发布 skill，不归本文管。
