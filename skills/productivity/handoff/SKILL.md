# 工作交接

工作交接的目标,就是把当前会话的核心内容整理成一份清楚明白的交接文档.无论是人直接看,还是下一位接手的 Agent 在没有历史聊天记录的情况下接手,都能立刻明白前面干了什么、现在卡在哪里、接下来该从哪一步继续干.

## 交前检查

开始整理交接前,先确认两件事:
1. 检查当前会话是否还有正在运行的子代理.手头操作必须先收尾完毕,确认子代理已经退出之后再开始交接,确保交给下一位 Agent 时现场是干净稳定的.
2. 检查此前由当前会话明确拉起的子代理、孙代理所遗留的临时会话文件,确认归属后清理干净,不要留给用户手动处理.无法确认归属的文件不要乱动.

## 整理交接内容时的纪律

写交接文档的时候,职责是老老实实把当前会话里已经发生的事情交代清楚,不要借着交接的由头去调查新问题、修改代码、运行测试或者提交 git.

- **用户传入参数的处理**:用户调用交接时传入的参数代表下一位接手者的关注重点,可以据此调整内容的详略分布,但绝不能因此漏掉继续开展工作必需的基础信息.
- **实话实说,不瞎编也不打免责补丁**:没有实际跑命令验证过的事情,就老老实实告诉接手者这件事还没验证,千万不要脑补成确定事实.但也不要在文档里到处加括号写“凭记忆未核验”这种免责套话,自然把情况说明白就行.
- **不抄大段已有资料**:如果项目里已经有写好的需求文档、方案设计、Git 提交记录或者 issue,只要交代清楚它们在哪个路径、主要说了什么就行,不要把整篇正文原封不动抄进交接里.
- **敏感信息必须脱敏**:密码、API Key、Token 这类敏感内容,统一替换成 `<REDACTED>`.交接里只告诉接手者去哪个配置文件找,或者怎么配置环境变量,绝对不能把明文留在文档里.
- **保留准确的技术线索**:接手者继续工作时必须要用到的文件路径、函数名、错误日志原文、关键命令和 commit hash,必须完整准确地留下来.
- **处理之前的摘要**:如果上下文里有之前留下的交接摘要标签(比如 `<prior-summary>` 或 `<previous-summary>`),把里面依然有效的内容和这轮会话的新进展合并在一起,写成一份自包含的新交接.已经做完且后续不需要的内容直接去掉,如果之前的信息和最新情况冲突,以最新情况为准;阻塞解除后更新状态,但保留继续工作仍需要的失败原因和解决结果.不要把摘要标签本身抄进文档正文.
- **自然流畅的大白话**:正文用自然的简体中文写,技术术语、命令和路径保持原文,不要写成生硬的公文或者法务条款.

## 必须覆盖的信息

交接文档不用强求格式死板,可以根据手头任务的实际情况来组织,但下面这几件事必须说清楚:

1. **目标与用户约束**:用户最终要做成什么效果,期间提过哪些明确的限制、偏好或者授权边界.
2. **当前的真实状态**:哪些工作是已经做完并且验证通过的,哪些工作正在做一半,哪些还没开始,以及当前真正阻止工作继续推进的问题是什么.
3. **关键决策与背景**:为什么选择现在的技术方案,中途放弃过什么做法,还有哪些暂时不确定的假设.
4. **下一步具体动作**:接手者拿到文档后,第一步应该具体干什么,给出一个清晰可执行的操作起点.
5. **相关文件与位置**:涉及的核心代码文件在什么位置,去哪里看报错,测试命令怎么跑.
6. **建议加载的 skill**:接手者开展后续工作确实需要用到的 skill.只列出当前环境里确实存在的 skill,不要去猜名字,也不要把 handoff 自己放进去.

## 交接文档结构参考

交接文档的正文直接陈述事实和计划.文件末尾**绝对不要包含任何让接手者停下来汇报、复述大纲或者向用户请示批准的流程条款**.

推荐参考下面的结构编写:

```md
# 工作交接

## 目标与关键约束

## 当前进展与卡点
- 已完成:
- 进行中:
- 待办与阻塞:

## 关键技术决策

## 下一步具体动作

## 相关文件与命令

## 建议加载的 skill
```

## 交付前检查(由子代理独立把关)

交接文档草稿写好后,不能直接发给接手者,必须拉起一个只读的检查子代理,对照真实环境认真核对一遍:

1. **核对信息真伪**:
   - 文档里提到的文件路径和分支名在当前环境中是否真实存在.
   - 如果项目有 git 记录,对照 `git status` 和 `git diff` 看看已完成和未完成的事项有没有漏记、错记.如果当前目录没有 git,就只核对文件是否存在.
   - 文档里给出的命令在语法上是否通顺;引用的报错信息如果能在当前可见的日志或历史会话中找到线索,就核对一下关键信息,找不到证据的就交代清楚是上一阶段排查发现的,别硬下断言.
   - **安全红线**:子代理只能做只读检查,绝对不能去执行带有修改、删除、代码提交或者外部网络请求等副作用的命令.
2. **检查文字表达**:
   - 检查文字是不是通顺自然的大白话,有没有写出一堆“（凭记忆未核验）”这种机械的免责牛皮癣.
   - 检查文档末尾有没有误写让接手者停工汇报、复述要点的官僚条款.
3. **修正与冷审后清理**:
   - 子代理发现有事实不符、关键信息遗漏或者文风别扭的地方,交接方负责修改草稿,随后重新核对,直到一轮完整检查没有新问题为止.如果遇到无法判断的争议或者反复冲突,停下来向用户请示.
   - 检查彻底完成后,只清理本次交接流程产生的临时记录,包括本会话拉起的检查子代理运行时创建的会话文件;无法确认归属的文件不要乱动.

## 交付路线选择

检查通过且收尾清理干净后,根据用户需求选择交付方式:

- 如果用户明确要求保存交接文件到指定路径:读取并执行 [文件交付模块](./modules/file-delivery.md).该路径生成的是用户的正式留存文件,不需要注入清理指令.
- 如果是其他情况(默认情况):读取并执行 [消息交付模块](./modules/message-delivery.md),生成临时中转文件并启动新会话交接.中转文件的清理指令会通过启动命令直接告知新会话.
- 如果用户同时提出了两种要求,或者拿不准用户的意思:停下来向用户确认.
