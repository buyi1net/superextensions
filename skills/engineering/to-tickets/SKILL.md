把计划、**规格说明（spec）**或当前对话拆成一组**工单（Tickets）**，每个工单都是一次**垂直切片（vertical slice）**（也叫“追踪弹”），并且标明它**依赖**哪些其他工单。

## 执行流程

### 第一步：收集上下文

基于当前对话里已经有的内容来整理。如果用户传了一个引用作为参数（比如规格说明的路径、issue 编号或 URL），就去拉取并读取完整内容和评论。

### 第二步：探索代码库（可选）

如果还没探索过代码库，就先探索一遍，了解当前状态。工单的标题和描述里要用项目的领域术语表（`docs/GLOSSARY.md`；多领域项目先看 `docs/GLOSSARY-INDEX.md`），并遵守所涉及区域内的 ADR。

留意有没有机会先做预重构(prefactor)，以便让后续实现更容易。遵循原则：“先让改动变容易，再做容易的改动。”

### 第三步：起草工单

把工作拆成一组**追踪弹（tracer bullet）** 式的任务。每个任务都是一个**垂直切片**：从数据存储到 API 到界面，每一层都包含，只做一小块功能。可以想象成切蛋糕时直切一窄条下来，这一条里有蛋糕也有奶油也有水果，而不是先把所有蛋糕切完、再切所有奶油。

规则：

- 每个任务做完之后，自己就能演示或验证
- 每个任务的大小要能在一次新对话里完成
- 需要提前改代码结构的，先做

给每个任务标明**依赖关系**：哪些任务必须在它之前完成。没有依赖的可以马上开始。

**大规模改代码结构是例外**

有些改动看起来只是“改个名字”或“改个类型”，但**爆炸半径（blast radius）** 特别大：比如你改了一个公共函数名，整个代码库有几百处调用，一改全崩。这种情况下，没法拆成独立的小任务来逐个完成。

这时候不要硬拆，改用 **expand–contract（先扩展后收缩）** 的策略：

1. **扩展（expand）**：在旧的旁边加上新的，两个并存，谁都不影响谁。
2. **分批迁移**：按模块（按包、按目录）一批一批地换成新的，每批迁移要控制在爆炸半径内，作为一个独立任务，依赖第一步的扩展任务。因为旧的还在，所以每批改完 CI（持续集成）都能保持绿色。
3. **收缩（contract）**：等所有模块都迁移完了，再把旧的删掉。这个删除任务依赖所有迁移任务。

如果分批迁移也没法让 CI 保持绿色，就让所有迁移共享一个集成分支，最后用一个 **integrate-and-verify（整合验证）** 任务来收尾，只在那一个任务上保证 CI 是绿的。

### 第四步：询问用户

把拆好的方案按编号列表展示给用户。每个工单要展示：

- **标题**：简短描述
- **依赖**：哪些其他工单必须在此之前完成（如果有的话）
- **产出**：这个工单完成之后，用户能使用或验证什么

然后问用户：

- 每个工单的大小是否合适，需不需要再拆分或合并？
- 依赖关系对吗？每个工单只依赖那些真正挡着它的工单吗？
- 有没有遗漏的工单，或者不该存在的工单？

根据用户的反馈不断调整，直到用户认可这个拆分方案。

### **第五步：生成工单文件**

用户确认拆分结果后，先确定工单文件的保存目录：

- 如果用户指定了工单目录，使用该目录；
- 如果用户提供了规格说明的文件路径，使用规格说明所在目录下的 `issues/` 子目录；
- 如果以上信息都没有，先向用户确认保存目录，不得自行猜测。

确定目录后，为每个工单单独创建一个 Markdown 文件，文件名采用 `<NN>-<slug>.md`。按前置关系从 `01` 开始编号，前置工单排在依赖它的工单之前。每个文件都要写明要构建的行为、前置工单、当前状态和验收标准。一个文件只能对应一个工单，不得合并多个工单。

```md
# <编号>：<工单标题>

**要做什么：** 从用户角度说明完成这个工单后能使用或验证什么，不要写成分层实现清单。

**依赖：** 写明必须先完成的工单编号和标题，或“无（可直接开始）”。

**状态：** 未开始

- [ ] 验收标准 1
- [ ] 验收标准 2
```

本地文件里别写具体路径或代码，因为这些容易过时。除非原型里有一段代码比文字更能说清决策（比如状态机、reducer、数据结构、类型形状），可以把它写进去，并注明来自原型。只保留关键部分，不需要把整个能跑的 demo 贴进来，截取最重要的那几块就行。
