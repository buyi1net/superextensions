把当前对话的上下文和代码库理解整理成一份规格说明,并发布到项目的问题跟踪系统里.不需要再问用户问题,直接综合你们已经聊过的内容就行.

## 执行流程

### 第一步:探索代码

如果还没探索过代码库,先探索一遍,了解当前状态.整份规格说明里都要使用项目的领域术语表(`docs/GLOSSARY.md`;多领域项目先看 `docs/GLOSSARY-INDEX.md`),并遵守所涉及区域的 ADR.

### 第二步:确认接缝

确定你要测这个功能用到哪些**接缝（seam）**.优先用现有的,别急着加新的.接缝越靠近调用方越好,越少越好,理想状态是只有一个.

### 第三步:写 spec

按下面的模板写规格说明,然后将文档保存到指定位置;如果项目没有指定规格说明的保存位置,先向用户确认位置,不得自行猜测.

~~~md
## 问题陈述

用户所面临的问题,从用户的角度来描述.

## 解决方案

针对该问题的解决方案,从用户的角度来描述.

## 场景需求

编写一份内容**非常详尽**的,带编号的用户使用场景与需求清单,覆盖该功能的所有方面.

每一项都必须说明:谁在使用,希望获得什么功能,以及获得该功能后能解决什么问题或得到什么收益.

每一项必须使用以下格式:

```text
1. 作为一名 <角色>,我希望拥有 <功能>,以便获得 <收益>
```

示例:

```text
1. 作为一名移动银行客户,我希望查看账户余额,以便更明智地决定如何消费
```

## 实现决策

列出已经确定的实现决策,包括:

- 将要构建/修改的模块;
- 这些模块中将要修改的接口;
- 来自开发人员的技术澄清;
- 架构决策;
- Schema 变更;
- API 契约;
- 具体交互方式.

**禁止写入具体文件路径或代码片段。** 这些内容可能很快过时.

唯一例外:原型生成的片段如果比普通文字更准确地表达某项决策,可以嵌入到对应的实现决策里(比如:state machine,reducer,schema,type shape),嵌入时简短注明该片段来自原型.只保留能够表达决策的部分,而非可运行的演示.

## 测试决策

列出已经确定的测试决策,包括:

- 什么是好测试的判据(只测外部行为,不测实现细节).
- 将要被测试的模块.
- 测试的已有先例.(即代码库中类似类型的测试方法)

## 超出范围

描述这份规格书明确不包含的内容.

## 补充说明

记录关于该功能的任何进一步说明.
~~~

### 第四步:审查 spec

把当前对话的上下文和代码库理解以及你写好的 `spec` 发给子代理去做审查,让其它 `LLM` 去给方案做查漏补缺操作,优先选用当前 `agent` 模型列表内的最强旗舰.比如:

1. `OpenAI` 系的 `gpt-6` 或 `gpt-5.6-sol`
2. `Anthropic` 系的  `Fable` 或 `opus`
3. 不要局限于列出的这些具体型号来,按照可用的最新系列来.
4. 给可用思考等级拉倒Max,它们就是你最佳的审查助手.
5. 当然,如果没有上述模型,那就选主会话所用模型和思考等级.

这个过程中要保持理智,其它 `LLM` 提出的意见,合理就采纳,不合理就拒绝,这样经过几轮修正,方案大概率就没啥问题了.一定注意不要进入无限的修改轮询中,该停的时候果断停.

### 第五步:汇总结果

**把最后的成功和接缝列出来跟用户确认，看是否符合预期。**
