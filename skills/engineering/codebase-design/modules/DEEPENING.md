# 深化

有一堆浅层模块摆在那，它们各自有一些依赖。怎么在**不破坏现有依赖关系**的前提下，**安全地**把它们**深化**。

默认你已掌握主 `SKILL.md` 的术语表：模块(module)、接口(Interface)、接缝(seam)、适配器(Adapter)。

## 依赖分类

看一个模块能不能深、怎么深，先看它**依赖了什么东西**。依赖属于哪一类，直接决定了**测试要怎么跨接缝去测**这个深化后的模块。

### 1. 进程内（in-process）

纯计算、内存里的状态、零 I/O。随时能深化：把模块合并，并直接通过新接口进行测试，适配器都省了。

### 2. 本地可替换（local-substitutable）

有些依赖在本地就能找到"替身"来顶替，比如测 Postgres 可以用 PGLite，测文件系统可以用内存版的。**只要替身存在，这个模块就能深化**。测试的时候，测试套件里把替身跑起来，模块对着替身测就行。这种情况下，**接缝在模块内部**，对外接口是不暴露端口的。

### 3. 远程但自有（端口与适配器）

有些服务是你自己的，但**隔着网络**——比如微服务调微服务、调内部 API。这种情况下，在接缝处定义一个**端口（port）**，也就是接口。**业务逻辑归深度模块管**，传输层（HTTP/gRPC/队列）当成**适配器**从外面塞进去。测试的时候塞一个内存版的适配器（不走网络），生产环境塞真的 HTTP 或 gRPC 适配器。

套用模板来说就是：*“在接缝处定义端口，生产环境接 HTTP，测试环境接内存版。这样哪怕系统是分布式的，核心逻辑还是收在一个深度模块里。”*

### 4. 真正的外部依赖（mock）

有些依赖是你管不了的，比如 Stripe、Twilio 这类第三方服务。深化后的模块不直接 new 它们，而是把这些外部依赖当作**端口**从外面**注入**进来。测试的时候，往这个端口塞一个**模拟适配器**（mock），不走真实的第三方。

## 接缝纪律

- **一个适配器 = 假接缝，两个适配器 = 真接缝。** 除非你能说出至少两个合理的适配器（比如一个跑生产、一个跑测试），否则别加端口。只挂一个适配器的接缝，就是多绕了一层，没有带来任何好处。
- **内部接缝与外部接缝。**一个深模块可以既有内部接缝（藏在实现里、只给自己的测试用），又有接口上的外部接缝。不要仅仅因为测试使用了内部接缝，就把内部接缝捅到对外的接口上。

## 测试策略：替换，而非分层

- 深模块接口上的测试一到位，浅层模块上的旧单元测试就变成了废纸，删掉。
- 在深化后模块的接口处编写新的测试。**接口就是测试面**。

- 测试只断言隔着接口看得见的结果，不看内部状态。
- 测试应该在内部重构后仍然有效，因为它们描述的是行为，而不是实现。
- 实现一动测试就得跟着动，说明它测穿接口了。
