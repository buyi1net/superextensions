# 深化

手上有一批浅层模块,它们各自有一些依赖.本文讲怎么在**不破坏现有依赖关系**的前提下,**安全地**把它们**深化**.

本文沿用主 `SKILL.md` 的术语表:模块(module),接口(Interface),接缝(seam),适配器(Adapter).

## 依赖分类

看一个模块能不能深,怎么深,先看它**依赖了什么东西**.依赖属于哪一类,直接决定了深化后的模块**要怎么跨接缝去测**.

### 1. 进程内(in-process)

这类模块只做纯计算,只用内存里的状态,不碰 I/O.它们随时能深化:把模块合并,直接通过新接口测试,连适配器都用不上.

### 2. 本地可替换(local-substitutable)

有些依赖在本地就能找到替身来顶替,比如测 Postgres 可以用 PGLite,测文件系统可以用内存版的.**只要有替身,这个模块就能深化**.

测试的时候,在测试套件里把替身跑起来,模块对着替身测就行.这种情况下,**接缝在模块内部**,对外的接口不需要为测试多开口子.

### 3. 远程但自有

有些依赖是你自己的代码,但**隔着网络**,比如调用自己部署的另一个进程.这种情况下,在接缝处定义一个接口(也就是常说的端口与适配器模式里的「端口」).

**业务逻辑归深度模块管**,传输层(HTTP,gRPC,队列)当成**适配器**从外面传进来.测试的时候传一个内存版的适配器,不走网络;生产环境传真正的 HTTP 或 gRPC 适配器.这样哪怕系统是分布式的,核心逻辑还是收在一个深度模块里.

### 4. 真正的外部依赖(mock)

有些依赖是你管不了的,比如 Stripe,Twilio 这类第三方.深化后的模块不在内部直接 new 它们,而是把这些外部依赖当作接口,从外面**注入**进来.测试的时候,给这个接口传一个 mock 适配器,不走真实的第三方.

## 接缝纪律

- **只有一个适配器的接缝是假接缝,有两个才是真接缝.** 除非你能说出至少两个合理的适配器(比如一个跑生产,一个跑测试),否则别加接缝.只挂一个适配器的接缝,只是多绕了一层,没有带来任何好处.
- **内部接缝和外部接缝分开.** 一个深模块可以既有内部接缝(藏在实现里,只给自己的测试用),又有接口上的外部接缝.不要因为测试用到了内部接缝,就把它暴露到对外的接口上.

## 测试策略:替换,而非分层

- 深模块接口上的测试写好以后,浅层模块上的旧单元测试就没用了,删掉.
- 新测试写在深化后模块的接口上,测试从接口调用,不从别处进.
- 测试只断言隔着接口看得见的结果,不看内部状态.
- 内部重构以后,测试应该照样能过,因为测试描述的是行为,不是实现.
- 实现一改,测试就得跟着改,说明测试绕过接口测到了实现细节.
