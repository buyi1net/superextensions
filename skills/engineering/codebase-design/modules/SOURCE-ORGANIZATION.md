# 源码组织

主 [SKILL.md](../SKILL.md) 负责定拆分和复用的原则,本文负责定代码放在哪儿,目录长什么样.

**适用范围**:新建项目时按本文的结构组织代码.接手已有项目时,按主 SKILL.md「已有结构的延续」沿用既有布局,新功能也顺着既有布局放;只有用户要求整理结构时,才按本文来改.开发框架对目录有约定的(比如 Next.js 的 `app/`,Rails),遵循框架的约定,本文只管框架没规定的部分.

**术语**:模块,接口,实现沿用主 SKILL.md 的定义.本文另外用到这几个词:

- **功能模块**:就是一个模块.只有一个文件时叫单文件的功能模块;拆成多个文件后,放这些文件的目录叫**功能目录**.
- **职责文件**:功能目录里按职责拆开的文件,比如界面,提示词,类型.
- **私有部件**:只给一个功能模块用的代码和资源.
- **分类目录**:放一排同类功能模块的目录,它本身不是模块.
- **注册列表**:把分类目录里的功能模块汇成一份列表的模块.
- **三件套**:接口,注册列表,分类目录这三样放在一起的结构,见「三件套」一节.
- **平台目录**:一个端(终端,桌面,Web,Android,iOS)的入口和它专有的代码,相当于这个端自己的源码根,见「平台目录」一节.
- **行数警戒线**:500 行左右的那条提醒线,见「文件体量」一节.

## 整体结构:浅而宽

源码树按四层来摆:源码根 → 分类目录 → 功能模块 → 职责文件.源码根看语言的惯例,TS 和 Rust 通常是 `src/`,Go 常用 `internal/`.

- **分类目录**:收一排同类,彼此独立的功能模块,比如 `tools/`,`commands/`,`tasks/`.除了这些成员,分类目录里只多一个放共用代码的 `shared/`.所有分类目录并排放在源码根下,中间不加 `core/`,`platform/`,`features/` 这类分组层.
- **功能模块**:一般是分类目录里的一个成员.不属于任何一组的功能模块(比如应用入口 `main.tsx`)直接放在源码根下.
- **职责文件**:功能目录里按职责拆开的文件,平铺在同一层.
- **接口和注册列表**:放在源码根下,和它们的分类目录同层(Go 和 Python 的注册列表例外,见各自一节).
- **平台目录**:每个端一个,和分类目录并排放在源码根下,见「平台目录」一节.

功能目录里的子目录只有两种:一种是资源目录(`locales/`,`assets/`,`native/`),里面放文案,图片,原生代码这类资源,不需要入口文件,内部怎么分按资源自己的规则(比如「界面文案」一节);另一种是职责文件变大后升级成的职责目录(见「职责文件变大」).

如果还想在功能目录里套别的子目录,先看它是不是一个能独立存在的新功能:是的话,就把它拿出来,作为分类目录里的另一个成员.

单元测试跟着被测文件放(`BashTool/BashTool.test.ts`).语言有固定约定的,按语言的约定来:Go 是放在同一目录的 `_test.go`,Rust 是写在同一个文件里的 `#[cfg(test)]` 模块.

## 三件套:接口,注册列表,分类目录

一组可插拔,可枚举的能力(比如工具,命令,任务),拆成接口,注册列表,分类目录三处,放在同一层:

```text
src/
├── Tool.ts    // 接口:单数.Tool 类型,调用上下文,公共类型
├── tools/     // 分类目录:每个工具一个成员
└── tools.ts   // 注册列表:复数,和分类目录同名.引入全部实现,按配置或特性开关决定启用哪些,导出工具列表
```

至少有两个成员,或者已经确定还要继续加,才立三件套.只有一个成员时,它就是一个普通的功能模块,放在使用它的那个模块旁边,不用提前立接口和注册列表.

依赖只朝一个方向走:实现依赖接口;注册列表依赖实现和接口.实现不 import 注册列表,同级的实现之间也不直接互相 import;实现要用工具列表或同级工具时,由调用方当参数传进来.接口,`shared/` 和 `utils/` 可以正常 import.

`shared/` 不是成员,注册列表不登记它(Rust 在 `tools.rs` 里写 `mod shared;` 是语言要求的模块声明,不算登记).

接口要单独放:注册列表要 import 全部实现,各个实现又要 import 接口,如果接口和注册列表写在同一个文件里,两边就会互相 import,形成循环依赖.

注册列表和分类目录同名.在 TS 和 Rust 里,注册列表放在分类目录旁边;Go 和 Python 放不了,注册列表要放进分类目录里,见各自一节.

新增或删除一个工具时,要改的只有两处:分类目录里对应的那个成员,和注册列表里的登记.

## 平台目录

一个产品要出多个端(终端,桌面,Web,Android,iOS)时,每个端一个平台目录,和分类目录并排放在源码根下,不为平台多套一层 `platforms/`.平台目录相当于这个端自己的源码根:入口文件放在这一层,本端的分类目录和功能模块在里面照本文组织,和外面一样平铺.所以平台里的代码会比源码根下多一层,这是本文唯一允许的整体加层.

- **入口文件**:按平台的惯例命名,比如 `main.tsx`,`MainActivity.kt`,`App.swift`,放在平台目录里.
- **连接适配**:要连到执行端的平台,放一个连接适配模块,只管协议适配;它也按「单文件与功能目录」组织,只有一个文件时就是 `connection.ts`,示例里写成目录是因为它拆过.模型循环,工具,权限这些执行能力只保留一份,在源码根下的分类目录里,各端通过 `connection/` 调用,不在平台目录里再实现一遍.
- **平台界面功能**:这个端专有的界面功能,每个功能一个功能模块,直接放在平台目录下;单文件还是目录,按「单文件与功能目录」来(`web/chat/` 是拆过的例子).功能目录里照样按「私有部件放哪儿」放界面,状态和文案.
- **框架约定**:有的框架会把一个端再分成几块,比如 Electron 的主进程 `main/` 和界面进程 `renderer/`,按框架来,每一块里面再照本文组织.

```text
src/
├── android/
│   ├── connection/           // 连到执行端的协议适配
│   ├── MainActivity.kt       // 入口
│   └── sessions/             // Android 端的会话列表功能
├── cli/
│   ├── handlers/             // 本端的分类目录:每个子命令一个成员
│   └── main.ts               // 入口
├── desktop/
│   ├── main/                 // Electron 主进程:窗口,托盘,托管本机 CLI 进程
│   └── renderer/             // Electron 界面进程
├── ios/
│   ├── App.swift             // 入口
│   └── connection/
├── Tool.ts
├── tools/                    // 执行能力,各端共用这一份
├── tools.ts
└── web/
    ├── chat/                 // 会话界面功能
    │   ├── chat.tsx          // 入口,用功能名命名
    │   └── locales.json
    ├── connection/
    └── main.tsx              // 入口
```

几个端共用一个完整的界面功能(比如桌面和 Web 共用的会话界面)时,在源码根下建一个分类目录(比如 `ui/`)放这个功能模块,和平台目录并排,平台目录只保留各端自己的部分.`utils/` 只放从功能里抽出来的通用代码,不放完整的功能模块.共享的界面功能用到窗口,通知,存储这类各端不一样的能力时,通过接口拿,由各个平台目录提供实现.

Android 的 Gradle,iOS 的 Xcode,桌面和 Web 的打包工具,各自在构建配置里登记自己平台目录的路径(Gradle 的源码集,Xcode 的构建目标,打包入口).源码放在 `src/` 下,不等于它们要共用一套构建.

## 文件体量

各家模型的上下文窗口大小不一样.小窗口的模型接手项目时,读到一个超大文件,上下文很容易被撑爆,注意力也跟着散掉,接下来就容易偷工减料,搞混自己该干什么.所以写代码时要有意识地控制单个文件的大小:

- 500 行左右是**行数警戒线**:过了它,就开始考虑要不要拆.
- 到 800 行左右,要按主 SKILL.md「目录和文件怎么分」的原则判断是拆还是保留:拆,就拿出拆分方案;保留,就说清哪些逻辑需要放在一起理解.

这两个数都是提醒值,不是硬上限.行数只负责提醒你该想想要不要拆;真正决定拆不拆的,是主 SKILL.md 的「高频共改的代码别轻易拆散」:拆完以后,改一处是不是更省事.

## 单文件与功能目录

一个功能模块只有一个文件时,就把这个文件直接放在分类目录里.文件里先写对外的入口和主流程,私有的小类型和辅助函数放在后半部分.

需要拆出第二个文件时,就在原地把它升级成同名目录:

1. 建目录 `commands/brief/`,把 `commands/brief.ts` 移进去,变成 `commands/brief/brief.ts`.
2. 新拆出来的文件也放进这个目录.
3. 全局搜索旧路径,把所有引用它的导入都改掉.原来的位置不留任何文件.

只有一种例外:对外发布的库,如果旧路径是外部用户正在 import 的公开路径,原位置可以留一个只做转发的文件,实现全部移进目录.

升级成目录只有一个触发条件:确实要拆出第二个文件.要不要拆,按「文件体量」一节判断;决定拆了,就按上面三步升级成目录.

**一个目录是功能目录还是分类目录,看里面装的是什么**:装的是一个功能模块的私有部件,它就是功能目录,入口要放在目录里面;装的是一排独立的同类功能模块,它就是分类目录,本身没有入口.平台目录不按这条判断,它相当于一个端的源码根,见「平台目录」.

分类目录不一定有注册列表:只有这组功能模块需要注册或枚举时(见「三件套」),旁边那个同名的复数文件才是它的注册列表.

所以看到 `foo.ts` 旁边有个 `foo/` 时,先问一句:`foo/` 里装的是不是一排独立的功能模块?是的话,这就是三件套;不是的话,说明 `foo/` 只是 `foo.ts` 拆出去的私有部件,入口漏在了外面,要把 `foo.ts` 移进 `foo/`.

入口文件用功能名命名(`BashTool/BashTool.tsx`),这样全局搜文件名能直接搜到,编辑器里也不会开出一排分不清的 `index.ts`.语言对入口文件名有规定的,按语言来:Rust 是 `mod.rs`,Python 是 `__init__.py`.

### 职责文件变大

功能模块本身还是一个,只是某个职责文件(最常见的是 UI)过了行数警戒线,决定拆开:这时把同一套升级规则往下用一层:把 `UI.tsx` 升级成 `UI/` 目录,入口 `UI/UI.tsx` 和拆出来的文件一起放进去.

拆出来的部分(比如一个 diff 视图)先留在 `UI/` 里;等别的功能模块也要用它时,再按「私有部件放哪儿」判断它归谁.

职责目录只有这一层;职责目录里还要再拆,就回头想想是不是该把功能模块拆开了.

## 私有部件放哪儿

只有这个功能模块用到的代码和资源,放进它的功能目录.常见的职责用固定的文件名,同一个分类目录里每个功能模块都这么叫,点进哪个工具目录都知道 UI 在哪:

| 职责 | 文件名 |
|---|---|
| 界面 | `UI.tsx` |
| 给模型的提示词 | `prompt.ts` |
| 类型 | `types.ts` |
| 常量 | `constants.ts` |
| 辅助函数 | `utils.ts` |
| 界面文案 | `locales.json`,拆开后变成资源目录 `locales/` |
| 原生扩展(N-API,Wasm) | 资源目录 `native/` |

表里没有的职责,按内容起名,比如 `permissions.ts`.文件已经在功能目录里了,文件名不用再带功能名前缀.

原生扩展有一个例外:如果构建工具链对源码路径有改不掉的要求(比如必须放进某个 Cargo workspace),可以放到工具链要求的位置,由所属功能模块的构建配置引用它,顺着这条引用就能查到它归谁.

一段代码出现第二个使用方时,先按主 SKILL.md「调用方多,不等于它通用」判断它归谁管.归某个功能模块管的,就留在那个功能模块里;确认是几方共用的,再放到所有使用方的最近公共祖先下面:

- 同一个分类目录里几个成员共用,放到这个分类目录下的 `shared/`,比如 `tools/shared/`.
- 跨多个分类目录通用,放到源码根下的 `utils/`.

`shared/` 和 `utils/` 是放共用代码的目录,既不是功能目录,也不是分类目录.它们里面的代码同样按「单文件与功能目录」组织.

## 界面文案(i18n)

界面文案和代码一样,跟着功能模块走.同一套文案只维护一份源文件;i18n 库需要的按语种格式,以及平台资源格式(比如 Android 的 `strings.xml`,iOS 的 `.xcstrings`),都是构建脚本从源文件生成的,不要手动修改这些生成的文件,要改就改源文件.

### 随规模变化

1. **起步:一个文件,按键组织.** 功能目录下放一个 `locales.json`,同一个键的所有语种写在一起:

   ```json
   {
     "permission_denied": {
       "en": "Command blocked by security rules",
       "zh-CN": "命令被安全规则拦截"
     },
     "execution_failed": {
       "en": "Execution failed with exit code {code}",
       "zh-CN": "执行失败,退出码 {code}"
     }
   }
   ```

   这样改一个键的时候,所有语种都在眼前,不容易出现改了英文忘了中文的情况.如果按语种分段写(`{"en": {...}, "zh-CN": {...}}`),同一个键的各个语种就被隔开了,单文件的好处也就没了.各语种用相同的占位符.

2. **文件过了行数警戒线:按命名空间拆,仍然按键组织.** 把 `locales.json` 拆成 `locales/<命名空间>.json`,每个文件还是同一个键的所有语种写在一起.命名空间按文案说的是哪一块来分,比如错误提示,权限提示.按键组织的文件,每个键大约占「语种数 + 2」行,三个语种一百来个键就到警戒线了.

   ```text
   tools/BashTool/locales/
   ├── errors.json
   └── permissions.json
   ```

   这样拆完,改一个键时所有语种仍然在眼前.文案一拆成多个文件,就接上校验脚本(见「防漏」).

3. **工具链要求集中目录:构建时汇总.** 翻译平台(Crowdin,Lokalise)或打包工具要求所有文案放在一个目录时,由构建脚本把各个功能模块的源文件汇总过去,需要按语种分的格式也由脚本转换,源文件本身仍然留在功能模块里,仍然按键组织.

4. **工具链要求源文件按语种维护:才按语种拆.** 只有工具链要求源文件本身就放在集中目录,并且按语种分文件(比如翻译平台会把译文直接写回那里),才在应用层按语种集中维护:一个功能模块一个文件,文件名用功能名;跨功能模块通用的词(比如确认,取消)放进 `common.json`.

   这时同一个键的各个语种分在不同文件里,按键组织带来的那层防漏没了,全靠校验脚本兜底:

   ```text
   src/locales/
   ├── en/
   │   ├── BashTool.json
   │   ├── common.json
   │   └── FileEditTool.json
   └── zh-CN/
       └── ...
   ```

加语种时,在每个有文案的功能模块里把这个语种补上:按键组织时是在每个键里加一行;按语种集中维护时是加一个语种目录.同时把它登记到必需语种清单(比如 `["en", "zh-CN", "ru"]`).这份清单全项目只有一份,放在 i18n 配置里;项目里还没有的话就建一份.语种代码用 BCP 47(`ja`,`zh-CN`).

### 谁负责翻译

- 界面文案由最终把它显示给用户的那一端负责.后端进程和跨进程消息只传稳定的错误码和参数(`{"code": "ERR_PERMISSION_DENIED", "args": {...}}`),由显示的那一端选语种.程序里的判断都看错误码,不去解析翻译后的文字.
- 给模型的提示词(`prompt.ts`)不是界面文案,不放进 `locales/`,也不跟界面文案一起批量机器翻译.要出多语种版本,就单独评测每个语种的效果.

### 防漏

按键组织时,改的时候各个语种都在眼前;但文案一拆成多个文件,或者按语种集中维护以后,改了英文漏了别的语种的情况就多起来了.这时候靠校验脚本来兜底,不靠 Agent 自觉.项目里还没有校验脚本,就写一个接进测试或 CI;文案的目录结构变了,脚本也跟着改:

- 以主语种(通常是 `en`)为准,必需语种里缺了键,或者占位符和主语种对不上,校验直接报错.
- 删键或改键名时,同时在代码里搜一遍引用,一起改掉.
- 键没变,但主语种的文案改了意思:把其他语种的对应条目标成需要重新翻译(用翻译平台的状态,或者项目自己的标记),发布前按项目的策略处理.

## 反例

下面这些都出自一份真实的大型 CLI 源码:

| 写法 | 问题 | 改成 |
|---|---|---|
| `query.ts`(1700 多行)+ `query/`(5 个文件,只有 `query.ts` 引用) | `query/` 是 `query.ts` 拆出去的私有部件,不是一排独立的功能模块,入口漏在了外面 | 把它移成 `query/query.ts`;移完它还有 1700 多行,再按「文件体量」一节拆 |
| `context.ts` + `context/`,两者毫无关系 | 名字刚好凑成三件套的样子,读代码的人会把 `context.ts` 当成 `context/` 的注册列表 | 改名,让不相干的两个模块用不同的名字 |
| `tools/AgentTool/AgentTool.tsx` 里 `import { assembleToolPool } from '../../tools.js'` | 实现反过来依赖注册列表,形成循环依赖 | 工具列表由调用方当参数传进来 |
| `tools/AgentTool/UI.tsx` 1194 行 | 里面混着进度处理,结果显示,拒绝和出错显示,分组统计好几块,改其中一块要在上千行里找 | 按「文件体量」一节判断该拆,再按「职责文件变大」升级成 `UI/` |

## 语言对照

### TypeScript(通用写法)

JavaScript 也是同样的组织方式.Python 的功能目录入口换成 `__init__.py`,注册列表另有写法,见下面的 Python 一节.

```text
src/
├── Command.ts                  // 命令接口
├── commands/
│   ├── brief.ts                // 单文件的功能模块
│   └── login/                  // 拆过的功能模块
│       ├── login.ts            // 入口
│       └── oauth.ts            // 表里没有的职责(OAuth 流程),按内容起名
├── commands.ts                 // 命令注册列表
├── Tool.ts                     // 工具接口
├── tools/
│   ├── AgentTool/
│   │   ├── AgentTool.tsx       // 入口
│   │   ├── prompt.ts
│   │   └── UI/                 // UI 变大后升级成的职责目录
│   │       ├── ProgressView.tsx
│   │       ├── ResultView.tsx
│   │       └── UI.tsx          // 职责目录的入口
│   ├── BashTool/
│   │   ├── BashTool.tsx        // 入口
│   │   ├── locales.json        // 界面文案,所有语种在一个文件里
│   │   ├── permissions.ts      // 本工具专用的权限适配
│   │   ├── prompt.ts
│   │   └── UI.tsx
│   └── shared/                 // 几个工具共用
├── tools.ts                    // 工具注册列表
└── utils/                      // 跨分类目录通用
```

入口文件用功能名命名,所以升级成目录以后,导入路径一定会变,全局修改导入这一步省不了.在 Node 原生 ESM 下(不经过打包器),导入还要写全扩展名,比如 `./tools/BashTool/BashTool.js`.

### Python

Python 的注册列表不能和分类目录同名并排放:`tools.py` 和 `tools/` 同时存在时,`tools/` 里有 `__init__.py` 就会遮住 `tools.py`,没有的话 `tools.py` 又会遮住 `tools/`,总有一边导入不到.

所以 Python 把注册列表放进分类目录,写成 `tools/registry.py`,`tools/__init__.py` 留空.接口文件用单数 `tool.py`,和 `tools/` 不重名,照常放在源码根下.

```text
src/
├── tool.py               # 接口
└── tools/
    ├── __init__.py       # 留空
    ├── bash/
    │   ├── __init__.py   # 入口
    │   └── prompt.py
    ├── registry.py       # 注册列表
    └── version.py        # 单文件的功能模块
```

### Go

Go 的一个目录就是一个包,一个包里可以有任意多个文件,包之间一旦循环 import,编译就会直接报错.所以规则在 Go 里这样对应:

- **分类目录里的每个成员都是一个子包**,只有一个文件也一样.对外用的名字首字母大写,私有的部分用小写留在包里.
- **成员包内部拆文件,不用再建目录**,在同一个包里多加文件就行.职责文件变大也一样(比如从 `ui.go` 拆出 `ui_progress.go`),不建职责目录,因为在 Go 里子目录就是一个新的包.
- **分类目录本身也是一个包,注册列表就写在里面**,文件名和分类目录同名.接口单独成包:成员的方法参数,返回值常常要用到接口所在包里的类型,这时如果接口放在分类目录的包里,成员就得 import 分类目录的包,而注册列表又 import 成员,形成循环依赖.接口单独成包,就不会碰上这个问题.

```text
internal/
├── tool/
│   └── tool.go           // 接口:type Tool interface
└── tools/                // 分类目录,同时是 package tools
    ├── bash/             // package bash
    │   ├── bash.go       // 入口,实现 tool.Tool
    │   ├── permissions.go
    │   ├── prompt.go
    │   └── ui.go
    ├── shared/           // package shared,几个工具共用
    ├── tools.go          // 注册列表:import tool 和各个成员,导出工具列表
    └── version/
        └── version.go    // 单文件的功能模块,也是一个子包
```

依赖方向是 `tools` → `tools/bash` → `tool`.如果这个仓库以后要对外提供 Go 库,就把接口包从 `internal/` 移出来.

### Rust

Rust 的模块树靠 `mod` 声明挂起来,一个模块可以写成 `foo.rs`,也可以写成 `foo/mod.rs`.按本文组织时两种写法都会用到,按功能目录和分类目录来区分:

- **功能目录用 `foo/mod.rs`.** 入口要放在目录里,而 Rust 不能用功能名当入口文件(写成 `file_edit/file_edit.rs` 会变成子模块 `file_edit::file_edit`),所以只能叫 `mod.rs`.职责文件变大也一样,`ui.rs` 升级成 `ui/mod.rs`.
- **分类目录用 `tools.rs` + `tools/`.** `tools.rs` 就是 `tools` 模块本身,它负责声明成员(`mod bash;`)和做注册列表,正好对上三件套.
- **单文件的功能模块用 `foo.rs`**,比如 `tools/version.rs`.升级成目录时改成 `version/mod.rs`,父模块里的 `mod version;` 两种写法都能解析,调用方的路径不用改.

```text
src/
├── lib.rs            // mod tool; mod tools;
├── tool.rs           // 接口:pub trait Tool
├── tools/
│   ├── bash/
│   │   ├── mod.rs    // 入口:mod prompt; mod ui;(不加 pub)
│   │   ├── prompt.rs
│   │   └── ui.rs
│   ├── shared.rs     // 几个工具共用
│   └── version.rs    // 单文件的功能模块
└── tools.rs          // 注册列表:mod bash; mod shared; mod version; 加注册函数
```

- 私有的子模块不加 `pub`.子模块里给上一层用的函数标 `pub(super)`:`bash/prompt.rs` 给 `bash/mod.rs` 用,`shared.rs` 给 `tools` 下的各个成员用,都是这么写.
- 同一个 crate 里模块之间互相引用,编译器不会拦,单向依赖要靠自己守住.

**分类目录也可以是一整个 crate.** 工具多到要单独编译时,把它们放进一个独立的 crate:这个 crate 的 `src/` 就是分类目录,`lib.rs` 声明各个成员并做注册列表,接口放在另一个 crate 里.

crate 之间不能循环依赖,接口单独成 crate,依赖方向就由编译器守住了.各个 crate 按「多个构建单元」并排放在仓库根下:

```text
my-agent/
├── Cargo.toml            // [workspace] members = ["agent", "tools"]
├── agent/
│   └── src/
│       ├── lib.rs
│       └── tool.rs       // 接口:pub trait Tool
└── tools/                // 依赖 agent;整个 crate 是一个分类目录
    └── src/
        ├── bash_tool/
        │   ├── locales.json
        │   └── mod.rs    // 入口
        ├── lib.rs        // 注册列表:mod bash_tool; mod shared; 加注册函数
        └── shared.rs     // 几个工具共用
```
- Rust Book 把 `mod.rs` 叫作旧写法,但编译器仍然支持;同一个模块两种写法同时存在会编译报错(E0761),不同模块各用一种是合法的.按上面的判断方法,一个模块只用一种写法.

## 多个构建单元

这一节说的构建单元,是有自己构建清单的单元:独立的 npm 包,Go module,Cargo workspace 里的各个 crate.同一个产品的各个端按「平台目录」放在 `src/` 下,不算构建单元.

一个仓库里有多个构建单元时,每个构建单元内部各自按本文组织.仓库根下也是浅而宽:各个构建单元并排放在仓库根下,目录名说清它是什么(`agent/`,`tools/`,`executor/`),中间不按语言或类型再套一层 `apps/`,`crates/`,`services/`.Cargo workspace 常见的 `crates/` 也一样不套,Cargo 的 `members` 写哪个路径都行,没有要求这一层.多了一个构建单元,也只是在仓库根下多一个并排的目录.

构建工具对目录真有硬要求时,才按工具来.

```text
my-agent/
├── executor/             // Rust 执行引擎,独立 Cargo.toml,单独发版
├── protocols/            // 跨构建单元共享的协议源文件
│   └── agent_event.proto
└── src/                  // 主产品,各端的平台目录都在这里
    ├── android/
    ├── cli/
    └── web/
```

跨构建单元共享的协议源文件(`.proto`,schema)放在仓库根下单独的一个目录里.根据协议生成的代码归各个使用方,在生成配置里写明输入的协议文件和输出位置;要改就改协议源文件,再重新生成.
