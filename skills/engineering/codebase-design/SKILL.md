# 代码库设计

写一个功能,既要琢磨怎么实现,也要考虑代码放哪儿,能不能复用现有的东西.先看手头的需求需要多复杂,再去安排目录和文件;涉及接口定义,模块封装和测试时,用「深度模块」和「可测试性」原则来做取舍.具体怎么组织,跟着项目的实际情况走.

模块尽量做成**深度模块(Deep Module)**:接口尽量小,暴露的信息尽量少,背后的实现足够厚,能解决的问题足够多.接口开在**接缝(Seam)**上,测试对着接口测.

设计和重构时看三件事:**让调用方省力(高杠杆 leverage),让维护方省心(高局部性 Locality),让测试方省事(直测接口).**

## 一、术语表

下面这些术语严格按定义用,不要拿 `component`,`service`,`API`,`boundary` 换着叫.

**模块(Module)**:指任何「有接口,有实现」的东西.模块的规模不设限,可以小到一个函数,也可以大到一个包或横跨多层的模块.别用「单元」「组件」「服务」这类词代替它.

**接口(Interface)**:远不止函数签名那几行代码.**调用方为了把它用对,所需要知道的一切信息,全都是接口的一部分.** 比如:类型签名,合法调用的前提条件(不变量),调用顺序约束,会抛出哪些错误,依赖什么环境变量,性能特征.别用「API」或「签名」指代接口,这两个词只涵盖了外表,装不下这些内在约定.

**实现(Implementation)**:模块内部的具体代码.它与「适配器」不同:只有在讨论接缝的两端时,我们才叫它**适配器(Adapter)**;平时一律叫**实现**.

**接缝(Seam)**:(源自 Michael Feathers)指的是程序里的一个位置:不用改这里的代码,就能改变程序在这里的行为.模块的接口就开在接缝上.

注意把两件事分开想:**接缝选在哪儿**是一项独立的设计;**接缝后挂什么实现**是另一回事.

别把接缝叫成「边界」,避免跟领域驱动设计(DDD)里的「限界上下文」搞混.

**适配器(Adapter)**:立在接缝那头,把接口落实下来的那份实现.这个叫法强调的是它扮演什么角色,顶的是哪个坑,不是里面代码有多长.

**深度(Depth)**:本质是接口的「杠杆率」.调用方弄懂这个接口,能撬动多大的能力?接口极其精简,背后能摆平极多复杂度 → **深(Deep)**;接口本身跟实现一样繁琐,调用方学完接口等于把源码也读了一遍 → **浅(Shallow)**.

**杠杆效应(Leverage)**:深模块带给调用方的好处.调用方花很小的理解成本,就能办成很大的事.实现只写一次,所有调用方和测试都能低成本复用.

**局部性(Locality)**:深模块带给维护者的好处.以后要改的需求,要修的 bug,要读懂的核心逻辑,都**收在这一处**.不用顺着调用链到处找,改好这一处就行.

### 深与浅

**深模块(Deep Module)** = 小接口 + 大量的实现细节:

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少,参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑全藏在里面
│                     │
└─────────────────────┘
```

**浅模块**(**Shallow module**) = 大接口 + 较少的实现内容(应避免这种情况):

```
┌──────────────────────────┐
│    Large Interface       │  ← 方法多,参数复杂
├──────────────────────────┤
│   Thin Implementation    │  ← 只是把调用转手传下去
└──────────────────────────┘
```

**设计接口时,拿这几个问题问一遍:**

- 我能把方法数量再砍掉几个吗?
- 参数还能再精简一些吗?
- 我还能在内部隐藏更多的复杂度吗?

### 核心脉络串联

- 一个**模块**对外有且只有一个**接口**,调用方和测试只能看见这个.
- 模块**深不深**,衡量的是它的**接口杠杆率**:接口越窄,办的事越多,模块就越深.
- **接缝**是模块**接口**所处的位置;**适配器**立在**接缝**后,负责把接口兑现.
- **深模块**带来的好处是:调用方省力(**杠杆效应 leverage**),维护方省心(**局部性 Locality**),测试方省事(对着接口测).

## 二、设计规则

### 简洁设计

简洁的目的,是让代码更容易理解和修改.涉及模块和接口时,结合深度模块的原则,把调用方不必知道的复杂度留在实现里.

1. **先做好眼前的事,怎么简单怎么来.** 只用一次的代码,按当前需要写利索就行,别急着抽象成「通用架构」;眼下用不着的灵活性和配置项,等真有需要了再补.
2. **分支与兼容要有理有据.** 错误处理,兼容分支,为同一件事保留两套做法,都不能凭感觉随便加.写之前要看实际需要:会收到什么输入,运行在什么环境,还要支持哪些行为.有这些需要,就留着;若是觉得「以后可能用得上」,就先别加.当然反过来也一样:当前样例或测试没碰到的路径,未必就是废代码,得结合真实场景判断.
3. **简化是为了让人读起来更容易理解,改起来少踩坑.** 不能靠无谓的「压行」或炫技把代码变短;让代码容易理解的主要手段是结构,命名,类型和测试,不要为了补说明性文字注释而保留多余复杂度.功能完整且代码质量过关就该收手,千万别因为「好像能少写两行」或「我更喜欢另一种写法」就无休止地返工.
4. **守住底线.** 再怎么追求精简,对外部输入(用户输入,网络数据,读进来的文件)的校验,防止数据丢失的错误处理,安全相关逻辑以及用户明确要求的内容,也一概不能省.

### 源码组织与复用

代码该放在哪儿,该不该拆,该不该抽成公用,可以重点看两点:

- **局部性**:改动这里时,被波及的逻辑能不能在同一个地方顺手搞定?
- **杠杆效应**:抽成公用后,调用方是真的更省事了,还是反而更累了?

#### 目录和文件怎么分

动手写第一行代码之前,先读 [源码组织](./modules/SOURCE-ORGANIZATION.md),弄清楚代码该放在哪儿.它讲这些:

- 分类目录和注册列表怎么配,各个端的平台目录怎么摆;
- 文件写到多大该考虑拆,单文件什么时候升级成目录;
- 私有部件和界面文案放哪儿;
- 老项目和框架约定怎么让路;
- TS,Python,Go,Rust 各自的写法.

下面四条是拿不准时做判断用的原则,模块里的具体规定不在这里重复.

1. **职责优先.** 先理清这段代码背后的业务归属或技术职责,再决定落脚点.关系紧密的代码尽量放在一起;职责独立,需要各自变化的部分,可以分开.
2. **一个文件理清一件事.** 文件里放一组职责清楚的代码,目录把相关文件放在一起.
3. **高频共改的代码别轻易拆散.** 经常一起阅读,一起变动的代码,尽量放在一起.拆分前先想想:拆开之后,改一处时能少读一些无关代码,还是得在好几个文件间来回跳跃,透传一堆中间状态?用理解和修改的成本来衡量拆分是否划算,行数和函数数量只是提醒.
4. **拆文件不等于拆模块.** 一个模块内部可以有多个文件,调用方仍然通过模块接口使用它.拆文件本身不需要增加对外接口;有独立职责和实际调用需求,再考虑新的抽象.

#### 共享代码与实现复用

1. **调用方多,不等于它通用.** 一段代码放哪儿,看它「归谁管」.订单规则就算有很多调用方,也可以继续放在订单模块里.确实跨模块通用,职责又稳定的能力,再放到共享位置;放进哪个共享目录,见源码组织模块的「私有部件放哪儿」.别一看到有第二个地方在用就急着提公用;反过来,也别一看到 utils 目录就盲目认定设计有问题.
2. **看本质是不是同一回事.** 看两处代码是不是在做同一件事,会不会因为同一条规则变化而一起改.输入输出,错误处理,副作用和外部约束能配合这次需求,就优先用已有实现;只是代码「长得像」,还不够成为合并的理由.
3. **共享不能给调用方添堵.** 共享模块应该让调用方省心.如果调用方想用它,还得先研究其他模块的业务,或者共享函数里总要加 `mode` 参数和业务分支,就回头看看共同部分是不是找错了.别让原本独立的需求,因为强行共享而被绑定在一起改.

#### 已有结构的延续

接手现有项目时,先顺着手头的需求,看清相关的目录结构,命名习惯,实现方式与调用关系,并参考项目规范弄懂原有的代码组织逻辑.既有的合理设计尽量沿用,让后人按习惯就能轻松找到新代码;如果原有结构确实挡住了当前实现,再局部改造相关部分.改造的标准是代码是不是更容易理解和修改,而不是长得像不像教科书模板.

这里不额外要求目录说明或逐文件清单;项目已有要求的,照常执行.

### 模块与接口设计

1. **深度看的是接口,而不是实现有多长.** 一个深模块内部完全可以拆成几个内部模块,各自能独立 mock 和替换,但这些内部模块绝不该暴露给外部.

   一个成熟模块可以同时有两套接缝:**内部接缝**(给自己的测试替换依赖用,外部感知不到)和**外部接缝**(真正对外暴露的接口).
2. **做个「假想删除」的思想实验.** 保持现有功能和对外契约不变,假想去掉这一层模块封装,看看调用方需要接手哪些工作.
   1. 如果它的复杂度也跟着消失了 → 说明这模块本来就没用,徒增调用层级.
   2. 它的复杂度没有消失,反而散落到每个调用方手里,每个调用方都得各自把这些活重写一遍 → 说明这个模块**替调用方扛下了复杂度**,值得留着.
3. **测试只能对着接口测.** 测一个模块,就像真实调用方那样从它的接口调用;单独测某个内部模块,就对着这个内部模块自己的接口.替换依赖可以走内部接缝,但调用入口始终是接口.

   如果测试非得绕过接口,去碰私有函数或内部状态,说明这个模块的设计有问题.
4. **接缝要有实际的替换需要.** 至少能说出两个合理的适配器,比如生产实现和测试替身,再考虑加这道接缝;不要求提前把两套都写出来.没有实际的替换需要,就别凭空加一层抽象.

### 可测试性设计

接口开在接缝上,测试才能对着接口来,而不用扒开模块内部.好的接口让测试水到渠成,下面三条都是这个意思:

1. **依赖从外面传进来,不要自己在里面 new.**

   好测的写法:

   ```typescript
   function processOrder(order, paymentGateway) {}
   ```

   难测的写法:

   ```typescript
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **结果从函数返回出去,不要偷偷改外面的状态.**

   好测的写法:

   ```typescript
   function calculateDiscount(cart): Discount {}
   ```

   难测的写法:

   ```typescript
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **接口要让调用方容易理解和使用.** 减少不必要的方法,参数和使用约束,保留必要的参数和依赖注入点.看调用和测试是不是更省事,不按方法或参数的数量直接下结论.

## 附: 禁止的表达方式

**1. 深度 = 实现行数 / 接口行数**

这是 Ousterhout 书里的定义,但别机械套用.按这个算法,往实现里堆无用代码也能「变深」,这显然不对.

我们说的深度,看的是**杠杆效应**:接口很薄,背后撬动的能力很多.

**2. 把「接口」理解成 TypeScript 的 `interface` 关键字**

这样理解太窄了.我们说的接口,是调用方为了不踩坑必须知道的**所有东西**:除了类型,还有调用顺序,会抛什么错误,依赖什么环境变量,性能特征.

**3. 滥用「边界」这个词**

「边界」在软件领域用得太泛,特别容易和领域驱动设计(DDD)里的「限界上下文(Bounded Context)」搞混.谈模块之间怎么交互时,用接缝(Seam)或接口(Interface),说得更准.

## 附: 进阶延伸

- **要按已有的依赖关系深化一组模块时**,读 [DEEPENING](./modules/DEEPENING.md):依赖分哪几类,接缝怎么管,以及「替换,而非分层」的测试策略.
- **想看一个接口还有没有别的设计方式时**,读 [DESIGN-IT-TWICE](./modules/DESIGN-IT-TWICE.md).做法是并行拉起多个子代理,让它们各自用完全不同的思路设计同一个接口,再从三个方面横向对比,做取舍:**深度**(杠杆有多高),**局部性**(改动集中在一处还是到处散落),**接缝位置**(接口放在哪儿).
