# 代码库设计

写一项功能,既要想怎么实现,也要想代码放哪儿、能不能用已有的实现.这里把这些判断放在一起:先看当前需求需要多复杂,再安排目录和文件;涉及接口、模块实现和测试,就结合深度模块和可测试性原则来判断.具体怎么组织,跟着项目的实际情况走.

设计**深度模块(deep module)**:接口很小,背后能做的事却很多,接口开在一条干净的**接缝(seam)**上,测试只对着接口做.凡是设计代码,重构代码的场合都要使用这套术语和这些原则.**我们的目标是让调用方省力（杠杆效应 leverage），维护方省心（局部性 Locality），测试方省事（对着接口测）。**

## 简洁设计

1. 先把当前需求做好,选足够简单的写法.只用一次的代码,就按这次的需要写,不额外搭一套通用抽象;还没人要求的灵活性和配置,等有需要再加.
2. 错误处理、兼容分支,或者为同一件事保留两套处理路径,都要有实际理由:会收到什么输入、要在哪些环境运行、哪些行为还得支持.有这些需要就保留,纯粹猜想出来的场景不用提前安排.当前样例或测试没遇到,不代表那条路径就多余.
3. 简化是为了让实现更容易理解和修改.功能要保住,格式、命名和必要注释也要正常,不能靠压行把代码变短.需求和质量要求都满足了,就可以停;还能少写几行,或者自己更喜欢另一种写法,都不是继续重写的理由.
4. 有几类东西不能为了精简省掉:信任边界的输入校验、防止数据丢失的错误处理、安全相关逻辑,还有用户明确要求的内容.

## 源码组织与复用

### 目录和文件怎么分

1. 先看这段代码负责什么业务,或者承担什么技术职责,再找适合放它的模块.相关实现尽量放在一起;职责本来就独立、需要各自变化的部分,可以分开.
2. 文件里放一组说得清职责的代码,目录把相关文件放在一起.具体放哪儿,要看语言、框架、构建要求和项目现有结构.新项目先满足眼前的需求,内容多起来再建目录.
3. 经常要一起读、一起改的代码,尽量放在一起.拆开以后,改一个地方是不是能少读一些无关代码?还是得来回跳更多文件、传更多状态?用这些变化判断拆得好不好,别按固定行数或函数数量切,也不用给每个小功能都建一个目录.
4. 一个模块内部可以有多个文件,调用方还是通过模块接口使用它.拆文件本身不需要增加对外接口;确实有独立职责和调用需求,再考虑新的抽象.

### 共享代码与实现复用

1. 先看这项能力归谁负责.订单规则有多个调用方,也可以继续放在订单模块里;确实跨模块通用、职责又稳定的能力,再放到合适的共享位置.不用一有第二个调用方就搬进 utils 或 common,也不能光看目录叫这个名字就说设计有问题.
2. 看两处代码是不是在做同一件事,会不会因为同一条规则变化而一起改.输入输出、错误处理、副作用和外部约束能配合这次需求,就优先用已有实现.只是代码长得像,还不够成为合并的理由.
3. 共享以后,调用方应该更省心.如果反而得了解别的业务,或者共享函数总要加模式参数和业务分支,就回头看看共同部分是不是找错了.原本独立的需求,也不该因为复用而被迫一起改.

### 已有结构的延续

接手项目,先看这次相关的目录、命名、实现和调用关系,再结合项目已有的规范和说明,弄清代码原来是怎么放的.合理的习惯接着用,让后来的人顺着原来的结构就能找到新代码.现有结构确实挡着这次实现,就改相关的部分.判断依据是代码好不好理解和修改,不是目录长得像不像某个模板;这里也不要求另写组织说明或逐文件清单.

## 术语表

请严格使用这些术语:不要拿 `component`,`service`,`API`,`boundary` 换着叫.保持术语的一致性才是关键所在.

**模块(module)**:就是指任何"有接口,有实现"的东西.故意不做规模上的限制,可以小到一个函数,也可以大到一个包,甚至是一个横跨多层的东西.不要用"单元","组件","服务"这些词来替代.

**接口(Interface)**:不光是函数签名那几行字.调用方想把这个模块用对,需要知道的所有东西都算接口的一部分,类型签名算,但还有:什么情况下调用合法(不变量),必须先调哪个再调哪个(顺序约束),会抛出什么错(错误模式),要不要配环境变量(配置),大概多快多慢(性能特征).这些全算接口.别用"API"或"签名"来替代,这两个词太窄了,说的只是"类型长什么样",装不下上面这一堆东西.

**实现(implementation)**:指的是一个模块内部的东西,即它的代码本体.它与**适配器(Adapter)** 是两个词.适配器可以很小但背后实现很大(比如连 `Postgres` 的仓储),也可以很大但背后实现很小(比如内存里的假实现).聊到接缝的时候才叫"适配器",平时就管它叫"实现".

**深度(depth)**:说白了就是接口的"杠杆率",调用方学一个接口,能撬动多大的能力?接口很小,但能干的事很多 → 深(deep).接口本身就跟实现一样复杂,调用方学完接口基本等于把实现也学了一遍 → 浅(shallow).

**接缝（seam）**:(出自 Michael Feathers)它的定义是:程序里有一个位置,你可以在这个位置改变程序的行为,而不用直接修改这个位置的代码.说白了,模块的接口就挂在这个位置上.关于接缝,有两件事得分开放:接缝放哪儿,这是独立的设计决策;接缝后面放什么,那是另一回事.另外,别用"边界"这个词,因为它和`DDD(领域驱动设计)`中的`限界上下文(bounded context)`概念容易混淆.

**适配器(Adapter)**:就是在接缝那头实现某个接口的具体物件.它说的是"它扮演什么角色"(顶的是哪个坑),而不是"里面是什么"(怎么实现的).

**杠杆效应(leverage)**:就是深度设计给调用方带来的好处.接口越深,调用方花越少的力气学会它,就能干越多的事.而且这个好处是一次投入,多处回报:同一个实现,N 个调用方在用,M 个测试在测,但成本只付了一次.

**局部性(Locality)**,就是深度设计给维护者带来的回报.你要改的东西,要修的 bug,要懂的逻辑,要测的验证,全都**聚在一处**,不用翻遍所有调用方.改一处,全解决.

## 深与浅

**深模块(depth module)** = 小接口 + 大量的实现细节:

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少,参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑全藏在里面
│                     │
└─────────────────────┘
```

**浅模块**(**Shallow module**) = 大接口 + 较少的实现内容(应避免这种情况):

```
┌──────────────────────────┐
│    Large Interface       │  ← 方法多,参数复杂
├──────────────────────────┤
│   Thin Implementation    │  ← 只是把调用转手传下去
└──────────────────────────┘
```

**在设计一个接口时，问自己几个问题：**

- 我能减少方法的数量吗?
- 我能简化这些参数吗?
- 我还能在内部隐藏更多的复杂度吗?

## 设计原则

1. **深度看的是接口，不是看里头怎么写的。** 一个深模块完全可以在内部拆成一堆小零件,每个都能单独 mock,单独替换,但这些零件不暴露给外面.一个模块可以同时拥有**内部接缝**(给自己测试用的,外部看不见)和**外部接缝**(对外暴露的接口).
2. **假想删除该模块。**做个思想实验:把这个模块删了会怎样?
   1. 如果它的复杂度也跟着消失了 → 说明这个模块啥也没干,就是个"传话筒",多余的.
   2. 它的复杂度没有消失,而是分散到了 N 个调用方那边,每个调用方都得自己处理一遍 → 说明这个模块**在帮调用方扛事儿**,值这个钱.

3. **测试只能对着接口来。** 真正的调用方怎么用这个模块,测试就应该怎么用,跨的是同一个接缝.如果你的测试非要**绕过接口**,直接扒开模块内部去测,那说明这个模块长歪了.
4. **只有一个适配器？那这个接缝是假的。有两个适配器？才是真的**. 如果没有什么东西会真的在接缝两边有所不同,就别硬造一个接缝出来.

## 可测试性设计

好的接口让测试水到渠成:

1. **依赖从外面传进来，不要自己在里面 new。**

   ```typescript
   // 好测
   function processOrder(order, paymentGateway) {}

   // 难测
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **结果从函数返回出去，不要偷偷改外面的状态。**

   ```typescript
   // 好测
   function calculateDiscount(cart): Discount {}

   // 难测
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **接口越小越好。** 方法少一个,测试就少写几个;参数少一个,测试前置准备就省一行.

## 概念关系

- 一个**模块**有且只有一个**接口**,调用方和测试只能看见这个.
- **深不深**说的是**模块**,量的是它的**接口**,接口窄,干的事多,就深.
- **接缝**就是**模块**的**接口**待的那个地方.
- **适配器**蹲在**接缝**那里,把**接口**的要求给实现了.
- **深模块**带来的好处是:调用方省力(**杠杆效应 leverage**),维护方省心(**局部性 Locality**),测试方省事(对着接口测).

## 禁止的表达方式

**1. 深度 = 实现行数 / 接口行数**

这是 Ousterhout 原书的定义,但按这个逻辑,你往实现里拼命堆代码就能"变深",完全跑偏了.我们定义的深度是**杠杆效应**,即接口有多大的"撬动力".

**2. 把“接口”理解成 TypeScript 的 `interface` 关键字**

那也太窄了.我们说的"接口"是调用方为了用对这个模块而需要知道的**所有东西**,类型签名算,但调用顺序,错误模式,配置,性能预期这些都算,不光是那几个类型.

**3. 用“边界”这个词**

"边界"这个词和`DDD(领域驱动设计)`中的`限界上下文(bounded context)`概念容易混淆.我们说**接缝**或**接口**就好.

## 更深入的探讨

- **如何根据已有的依赖关系来深化一组模块**:请参阅 [DEEPENING](./modules/DEEPENING.md) 文档,了解依赖分哪几类,接缝怎么管以及「替换而非分层」的测试策略.
- **想探索一个接口还有没有别的设计方式？**:请参阅 [DESIGN-IT-TWICE](./modules/DESIGN-IT-TWICE.md) 文档,做法是:并行拉起多个子代理,让它们各自用完全不同的思路设计同一个接口,然后从**深度**(杠杆有多高),**局部性**(改动集中在一个地方还是到处散落),**接缝位置**(接口搁在哪儿)三个角度横向对比.
