用户发起了**会话复盘**。你的任务是帮 Agent 优化**工作环境**（包括规则、工具和检查流程），让后面的任务少走弯路。

## 执行步骤

1. 用 Skill 工具加载 `express-agents`，参考给 Agent 写文档的规范。

2. 读取用户指定会话的原始记录（必要时翻一下本地日志）。用户没特别指定的话，直接复盘当前这场。

3. 从下面几个方面排查改进项：

- **文件导航**：Agent 找文件顺手吗？文件之间有没有没写明的依赖？加个**上下文指针**会不会更容易找？_适用场景_：Agent 花了很久才找到所需信息。
- **自动检查**：有没有能帮 Agent 拦截错误的自动检查？比如代码风格检查（lint）、类型检查、单元测试。先看仓库现有的检查命令（查看 `package.json` 或构建工具里的 `lint`/`check`/`test` 脚本，以及 CI 工作流配置）。要是已有检查原本存在，只是没接进流程或者已经失效，把这个列为改进项，别急着重新造一套。只要项目没有 pre-commit 钩子，CI 也没有运行 lint、类型检查或测试的任务，就算缺少护栏，这本身就是一个改进项；不做代码检查绝不是理所当然的默认状态，而是在白白漏掉排查机会。_适用场景_：Agent 犯了自动检查本该拦截的错，或者仓库压根没有配置护栏保护。
- **编码规范**：该不该给**审查代码的 Agent** 加条新规矩？现有规则要不要删掉或写明白点？先看这类问题能不能靠工具拦截：只要是**死板的机械规则**（比如固定的代码写法、禁止调用的接口、导包格式、文件存放目录），就直接上自动化工具检查，别写进文档指望人脑去记。在项目 linter 里加条规则、加个 pre-commit 钩子、或者加进 CI 都行，挑成本最低的来。默认先建自动化检查，别只写文档规则；只有自动化工具无法判断的**主观判断题**（比如跨文件风格统一、代码设计是否自然），才写进 `CODING_STANDARDS.md`。_适用场景_：代码审查时漏掉了本该发现的问题。
- **全局 AGENTS.md 瘦身**：有些指令是不是该挪进具体编码规范，或者做成自动检查？_适用场景_：项目或全局的 `AGENTS.md` 写得太长太臃肿。
- **工具调用开销**：Agent 有没有跑过特别耗费 token、本来能更精简的工具调用？自定义工具（CLI、MCP）是不是消耗 token 过多？_适用场景_：Agent 调工具的开销明显偏大。
- **清理废话指令**：找出引导文件里那些写不写都一样的废话指令。_适用场景_：引导文件太长，读着费劲。
- **信息获取**：看看能不能给 Agent 提供更多有用信息。比如把本地服务的实时日志打出来，或者给第三方服务开个只读权限。_适用场景_：Agent 因为拿不到关键信息被卡住了。

4. 把找出来的优化项按严重程度排好，列给用户看。

## 参考说明

### 写代码与代码审查的分工

写代码和做审查要分开：

写代码的 Agent **上下文最吃紧**：它要查代码、写业务逻辑、还要排查报错。

审查代码的 Agent **上下文最轻省**：它主要看改动差异（diff），通常不用大范围探索代码，也不需要写代码或排查报错。

因此，**代码规不规范由审查 Agent 负责把关，不用让写代码的 Agent 分心记这些。**

### 常见项目文件职责

- `CLAUDE.md` / `AGENTS.md`：只要 Agent 在这个仓库干活，就会一直加载这些文件。所以里面能不写就不写，尽量只留指向其他文件的上下文指针。
- `CODING_STANDARDS.md`：这份文件只在审查代码时读，写代码时不读。如果规范超过 1000 行，就把具体规则拆到单独的文档里，这里只留指针。
- 文档文件（Docs）：作为补充参考资料，通过其他文件指过来。写新文档前，先看看项目里是不是已经有了。
- Skill：用来放那些按需加载的参考材料（其 description 会进入上下文充当指针），或者作为用户直接调用的命令。写法按 `express-agents` 的规范来。
