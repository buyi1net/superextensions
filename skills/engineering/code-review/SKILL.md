对用户指定的某个参照点（比如一个 commit、分支或标签）到当前代码之间的所有改动，做一次双维度交叉评审：

- **规格说明（Spec）**：代码有没有老老实实把规格说明或**工单（Tickets）**里要求的东西给实现了？
- **编码规范（Standards）**：代码写得规不规范？有没有遵守项目里写明的编码规范？

两个维度分别由**并行子代理**评审，因此它们不会污染彼此的上下文，最后由本 skill 汇总结果。

## 执行流程

### 第一步：先定下来“从哪看起”

用户指定的 commit SHA、分支、tag、`main`、`HEAD~5` 等，就是参照点。如果用户没说清楚，你就问他。

参照点定下来之后，固定使用这条 `git diff` 命令：`git diff <参照点>...HEAD`（这里用三个点表示比较基准为合并基准）。同时再用 `git log <参照点>..HEAD --oneline` 拉一份提交列表。

继续之前，先确认两件事：

1. 确认参照点是有效的（用 `git rev-parse` 能解析出来），
2. 确认参照点确实有改动（diff 不为空）。

如果参照点无效或者压根没改动，这里就直接报错停下，别等到两个子代理跑起来了才发现问题。

### 第二步：找到规格说明(Spec)

按照下面这个顺序来找规格说明：

1. 先看提交记录里有没有引用 issue 编号，比如 `#123`、`Closes #45` 这种。如果有，就通过 `docs/agents/issue-tracker.md` 里配置的方式去把内容拉回来。
2. 如果用户直接传了一个文件路径，就用那个。
3. 如果上面都没有，就去 docs/、specs/ 或者 .scratch/ 目录下找找有没有和当前分支名或功能名匹配的规格文件。
4. 都找不到时，询问规格说明在哪里。如果用户确认没有，那负责“规格维度”的那个子代理就跳过，并在报告里写一句“没有可用的规格说明”。

### 第三步：找到编码规范(Standards)

先去项目里找那些记录了“代码该怎么写”的文件，比如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了项目自己的规范之外，“标准维度”还会自带一套兜底的检查清单：就是 Fowler 在《重构》第 3 章里列的那组代码坏味道(Code Smell)。就算你的项目里什么规范都没写，这套清单照样能用。

但这里有两个原则：

- **项目规范优先**：如果项目规范里明确认可的做法，那就算兜底清单把它标记为**问题**，也要以项目规范为准，不上报这个。
- **代码坏味道(Code Smell)只是判断，不是硬性违规**：每个代码坏味道都只是打个标签说“这里可能有问题”，而不是“这里绝对错了”。另外，那些已经有工具（比如 ESLint）自动在查的规则，这里就不再重复报了。

每个代码坏味道都按照“它是什么 → 怎么改”理解，再对照 diff 来判断：

- **Mysterious Name（神秘命名）**：函数、变量或类型的名字看不出它做什么、存什么。→ 重命名；如果怎么起都觉得不对劲，那说明设计本身就含糊。
- **Duplicated Code（重复代码）**：同样的逻辑在改动里出现了多次。→ 提取成公共函数，让其可以多处复用。
- **Feature Envy（依恋情结）**：一个方法访问别的对象的数据多于访问自己的数据。→ 把方法移到它主要使用的数据所属对象上。
- **Data Clumps（数据抱团）**：同样的几个字段或参数总是一起传递，说明它们可能应该组成一个类型。→ 把它们打包成一个独立的类型，统一传递。
- **Primitive Obsession（原始类型滥用）**：用原始类型或字符串表示本该有独立类型的领域概念→ 为该概念单独建一个类型。
- **Repeated Switches（重复分支）**：对同一个类型，在改动里多处出现相同的 `switch` 或 `if` 判断链。→ 改用多态，或者用一张统一的映射表。
- **Shotgun Surgery（散弹式修改）**：一个逻辑变更要同时在很多文件里到处修改。→ 把相关逻辑集中到一个模块里。
- **Divergent Change（发散式变更）**：同一个文件或模块因为多个无关原因被反复修改。→ 拆开，让每个模块只因为一种理由而变动。
- **Speculative Generality（过度设计）**：为当前规格里压根没要求的需求提前加了抽象、参数、钩子。→ 删掉，等真有需求了再加回来。
- **Message Chains（过长消息链）**：代码里有一长串 `a.b().c().d()` 的链式调用，过于依赖内部结构。→ 在第一个对象上封装一个方法，把整条链藏起来。
- **Middle Man（中间人）**：某个类或函数啥也不干，基本只负责转发。→ 删除它，直接调用真正的目标。
- **Refused Bequest（拒绝继承）**：子类或实现者继承、实现了一大堆内容，但大部分都覆盖掉、忽略了或没用上。→ 放弃继承，改用组合。
- **Missing Why Comment（缺失意图注释）**：代码会让读者问「为什么不直接 X」，改动里却没有注释回答。→ 补一条只写「为什么」的注释；报告时必须写出读者会问的那个问题，写不出不算发现。
- **Noisy Comment（噪声注释）**：注释复述代码、解释语法本身，或是无契约信息的模板化 docstring。→ 删掉；判据是删后读者不损失信息，拿不准的不上报。

### 第四步：同时派出两个子代理

**编码规范(Standards)子代理**的提示词必须包含：

- 完整 diff 命令和提交列表；
- 以及将第三步找到的规范来源文件清单和完整代码坏味道清单逐项粘贴进提示词。子代理不会自动看到第三步内容，不能只写“见上文”。
- 指令摘要：“按文件和 diff 区块来汇报：(a)改动中每处违反项目规范的地方，要引用规范来源（哪个文件的哪条规则）；(b)你看到的任何代码坏味道，指出是哪种代码坏味道，并引用出问题的代码片段。要把硬性违规和判断性意见区分开：违反项目规范算硬性违规，但代码坏味道只是判断性意见，而且项目规范优先于代码坏味道清单。工具已经能自动查的规则就别报了。全文不超过 400 字。”

**规格说明(Spec)子代理**的提示词必须包含：

- diff 命令和提交列表；
- 规格说明的路径，或已经取得的规格内容；
- 指令摘要：“汇报：(a)规格说明里要求了但没实现或只做了一半的；(b)改动里做了但规格说明没要求的东西（也就是超范围了）；(c)看着实现了但实现方式可能有误的地方。每个发现都要引用规格说明原文。全文不超过 400 字。”

如果没找到规格说明，就跳过“规格维度”的子代理，并在最终报告里注明这一点。

### 第五步：汇总结果

把两份报告分别放在 `## Standards` 和 `## Spec` 两个标题下面，原文贴过来就行，稍微顺顺格式也可以。**不要把两份报告合并**，也不要重新排序，这两个维度本来就是故意分开的（原因见下面那段）。

最后用一句话收尾：每个维度各发现了多少问题，以及每个维度里最严重的一条是什么（如果有的话）。**不要跨维度选一个“最严重的”**：强行排个第一第二，正是分两个维度要避免的事情。

## 为什么要分两个维度

同一份代码完全可能在一条轴过关、在另一条轴失败：

- 代码写的完全遵守规范，但做出来的东西是错的→ **规范轴（Standards）过关，规格轴（Spec）失败。**
- 代码确实把需求全部实现了，但完全不按项目规范来写 → **规格轴（Spec）过关，规范轴（Standards）失败。**

分开汇报，就是为了防止一个好结果把另一个问题给盖过去。各自看清楚，互不遮掩。
