---
name: code-review
description: 分别检查代码变更是否符合规范和规格.当用户要求评审分支,PR,进行中的改动,或说 review since X 时使用.
---

按用户指定的提交范围,暂存区或当前工作区,检查这次任务的改动:需求有没有做完整,代码有没有遵守适用规范.

评审拆成两条互相独立的正交轴:

* **规格说明(Spec)**:代码有没有老老实实把规格说明或**工单(Tickets)**里要求的东西实现正确,实现完整?
* **编码规范(Standards)**:代码写得规不规范?有没有遵守项目里明文约定的编码规范与设计原则?

**两条轴必须独立评审,分开汇报**:
同一份代码完全可能在一条轴过关,在另一条轴失败(比如:代码结构极度严谨,但做出来的功能是错的;或者需求全跑通了,但到处硬编码,违背规范).分开汇报,为的就是防止一个好结果把另一个问题盖过去,各自看清楚,互不遮掩.

Standards 轴细分为第三步的四个检查组,Spec 轴与整个 Standards 轴并列.检查组用来划清职责,子代理负责具体执行.各项检查可以并行展开,最后由本 skill 汇总结果.

---

## 执行流程

### 第一步: 确定评审范围与目标版本

先看用户要审什么,以及交接里有没有明确范围.实现完成后,默认看这次任务在当前工作区的最终结果:已经提交的改动,以及后来暂存,没暂存和新建的内容,都算在内.用户明确只审提交,暂存区或未提交变化,就按指令来.比较起点从交接,当前会话和提交记录里找,别把整条分支的历史都算成这次任务.

1. **已提交改动**:先定比较起点和目标提交.用户没指定目标,才用 `HEAD`.比较分支用 `git diff <参照点>...<目标提交>`,明确指定了两端点就用 `git diff <起点> <目标提交>`,提交列表也按这个范围取.只审一个普通提交,就和它的父提交比较;根提交按新增内容看;合并提交按请求选父提交或分支基准.读文件也要读目标提交里的版本,后来的提交不算进来.
2. **当前工作区**:从确定的任务比较起点执行 `git diff <比较起点> --`,看已跟踪文件最后改成了什么,再用 `git ls-files --others --exclude-standard` 找出未跟踪文件.用户只审未提交变化,或者已经确认这次任务还没提交过,才默认从 `HEAD` 比.未跟踪文件要另外读或比较,普通 diff 为空也可能有新文件.
3. **暂存区**:用 `git diff --cached --`,读索引里的文件版本.没暂存的内容留在这次范围之外.
4. **组合改动**:用户给了分支等参照点,又要求包含本地改动,就从该参照点与 `HEAD` 的合并基准开始比;如果已知任务的起点提交,直接用它.从这个起点比较工作区的最终结果,再补未跟踪文件.提交,暂存,未暂存的差异不能简单相加,有些修改会重复,有些会互相抵消.

已有的提交引用先用 `git rev-parse` 确认有效.没有 `HEAD` 的新仓库,按选定范围和目标版本中的任务文件检查新增内容,比较起点记为「无历史基线」;不为评审自动初始化仓库.暂存区看索引,提交评审看目标提交,不能拿工作区正文代替其他版本.

把这次新增,修改,删除和重命名的文件列清楚,整理好评审范围,比较起点,目标版本和查看方法,第四步统一交给子代理.只选这次任务的文件和相关改动区块,其他并行任务的改动不要混进来.从请求,交接和现场仍看不出比较起点或改动归属,再找用户问清,不能悄悄改用 `HEAD` 然后声称整项任务都审过了.

这些改动都没有,才说明没有可评审内容.之后用目标版本的完整文件统计行数,用 diff 找本次变化,需要了解关联代码再去读.评审中目标又改了,就复核受影响的文件;结论只对应实际看过的代码.

---

### 第二步: 找到规格说明(Spec)

已经交来的规格,工单或已明确的用户要求,先拿来用.需求就在当前对话里,注明来源即可,但还没确认的讨论建议不能算成要求.这些信息足够评审,就不用再找用户要一份单独的规格文件.

独立评审缺少任务依据时,按以下顺序找规格说明:

1. 先看提交记录里有没有引用 issue 编号(如 `#123`,`Closes #45`).如果有,就通过 `docs/agents/issue-tracker.md` 里配置的方式把内容拉回来.
2. 如果用户直接传了一个文件路径,就用那个文件.
3. 如果上面都没有,就去 `docs/`,`specs/` 或 `.scratch/` 目录下找找有没有和当前分支名或功能名匹配的规格文件.
4. 都找不到时,询问规格说明在哪里.如果用户确认没有,就跳过负责规格检查的子代理,并在报告里明确记录「没有可用的规格说明」.

---

### 第三步: 准备规范检查(Standards)

先把这次适用的编码规范找齐.交接里给过的来源先用,再从项目入口和当前生效的规则里补查(如 `CODING_STANDARDS.md`,`CONTRIBUTING.md` 或项目引用的规范).用户直接发起评审也照这样找,不要求先走某个实现流程.交接不是全部依据,发现漏项要补上;确实读不到的来源,说明缺了哪部分,不要把没检查写成通过.

用 Skill 工具加载 `codebase-design`,结合这次改动使用「简洁设计」「源码组织与复用」,以及相关的接口,深化和可测试性原则.没动目录也可能有设计问题,同样要看.

规范文件里如果还带着实现或提交步骤,这里只取评审需要的规则,不顺着执行那些流程.评审检查最终改动是否符合这些要求,不默认追查写前加载,搜索或查看文件的顺序.用户明确要求检查实现过程,再按约定范围核对已有记录,单独说明发现和缺少的证据.普通代码评审不用索取写前记录,也不用逐项报告「无法核实是否加载过 skill」.

把检查内容按下面四个检查组整理好,第四步再分给子代理检查.各组里也放了代码坏味道(Code Smell)作为兜底线索,以 Fowler《重构》第 3 章为参考,并补充了注释检查.项目没写规范,这些线索照样能用.

坏味道放在哪组,表示主要由这组主动检查,不表示它只能属于这一组.比如散弹式修改可能由重复逻辑造成,设计组和复用组会碰到同一个问题.必要的重叠阅读可以保留,已有证据和结论按第四步交接复用.

但这里有两个原则:

- **项目规范优先**:如果项目规范里明确认可某种做法,即使兜底清单将其标记为**问题**,也要以项目规范为准,不上报此项.
- **代码坏味道(Code Smell)只是判断,不是硬性违规**:每个代码坏味道都只是打个标签提醒「这里可能有问题」,而不是「这里绝对错了」.

有现成的工具结果,先看它查的是不是这次的文件,版本和检查项,再看实际结果.都对得上就直接用,同一个问题报一次,证据留着.项目配过工具,不代表这次已经检查过;缺少有效结果,就按项目条件跑已有命令或人工检查,查不到的部分说清楚.不要求安装新工具,也不把工具缺失本身当成代码缺陷.

读之前先看文件大小,再用搜索,符号和局部代码逐步了解,不要一次读入一整组大文件.行数只能提醒体量,不能保证内容一定装得进上下文.

#### 一、设计与源码组织

结合设计原则,看这次实现是否足够简单,职责和接口是否清楚,代码是否方便测试.源码组织与文件体量重点看以下内容:

- 这次新建,修改或重命名的手写源码,测试和脚本,都看目标版本完整文件的行数,同时记下比较起点有多少行;新文件的起点记零.删掉的文件看关联影响,不再算最终行数.默认按物理行数统计,注释和空行也算,文件末尾的换行不额外算一行.
- 项目已有统计办法或阈值,就按项目的来,注明用了什么办法.项目没约定,超过 800 行就多看一下结构.这是提醒,不是硬上限;文件短也照样要看职责放得合不合适.
- 按前面读到的设计原则,结合相关目录,实现和调用关系,看新增代码和共享代码放得对不对.有问题就指出位置,这次怎么改的,以及给理解或修改带来了什么麻烦.仅仅不符合自己喜欢的目录模板,不能算问题.
- 看有没有按职责自然分开的地方.拆开以后,改一处能不能少读无关代码?会不会反而多一层目录,多几次跳转,增加依赖?文件变短只是结果之一,不能单凭它断言拆得好.
- 判断时带上项目现有结构和框架要求.项目没要求额外的组织说明或逐文件清单,这里也不要求补;项目本来有要求的,仍然照办.
- 超过提醒值但适合保留,就说清哪些逻辑需要一起理解,拆开又会多出哪些依赖或跳转.光写「职责单一」不够,但光凭行数超标也不能要求返工.历史长文件这次只改局部,没有新增职责或明显增加理解负担,说明体量与本次影响就够了,不用另做整文件拆分论证.
- 生成代码,第三方内容和纯数据资源,确认来源后注明,不按手写实现要求拆分.文件很长本身不能证明它是生成的.

相关的代码坏味道如下.每条按「它是什么 → 怎么改」理解,结合这次改动判断:

- **Feature Envy(依恋情结)**:一个方法访问别的对象的数据多于访问自己的数据.→ 把方法移到它主要使用的数据所属对象上.
- **Data Clumps(数据抱团)**:同样的几个字段或参数总是一起传递,说明它们可能应该组成一个类型.→ 把它们打包成一个独立的类型,统一传递.
- **Primitive Obsession(原始类型滥用)**:用原始类型或字符串表示本该有独立类型的领域概念.→ 为该概念单独建一个类型.
- **Shotgun Surgery(散弹式修改)**:一个逻辑变更要同时在很多文件里到处修改.→ 把相关逻辑集中到一个模块里.
- **Divergent Change(发散式变更)**:同一个文件或模块因为多个无关原因被反复修改.→ 拆开,让每个模块只因为一种理由而变动.
- **Speculative Generality(过度设计)**:为当前规格里压根没要求的需求提前加了抽象,参数,钩子.→ 删掉,等真有需求了再加回来.
- **Message Chains(过长消息链)**:代码里有一长串 `a.b().c().d()` 的链式调用,过于依赖内部结构.→ 在第一个对象上封装一个方法,把整条链藏起来.
- **Middle Man(中间人)**:某个类或函数啥也不干,基本只负责转发.→ 删除它,直接调用真正的目标.
- **Refused Bequest(拒绝继承)**:子类或实现者继承,实现了一大堆内容,但大部分都覆盖掉,忽略了或没用上.→ 放弃继承,改用组合.

#### 二、死代码

检查本次变化留下的闲置代码,也看有没有误删仍有用途的代码:

- 看这次加的 import,变量,函数等代码,最后有没有用上.已有工具结果符合前面说的条件,就直接用.
- 顺着这次变化往回找,尤其是删掉或换掉的调用,入口和导出,看看旧实现和只给它用的辅助代码还要不要留,别漏了没改过的文件.这次改过的校验或状态转换,也可能让旧分支失去用途.追查跟着这次变化走,不顺便清理整个仓库的历史旧代码.
- 按本次适用的清理规范核实实际用途,同时看有没有删掉仍需保留的代码.要判断的是残留和误删,不用追查实现者之前执行过哪些搜索命令.
- 报问题要交代位置和原因:是这次加了没用,还是哪项改动让旧代码没用了?查过哪些入口,还有什么没确定?工具说没用,实际入口却还在用,先把差异查清楚.
- 确认有本次该处理的问题,就交给实现方收尾.无关历史问题另列,证据还不够的标成待核实,别把猜测写成删除要求.

#### 三、重复逻辑与复用

围绕这次新增或替换的能力,找项目里有没有相关实现,没改过的文件也要考虑.沿着能力,入口和调用关系搜索,按前面读到的复用原则判断:

- **Duplicated Code(重复逻辑)**:看不同位置实现的是不是同一条规则.确实重复了,先看能不能用已有实现,再考虑提取共享部分;只是长得像,实际上需要各自变化的代码,可以继续分开.
- **Repeated Switches(重复分支)**:对同一个类型,在改动里多处出现相同的 `switch` 或 `if` 判断链.→ 改用多态,或者用一张统一的映射表.
- 看这次共享或提取的逻辑有没有把需要各自变化的行为绑在一起.复用之后调用是否更简单,还是多了许多模式参数和业务分支?
- 报问题时把相关位置,共同规则,行为差异和复用会带来的影响说清楚.是否重复要看业务含义,输入输出,错误处理和副作用,不能只比文本相似度.

#### 四、编码与项目规范

按本次适用的规范,检查命名,注释,编码约定和修改范围.项目还有其他要求,也要分到对应检查组里检查,不能因为没出现在这份清单里就漏掉.这一组的兜底线索如下:

- **Mysterious Name(神秘命名)**:函数,变量或类型的名字看不出它做什么,存什么.→ 重命名;如果怎么起都觉得不对劲,那说明设计本身就含糊.
- **Missing Why Comment(缺失意图注释)**:代码会让读者问「为什么不直接 X」,改动里却没有注释回答.→ 补一条只写「为什么」的注释;报告时必须写出读者会问的那个问题,写不出不算发现.
- **Noisy Comment(噪声注释)**:注释复述代码,解释语法本身,或是无契约信息的模板化 docstring.→ 删掉;判据是删后读者不损失信息,拿不准的不上报.

源码组织与文件体量,死代码,重复逻辑是重点检查项,整次评审都要覆盖到,其他适用要求也照样检查.

### 第四步: 分配检查任务

按第三步的四个检查组分配规范检查.分配策略遵循以下原则:

- **规格检查独立派出**:规格说明检查始终由独立的子代理负责,与规范子代理完全隔离.
- **死代码与重复逻辑优先独立**:这两项往往要沿本次变化跨文件追查,必要时在全仓搜索关联入口和实现,上下文开销大,优先分别交由独立子代理;若改动极小,关联范围清晰,可与局部检查合并.
- **支持弹性兼任与分担**:一个子代理可以兼任多个轻量检查组;同一个大组需要多人分担时,划清负责的模块范围.能并行就并行,并发受限就分批推进.

给参与评审的子代理同一份评审范围,比较起点,目标版本,文件清单和查看方法,包括实际使用的 diff 命令.有相关提交,再附提交列表.各自需要的代码按需读,不把整仓内容都塞进子代理的上下文.

派活时说清每个子代理负责哪些检查,哪些已有其他代理负责.即使按代码范围分工,追查仍要跟着调用和依赖走,需要时可以读其他模块和未修改的文件.

遇到职责交叉的线索,发现者把位置,已有证据和待确认点回传给主 Agent.主 Agent 先对照已有报告:查清了就复用结论;还没查清,就指定一位负责相关检查的子代理补查,其他人补充已有证据.负责人把核实结果交回主 Agent,只补缺口或新疑点,不用因为换了负责人就从头再查.

**编码规范(Standards)子代理**拿到自己负责部分的完整检查项,以及相关的规范来源,可访问路径和适用部分.它读不到文件,就把需要的原文交给它.共同的判断原则,相关验证结果和这些结果检查过的范围,也一起带上.只写 skill 名或「见上文」不够,独立子代理未必拿得到主 Agent 的上下文.给它以下指令:

> 按分配给你的检查组,范围和适用规范检查改动结果,也留意有证据的代码坏味道.回传时注明所属检查组,交代自己负责的部分查到了什么,不适用的说明原因,证据不够的说明缺口.
>
> 有问题就给位置,证据,跟这次任务的关系和建议,引用了哪条规则也说清楚.违反明确规则的,和设计上有待商量的,要让读者分得清;查不清的就说查不清.有效工具结果直接用,同一个问题报一次.
>
> 报告不设全文字数上限,每项说清楚即可,不用凑篇幅,也别丢掉必要发现和证据.负责的部分没有发现问题,用一句话说明即可,不要求每个函数,每个文件都生成一份报告.回传发现,必要证据,检查范围和缺口,不用附整段源码或完整搜索日志.
>
> 这次交付评审报告,不自行改代码或运行实现流程;写前步骤的执行记录不在默认检查范围内.

**规格说明(Spec)子代理**的提示词必须包含:

- 上述共同的范围和查看材料;
- 规格说明的路径,或已经取得的规格内容;
- 指令摘要:「汇报:(a) 规格说明里要求了但没实现或只做了一半的;(b) 改动里做了但规格说明没要求的东西(也就是超范围了);(c) 看着实现了但实现方式可能有误的地方.每个发现都要引用规格说明原文.按实际发现写清楚,保留必要证据;检查不完整的说明缺口.」

是否跳过规格检查,按第二步的结论处理;跳过时在最终报告里写明未评审及原因.

---

### 第五步: 汇总结果

先按检查组合并子代理回传的结果,对照分工看四个组有没有漏查,职责交叉的线索是否已有结论.缺了哪部分就按第四步安排补查,确实查不到的写清楚.主 Agent 根据报告和必要的代码核对疑点与冲突,不用把每个检查组的工作完整重做一遍.

最终报告按两条评审轴组织:四个规范检查组的结果都放进 `## Standards`,规格检查的结果放进 `## Spec`.无论派了几个子代理,都按这个结构汇总.报告的完整版式在 [REPORT-TEMPLATE](./modules/REPORT-TEMPLATE.md):汇总时读它,按实际检查结果填写,没有对应内容的占位项可以删去.

汇总前先看证据靠不靠谱,问题是不是这次任务造成的.同一个具体问题涉及多个检查组或坏味道,就在所属评审轴里合成一条发现,保留各方证据和相关标签;同一文件里的不同问题,或只是坏味道标签相同,仍然分别报告.确认是误报就去掉,说得不准确就改;不用为了原文贴回而保留错误结论,也不能为了缩短报告删掉必要发现和证据.同一问题同时影响规范和规格,两条评审轴分别交代各自的依据和影响,可以相互引用.

Standards 结果按下面三类呈现:

- **本次需修正的问题**:有依据的规范违反,或有明确维护影响的本次结构问题.
- **核查结论**:各检查组的实际检查范围与结论,以及超过提醒值但有依据保留的文件.未完成或不适用的部分说明原因.
- **待核实或后续事项**:证据不足,无关历史问题和需要独立任务处理的改进机会.

只有行数提醒,还没证实的怀疑,或者与本次无关的旧问题,不因此要求这次返工.发现确实需要改更大范围,或会碰到既定约束,按总纲处理,这里不再复制确认条款.

最后用一句话收尾:Standards 和 Spec 各确认了多少问题,以及各自最严重的一条是什么(如果有的话).部分完成的注明检查范围和缺口,未评审的写明原因,不能把未评审写成「零问题」.**不要跨这两组结果选一个「最严重的」**:强行排个第一第二,正是把规范和规格分开要避免的事情.

评审交出报告后,由原实现任务处理其中的明确问题,再把修正交回来复核.独立的只读评审到报告为止.问题解决了就停,不能因为设计还能继续优化,就一直改下去.
