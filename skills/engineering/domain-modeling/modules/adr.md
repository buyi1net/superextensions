# ADR 格式

ADR（architecture decision record）存放在 `docs/adr/` 目录中（只有需要时创建），使用顺序编号：`0001-<决策名称>.md`、`0002-<决策名称>.md`，以此类推。

## 模板

```md
# {决策的简短标题}

{用 1–3 句话说明背景、决定和作出该决定的原因。}
```

就这么多。ADR 可以只有一段话。它的价值在于记录**做过什么决定**以及**为什么这样做**，而不是填满各种表格。

## 可选

只有确实有必要时才加。大多数 ADR 用不上这些。

- **状态**(`proposed | accepted | deprecated | superseded by ADR-NNNN`)：日后重新考虑决策时非常有用。
- **考虑过的方案**(`Considered Options`)：只有被否掉的选项值得以后参考时才写。
- **后果**(`Consequences`)：只有当某些影响不写出来别人想不到时，才需要专门提一下。

## 编号

扫描对应的 `docs/adr/` 目录，找到当前最大编号，然后加 1。

## 什么时候该写 ADR

只有以下三条**同时满足**时，才提议创建 ADR：

1. **难以逆转**：事后反悔的代价不小
2. **脱离上下文则令人费解**：未来有人看到代码会纳闷“当时是怎么想的？”
3. **经过真正的权衡**：存在其他可行方案，基于具体理由选择了当前方案

总之，容易推翻的决策，不用记，反正还会改。不让人意外的，也不用记，没人会好奇。没有真正替代方案的，更不用记，无非是“做了显而易见的选择”。三条全占，再写 ADR。

## 哪些东西值得写进 ADR

- **项目整体架构**：比如"所有代码放在同一个仓库里"，或者"数据写入用事件溯源，读取从 Postgres 查"。这类决策影响全局，换起来很麻烦。
- **模块之间怎么通信**：比如"订单模块和计费模块不发同步 HTTP 请求，而是通过发消息来解耦"。这个决定了模块间的耦合程度，值得记。
- **选了就很难换的技术**：比如数据库、消息队列、认证服务、部署平台。不是每个第三方库都要记，只有那种换掉要花好几个月的东西，才值得记录为什么选它。
- **什么归谁管**：比如"客户数据只有客户模块能改，其他模块只能拿 ID 来查"。明确**不能做什么**，和明确**应该做什么**一样重要。
- **故意没按常规来的地方**：比如"一般这种场景大家都用 ORM，但我们手写 SQL，因为 X 原因"。不记下来，后面的人会觉得你写错了，帮你"修正"回来，把你故意的设计给改坏。
- **代码里看不出来的限制**：比如"合规原因不能用 AWS"，或者"对方接口要求必须在 200ms 内返回"。这些东西代码本身看不出来，但影响了很多设计决定。
- **为什么否掉了其他方案**：比如"考虑过 GraphQL，但因为某些原因最后选了 REST"。不记下来，半年后又会有人重新提一遍 GraphQL，你来来回回解释。
