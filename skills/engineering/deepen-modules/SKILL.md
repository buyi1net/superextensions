# 深化模块

找出架构上的摩擦，挖出**深化机会(deepening opportunity)**：把浅模块改造成深模块的重构。目标是可测试性和 AI 导航性。

本 skill 靠两样东西打底：项目自己的领域模型，一套共享的设计词汇。

- 调用 `codebase-design`，拿到架构词汇表（**模块(module)**、**接口(interface)**、**深度(depth)**、**接缝(seam)**、**适配器(adapter)**、**杠杆效应(leverage)**、**局部性(locality)**）和配套原则（删除测试、「接口就是测试面」、「一个适配器 = 假想接缝，两个 = 真接缝」）。后面每条建议都用这套术语说话，别换成「组件」「服务」「API」「边界」。
- 好接缝的名字要从 `GLOSSARY.md` 的领域语言里找；`docs/adr/` 里的 ADR 记的是已经拍板的决策，本 skill 不翻这个旧账。

## 流程

### 1. 探索

**先圈定范围再扫：YAGNI。** 深化一个模块，图的是以后改它更省事，所以近期常改的代码优先看。先定好看哪块，再动手扫：

- 用户点了方向（某个模块、某个子系统、某处痛点），就照着这块看，下面找热点那步就省了。
- 没指方向，就用 `git log --oneline` 往回翻一段提交历史，找代码库的热点：哪些文件、哪些区域总在提交里冒头，就先看哪里。要是改动很散、看不出热点，就把范围放大。

动手前先读 `GLOSSARY.md`，再把目标区域涉及的所有 ADR 读一遍。

然后派一个子代理去逛代码库。别拿死板清单挨个打勾，凭手感逛，撞到摩擦就记下来：

- 理解一个概念，要在一堆小模块之间来回跳？
- 哪里是**浅模块**：接口复杂得几乎跟实现一样？
- 哪里为了可测试性抽出了纯函数，但真正的 bug 藏在调用方式里（没有**局部性**）？
- 哪里有紧耦合的模块从接缝往外漏？
- 代码库哪些部分没有测试，或者隔着现有接口很难测？

凡是看着像浅模块的，都拿**删除测试**验一验：假想删掉它，复杂度是能收拢到一处，还是只是挪个地方？能收拢，说明这些复杂度背后有个该收留它们的深模块，并进去就是一次真正的深化，值得记进候选；只是挪地方的话，复杂度换个地方继续散着，这活就白干了。

### 2. 用 HTML 报告摆出候选

报告是一个自包含的 HTML 文件，写进系统临时目录，仓库里一个字节都不留。临时目录看 `$TMPDIR` 环境变量，没设就用 `/tmp`（Windows 是 `%TEMP%`）；文件名带时间戳（`architecture-review-<timestamp>.html`），每次运行各写各的。写完替用户打开（Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`），绝对路径也告诉用户。

布局和样式用 **Tailwind（CDN 引入）**，图用 **Mermaid（CDN 引入）**，但别把宝全押在 Mermaid 上：关系是图状的（调用图、依赖、时序）就用 Mermaid；要编辑风的图（体量图、横截面、坍缩动画），就手写 div/SVG。每个候选配一张**前后对比图**，视觉优先。

每个候选画成一张卡片：

- **文件**：涉及哪些文件/模块
- **问题**：当前架构为什么造成摩擦
- **方案**：用大白话描述会改什么
- **收益**：讲清局部性和杠杆效应上的赚头，顺带说测试会怎么变好
- **前后对比图**：并排摆放、手工绘制，画出浅在哪里、深化后又是什么样
- **推荐强度**：`Strong`（强烈推荐）、`Worth exploring`（值得探索）、`Speculative`（观望）三选一，渲染成徽章

报告结尾加一个**首推**小节：你最推荐先动哪个候选，一句话说为什么。

**领域用 `GLOSSARY.md` 的词汇，架构用 `codebase-design` 的词汇。** 如果 `GLOSSARY.md` 定义了「订单(Order)」，就说「订单接入模块」，不说「FooBarHandler」，也不说「订单服务」。

**ADR 冲突**：候选撞上现有 ADR 时，只有摩擦真实到值得重开这条 ADR，才摆出来说。在卡片里用醒目的警告框标出来（比如：_「与 ADR-0007 冲突，但值得重开，因为……」_）。ADR 已经否掉的、只在理论上成立的重构，别一个个翻出来列。

完整的 HTML 脚手架、图示模式和样式指南见 [HTML-REPORT.md](./modules/HTML-REPORT.md)。

报告里先不提接口设计。文件写完就问用户：「这些候选里，你想深挖哪一个？」

### 3. 追问循环

一旦用户选定某个候选方案，就调用 `grilling`，陪用户走一遍决策树：理清约束条件、依赖关系、深化后模块长什么样、接缝后面藏着什么、哪些测试还能跑通。决策过程中冒出的事项，当场就落进文件；调用 `domain-modeling`，随时让领域模型跟得上最新进展：

- **深化后的模块用了 `GLOSSARY.md` 里没有的概念来命名？** 把这个概念补进去。文件要是还没建，就按 `domain-modeling` 的约定建一个。
- **聊着聊着把某个模糊的说法给敲定了？** 立马更新 `GLOSSARY.md`。
- **用户因为某个硬理由把这个方案否了？** 主动问一句要不要记成 ADR，可以这么说：「要我把这条记下来吗？以后做架构评审时，省得别人再提一遍。」但这个理由得是真的值得后人知道，才记；临时性的（比如「现在顾不上」）或不说也明白的，就算了。
- **想给深化后的模块另找接口方案？** 调用 `codebase-design`，用它的「Design It Twice」模式：并行拉起多个子代理，给每个发不同的设计约束，各出一版接口设计。
