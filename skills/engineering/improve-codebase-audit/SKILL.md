# 项目体检

找出项目现在有什么，哪里已经妨碍理解或修改。默认只读，交付一份 HTML 报告；不直接改业务代码，也不替用户决定是否立项。

开始工作前，用 Skill 工具加载 `codebase-design`,拿到架构词汇表和配套原则,后面每条建议都用这套术语说话,别换成「组件」「服务」「API」或「边界」;项目里的业务名词和代码标识按原名引用.

## 执行流程

### 第一步:明确检查规范

#### 源码组织与复用

完整阅读 `codebase-design` 的「源码组织与复用」章节,其中目录和文件怎么分、共享代码与实现复用、已有结构的延续、文件体量的控制是项目体检的重要环节，深浅模块、接口设计以及可测试性不在当前 Skill 的检查范围，它由 `improve-codebase-architecture` 负责。体检时围绕能力、入口和调用关系搜索未改文件；重复与复用的判据，也以这一章为准。

#### 死代码与遗留入口

存量体检遇到疑似死代码,按三步核验:

1. 除了普通引用,还要看配置注册,框架约定,动态调用,以及对外公开的使用约定.搜不到,只能说明没搜到引用;测试没覆盖,也不能证明它没用.
2. 顺着旧入口,导出,状态转换和被替换的调用往下找,看看旧实现和只给它用的辅助代码还要不要留.新增但未使用的 import,变量,函数也算在内.
3. 再确认兼容旧版本,迁移过渡,回滚和外部系统入口现在是否还需要.只要用途仍在,就不能算死代码.

三步没有闭合,保留代码,把疑点放进「待确认」,不成为发现.三步查实无用,才报告为发现,档位按第五步定义评:已查实且不误导不添成本的通常为低,仍在误导理解或抬高修改成本的按实际评档.报告发现时写清成因:新增未用,还是哪项改动让旧实现失效;查过哪些入口,还有什么没确定.没有和本次体检目标直接相关的历史疑点,只列证据和风险,不直接安排删除.

#### 测试护栏与工程入口

先找项目已有的构建,类型检查,测试,静态检查和本地启动命令,再看它们覆盖了哪些入口和失败路径.工具结果只有在文件,版本和检查项都对得上时才算本轮证据;项目配过工具不等于本轮已检查,缺工具本身不算代码缺陷.没有有效结果,就按项目条件跑已有命令或人工检查,查不到的部分说清缺口.

关键模块如果没有沿真实接口运行的验证路径,导致修改不敢动,无法回归,或者测试必须扒开实现才能运行,才形成发现.

#### 声明、规则与代码

读取项目已有的 `README.md`、`AGENTS.md`、`CLAUDE.md`、架构说明、`docs/`、ADR、`GLOSSARY.md` 和入口配置(存在才读).把文档写的分层,入口,命名,启动方式和约束,与目录,依赖方向,实际调用和脚本对照.

规则文件还要查失效路径,已经退役的机制,被上位规则覆盖的重复条款,以及实际不改变行为的句子.仍然有效的条款,写清它约束什么;只在有证据时建议补 why.

项目声明和实际代码不一致,就报告这件事;是否改文档还是改代码,留给后续任务决定.

#### 命名与注释

只查会让读者吃亏的三类:

- 神秘命名:函数,变量或类型的名字看不出它做什么,存什么.
- 缺失意图注释:代码会让读者问「为什么不直接 X」,却没有注释回答.报告时必须写出读者会问的那个问题,写不出不算发现.
- 噪声注释:注释复述代码,解释语法本身,或是无契约信息的模板化 docstring.判据是删后读者不损失信息;拿不准的不上报.

**完成条件**:五节判据都已明确,codebase-design 对应章节读完,本轮检查项和口径定下来.

### 第二步:圈定检查范围

先读用户要求,定出目标目录,模块,问题方向和排除项.没有指定范围时,小项目可以全库检查;大项目先做目录和入口盘点,再按模块,核心路径和高频变更区域分片.抽样范围要在报告里写明.

记录 `git rev-parse HEAD` 的完整提交号和短号,`git status --short`,检查范围,分片方式,项目已有命令和读取过的入口资料.没有 Git 或没有 `HEAD` 时,记录「无 Git 基线」和可读的版本信息,不初始化仓库.

**完成条件**:版本,范围,排除项,分片方式和可用检查命令都已确认并记录在案.

### 第三步:做代码库地图

按模块或目录建立分片.每片标出入口,主要文件,关键调用方,测试位置,外部依赖,规则资料和生成,第三方,数据文件.先看行数,声明,搜索结果和局部符号,再沿疑点读代码.

地图只服务本轮检查,不做逐文件百科.每片只保留能支撑判断的事实.

**完成条件**:每个分片都有检查者,范围,入口,验证路径和未检查区域;大文件已经安排分段阅读.

### 第四步:分片核验

可以并行派分片任务.每个任务包附上:本文件判据,版本,范围,回传格式(检查范围,已核验事实,发现,证据位置,待确认项,未检查部分),以及 [codebase-design](../codebase-design/SKILL.md)「源码组织与复用」章节的路径;子代理读不到就附原文.检查者回传结论,不自行改代码.

每片按适用项检查:源码组织与复用,死代码与遗留入口,测试护栏与工程入口,声明、规则与代码,命名与注释.没有发现也写清查过什么和结论是什么;同一根因覆盖多个位置时合并证据.

分片间撞到同一线索,发现者回传位置和已有证据;主代理对照已有报告,查清的复用结论,没查清的指定一位补查,不用从头再查.

**完成条件**:所有分片都有回传;每个检查项要么有发现和证据,要么有明确的零发现结论或未检查说明.

### 第五步:汇总发现

主代理先按分片清单核覆盖,再合并同一根因,处理相互矛盾的证据;确认是误报就去掉,说得不准确就改.每条发现都写清现状,影响,证据,待确认条件和处理方向.主代理只补查决定结论所需的缺口,不重做整库扫描.

严重程度三档,每条发现选一档,为什么选这档写进 reason:

- `high`(高):已经在把人带偏,或让修改变危险:声明与实际相反,关键路径没有回归安全网,改一处必须多点同改.
- `medium`(中):确实抬高理解或修改成本,但没到带偏的程度:体量与结构不匹配,命名含糊,轻度漂移.
- `low`(低):不构成实际额外成本,清理只为整洁:已查实的无用途代码.

两类损害都沾的,按总体损害评档,依据同样写进 reason.行数超过提醒值但结构合理,证据不足,或和本轮目标无关的历史问题,保留在核查结论或待确认项,不升级成强制返工.

**完成条件**:每条发现都有独立根因,可复核证据,严重程度和理由,处理方向;同一问题只出现一次.

### 第六步:生成报告

读取 [HTML-REPORT.md](./modules/HTML-REPORT.md),复制 [assets/report.html](./assets/report.html) 到项目 `temp/`,文件名使用 `codebase-audit-<timestamp>.html`,不覆盖旧报告.字段和范围口径按[报告内容](./modules/HTML-REPORT.md#报告内容)执行;数据序列化和转义按[文件与数据安全](./modules/HTML-REPORT.md#文件与数据安全)执行.零发现也要交报告;修改模板或生成器时,按[交付验收](./modules/HTML-REPORT.md#交付验收)末条另用虚构数据验证转义,测试文本不进真实报告.

**完成条件**:HTML 能打开,报告数据与汇总发现一一对应,范围声明和未检查区域完整,旧报告没有被覆盖.

### 第七步:交叉审查

另派没有参与探索和初稿的检查者,给它版本,范围,分片清单,源码,声明资料,报告路径,本文件第一步的判据原文和 [HTML-REPORT.md](./modules/HTML-REPORT.md).它只审四件事:覆盖是否真实,证据能否复核,严重程度和处理方向是否站得住,页面和图是否与正文一致.

审查者发现缺口时,主代理补证据或收窄结论;改过的发现交回原审查者复核.拿不到证据的结论放入待确认.

**完成条件**:交叉审查意见逐条处理;仍保留的疑点都有依据和说明.

### 第八步:验收和交付

打开最终 HTML,按[交付验收](./modules/HTML-REPORT.md#交付验收)逐项检查,每张图都实际看一遍.最后重新核对版本和工作树;除本轮报告与审查记录外,源码或声明资料发生变化,就复核受影响的发现.

交付呈现:交叉审查和页面验收都过了,用系统命令打开报告(macOS `open`,Linux `xdg-open`,Windows `start`),交付语写在最终回复:报告绝对路径,实际范围,发现数量和未检查区域,再加一句导航.有发现时,说严重程度怎么分布,哪条最值得先看,理由是什么;并列时挑证据最全或影响面最大的一条,理由写清为什么挑它;最后问一句「这几条发现里,你想先处理哪一条?」.零发现时,说一句本轮范围内零发现,未检查区域照常列.

**完成条件**:页面验收通过,最终快照和报告一致,报告已打开,交付语已给出.
