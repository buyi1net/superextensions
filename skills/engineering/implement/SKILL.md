# 代码实现

按规格说明（spec）、工单或用户直接交代的任务实现代码工作。无论任务来自哪种输入、规模多小，「开发规范」各节对全部代码产出一律生效。

## 开发规范

### 简洁优先

**用最少的代码解决问题，不过度推测。**

1. 不加要求之外的功能。
2. 不为一次性代码造抽象。
3. 不加没要求的“灵活性”或“可配置性”。
4. 不为不可能发生的场景写错误处理。
5. 不搞多余的兼容分支或双路径。
6. 如果 200 行代码能写成 50 行，就重写。
7. 写新代码前先搜本项目有没有现成的可复用轮子，禁止重复造轮子。
8. 信任边界的输入校验、防止数据丢失的错误处理、安全相关逻辑和用户明确要求的内容不能为了精简而省略。
9. 如果资深工程师会觉得实现过于复杂，就继续简化。

### 精准修改

**只改必须改的，只清理自己造成的混乱。**

1. 不顺手改相邻代码、注释或格式。
2. 不重构没有问题的代码，匹配现有风格，即使你更想换一种写法。
3. 发现无关的死代码时只报告，不要删除。
4. 如果本次改动产生了无用的 import、变量或函数，应当删除；原本就存在的死代码不要顺手清理。
5. 每一行修改都必须能追溯到当前任务。

### 文件编码

**文件的编码和行尾由解析它的运行时决定，不由写文件工具的默认值决定。** 写文件前先确认：这个文件会被谁、按什么代码页和行尾约定解析。

1. 新建源文件默认 UTF-8；修改已有文件时跟随原编码，包括 BOM 的有无和行尾风格，不擅自转换，避免整文件 diff 或破坏已有非 ASCII 字符。
2. 工具链只支持 ASCII、Latin-1、Shift-JIS 等编码时，注释退回工具链支持的语言，不为中文注释引入编译或构建故障。
3. MSVC 或 Visual Studio 编译 C/C++ 时，不带 BOM 的 UTF-8 源文件可能按系统代码页解析中文并触发 C4819 或乱码。使用 UTF-8 BOM，或给编译器添加 `/utf-8`。
4. `.bat`/`.cmd` 由 cmd.exe 按系统 ANSI 代码页解析：中文直接按该代码页写（中文系统即 GBK），或用 UTF-8 无 BOM 并加 `chcp 65001`；带 BOM 会被并入首行命令导致报错。行尾必须 CRLF，LF 会让 `goto` 跨块定位标签失败。
5. `.ps1` 供 Windows PowerShell 5.1 使用时必须 UTF-8 带 BOM，无 BOM 会按 ANSI 误读中文；PowerShell 7 起默认 UTF-8，无此问题。与 `.bat` 的 BOM 答案相反，不要混淆。

### 代码注释

**注释默认使用简体中文，只写代码本身读不出的信息，复述代码的注释一律不写。** 

何时必须写、何时禁止写、用户不熟所用语言时怎么处理、写法细则与旧注释同步，详见 [代码注释规则](./modules/zhushi.md)。

## 实现流程

1. 明确要实现的范围、验收标准和超出范围的内容：有规格说明或工单就完整读取。
2. 用户直接交代的任务，从当前对话提炼，关键信息缺失时当场问清，不自行脑补。
3. 编写或修改测试时，用 skill 工具加载 `tdd`，测试接缝(Seam)、测试策略和测试实现按其规则执行。
4. 开发过程中定期运行类型检查和单个测试文件，及时发现问题，项目没有对应设施时，以实际运行代替。
5. 实现完成后，完整运行一次全量测试套件并处理失败结果。测试全绿只验证代码级断言，收尾仍要对照任务级成功标准（见 constitution「目标驱动」）——测试绿了但没做成用户要的事，不算完成。
6. 没有测试设施的项目，实际运行验证主要路径。
7. 随后按「代码注释」的清单回扫本次新增和修改的注释。
8. 用 skill 工具加载 `code-review`，对本次改动进行评审。
9. 评审完成并确认结果后，将代码提交到当前分支。
