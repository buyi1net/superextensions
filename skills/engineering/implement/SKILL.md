# 代码实现

按规格说明(spec)、工单,或者用户直接交代的任务来写代码.

无论任务来自哪种输入,规模多小,「开发规范」各节对全部代码产出一律生效.

## 开发规范

### 精准修改

**改什么？不改什么？**

只动这次任务要求的东西,只清理自己弄乱的地方.

1. 不加要求之外的功能
2. 不顺手修改旁边的代码、注释或格式
3. 不重构没问题的代码，跟着现有风格写，哪怕你更想换一种写法
4. 每一行改动,都要说得出是这次任务要的.

**死代码怎么处理？**

1. 和本次任务无关的死代码：只报告，不删除。
2. 本次任务造成的死代码，必须清理。但清之前，先按下面几步走。

   **第一步：确认它真的没用了**

   - 除了普通引用，还要看配置注册、框架约定、动态调用，以及对外公开的使用约定。
   - 顺着这次删掉或换掉的调用、入口、导出往下找，同时留意：改过的校验或状态转换，会不会让旧分支再也走不到。
   - 搜不到，只能说明没搜到引用；测试没覆盖，也不能证明它没用。

   **第二步：确认没用了之后，还要再看一眼**

   - 有些代码看起来没人用，但可能有别的用途：兼容旧版本、迁移过渡、给外部系统当入口。**只要这些用途现在还需要，就不能删，要留着。**

   **第三步：确实没用了，再清**

   - 本次任务新增的 import、变量、函数，最后没用上的，清掉。
   - 原有代码因为这次修改没用了，也要一起收尾，哪怕它在别的文件里。
   - 该挪走的调用，挪过去、接好。挪完之后，旧的实现、旧的导出、只给旧实现用的辅助代码，确认过没人用了，再一起清掉。

   **拿不准的**

   - 先保留，把疑点交给评审。

### 文件编码

**文件用什么编码、什么行尾,由解析它的运行时决定,不由写文件工具的默认值决定.**写文件前先确认:这个文件会被谁,按什么代码页和行尾约定解析.

1. 新建源文件默认用 `UTF-8`.修改已有文件时,跟随原编码,包括 `BOM` 有没有、行尾是什么风格,都不要擅自转换.转错了会出现整文件 diff,或者破坏已有的非 ASCII 字符.
2. 工具链只支持 `ASCII`,`Latin-1`,`Shift-JIS` 等编码时,遵循工具链支持的文件编码和字符集,不要因为非 `ASCII` 文本引入编译或构建故障.
3. 用 MSVC 或 Visual Studio 编译 C/C++ 时,不带 `BOM` 的 `UTF-8` 源文件,可能按系统代码页解析中文,触发 `C4819警告` 或乱码.这时候就需要使用 `UTF-8 BOM`,或者给编译器添加 `/utf-8`.

Windows shell 脚本(`.bat`/`.cmd`/`.ps1`)的编码与行尾规则属于命令行基本功,见 [命令行基本功](../../constitution/modules/command-shell.md);源码文件仍按本节原则处理.

### 代码注释

**注释只写代码自己说不出来的东西:为什么这么写,受什么约束.** 代码在做什么,交给命名,结构和类型表达.判断某处该不该写注释,就问一句:这里没有注释,下一个接手的人会不会把它改错,或者踩进同一个坑?会就必须写,不会就不写.

命中这条判据的,常见的有下面几类:

- 违反直觉的写法:看起来能简化其实不能,绕开了某个坑,顺序或时机不能随便调.
- 外部约束:平台差异,协议或第三方限制,兼容性处理,性能考量.
- 关键前提:边界条件,生命周期管理,错误恢复,安全相关的隐含假设.
- 刻意的简化或捷径:写明它撑得住什么程度,超出以后该换成什么做法,免得接手的人分不清是漏了还是故意的.

```cpp
// 简化:先用全局锁,所有账号共用一把;高并发下会串行,成为瓶颈,等吞吐吃紧再换成按账号加锁.
```

下面这些删掉不会让人改错,不写:复述代码在做什么,逐行翻译,模板化 docstring,记录改动历史(「修复了 xx」「新增」),命名已经说清楚的内容.

TODO 不留在代码里:项目有 issue 或工单,就记到那里;没有的,如果它属于刻意的简化,就按上面的写法写成简化注释.

```cpp
// 噪声:只重复代码,没有新信息
// 调用函数清理临时目录.
ScheduleTempDirectoryCleanup(tempPath);

// 有效:给出代码里看不到的原因
// Windows Installer 在卸载阶段可能仍持有文件句柄,这里延迟删除临时目录.
ScheduleTempDirectoryCleanup(tempPath);
```

写法和维护:

- 一条注释只说一件事,能一行写完就写一行.
- 新写的注释用简体中文;已有的英文注释按「精准修改」处理,不顺手改.工具链不支持中文时,按「文件编码」第 2 条处理.
- 本次改动改到的代码,同步更新或删除它身上的注释;没改到的代码上的注释,按「精准修改」不动.过时的注释会让接手的人把错的说法当成事实,比没有注释更糟.

编译器,检查器,测试工具,生成器,覆盖率工具或运行时会读取的注释属于行为输入,先查明是哪个工具读它,读了起什么作用,不按普通文字注释处理.

## 实现流程

### 开始前

先明确这次要做什么、不做什么、验收标准是什么.如果有规格说明或工单,就完整读一遍.如果是用户直接交代的任务,就直接从当前对话里提炼.如果缺失关键信息,就当场问清楚,切记不要自己脑补需求.

确认目标后,用 Skill 工具加载 `codebase-design` 了解代码库的设计取舍与源码组织原则.然后按照下面步骤做筹备

1. **先看已有代码.** 写代码前,先看这次改动放哪合适,测试代码也一样.然后围绕这次的功能,找已有实现和相关调用.对准备改的文件,先查一下行数,看里面主要放什么、这次会改到哪些内容.大文件先用搜索和声明定位,读相关代码,有疑点就继续往下查.如果已有的阅读结论和落点判断还有效,就继续沿用,不用重做这轮评估.
2. **安排改动位置**：结合 `codebase-design` 的原则安排这次改动，如果原文件适合接着写，就原地改，如果新增的职责适合分开，就放到合适的新文件，如果原有结构确实会挡着这次实现就先整理相关联的部分，如果是新项目还没这些东西，就按照当前需求安排。知道了这次要改什么、放哪儿、会牵扯到哪些直接相关的代码，就可以开工了，如果还有疑点就顺着它补查，不需要摸清整个项目，也不用写评估报告或预测新增行数，实现的过程中如果发现职责或者改动范围明显变了，可以回头安排调整。
3. **为什么一定要查行数？**查行数,只是想知道这个文件有多大,方便判断怎么读.不要因为行数多,就自动决定要拆它或者整理它.这次整理多少,要根据这次的任务需要来定,按「精准修改」判断.项目自己已有的规范、流程,该走还是走,这一步不额外加报告或审批.
4. **写入前防覆盖.** 沿用已有判断、准备写入时,先确认文件最新内容,按 `constitution`「写入前防覆盖」执行.

### 写代码

1. 写或改测试时,用 Skill 工具加载 `tdd`.测试接缝(Seam)怎么定、测试策略怎么选、测试怎么写,都按它的规则来.
2. 实现过程中碰到疑难杂症,用 Skill 工具加载 `diagnosing-bugs`,按它的流程走.
3. 开发过程中定期跑类型检查、跑单个测试文件,早点发现问题.项目没有这些设施,就实际跑一遍代替.

### 收尾

1. **跑全量测试.** 实现完成后,完整跑一次全量测试套件,失败就修.如果项目没有测试设施,就实际跑一遍主要路径.
2. **确认真的做成了.** 测试全绿,只说明代码层面没问题,不等于任务完成.还要对照任务级成功标准(见 constitution「目标驱动」),看有没有做成用户要的事.没做成,就不算完成.
3. **回扫文字注释.** 按「代码注释」回扫本次改动涉及的代码,漏写和多写两头都查:缺了会让人改错的地方写上注释没有,复述代码的噪声注释和已经过时的注释清掉没有.行为输入按「代码注释」最后一段单独核验.

### 评审

用 Skill 工具加载 code-review,检查这次任务最后改成了什么.

**交给评审什么**

把任务要求、改动范围、从哪个提交开始比、相关提交,都交代清楚.再带上已有验证结果,说明换掉了哪些旧入口、复用了哪些实现.任务里已经提交的部分也算,别只交剩下没提交的改动.

**适用规范一起交过去**

包括本 skill 的「开发规范」、这次用到的关联模块、`codebase-design` 的相关原则,以及项目自己的规范.给出可访问的路径和对应部分;评审方读不到文件,就提供所需原文.精准修改、编码、文字注释处理、删除前的用途判断,都在这份交接里.会话或工具结果里已有的信息可以直接引用,不用另写交接文件.

**评审回来之后**

评审交回明确问题后,在本次已授权的实现范围内修正,再复核受影响的部分.

### 提交

评审完成、结果确认后,把代码提交到当前分支.
