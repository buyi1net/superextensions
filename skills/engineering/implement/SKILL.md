# 代码实现

本 skill 管的是怎么把代码写出来:任务可能来自规格说明(spec),可能来自工单,也可能是用户在对话里直接交代的.

不管任务是从哪来的,也不管规模有多小,只要产出了代码,「开发规范」里的每一节就都同样生效.

## 开发规范

### 精准修改

**这次该改什么,不该改什么**

只动这次任务要求动的东西,只收拾自己弄乱的地方.具体来说:

1. 不加任务要求之外的功能.
2. 不顺手去改旁边的代码,注释和格式.
3. 没出问题的代码不重构.写代码要跟着现有的风格走,哪怕你更喜欢另一种写法.
4. 每一行改动,都要能说清楚它是这次任务需要的.

**死代码怎么处理**

和这次任务无关的死代码,只报告,不删除.

这次任务造成的死代码,必须清理干净.不过动手之前,要按下面几步走一遍.

1. **先确认它真的没用了.**
   - 除了普通的引用,还要查配置里的注册,框架的约定,动态调用,以及对外公开的使用约定.
   - 顺着这次删掉或换掉的调用,入口和导出往下找.同时留意改过的校验或状态转换,会不会让某个旧分支从此再也走不到.
   - 搜不到引用,只能说明没搜到;测试没覆盖到,也不能证明它没人用.
2. **确认没人用之后,再多看一眼它有没有别的用途.** 有些代码看起来没人调用,其实是在兼容旧版本,支撑迁移过渡,或者给外部系统当入口.**只要这些用途现在还需要,就不能删,必须留着.**
3. **确实没用了,再动手清理.**
   - 这次新加的 import,变量和函数,最后没用上的,清掉.
   - 原有代码因为这次修改变得没用了,也要一起收尾,哪怕它在别的文件里.
   - 需要挪走的调用,挪到新位置并接好.挪完以后,旧的实现,旧的导出,还有只给旧实现用的辅助代码,确认没人用了,再一起清掉.

拿不准该不该删的,先留着,把疑点交给评审去判断.

### 文件编码

**一个文件该用什么编码和行尾,由最终解析它的运行时决定,不由写文件工具的默认值决定.** 所以写文件之前,先弄清楚这个文件会被谁读,对方按什么代码页和行尾约定去解析它.

1. 新建的源文件默认用 `UTF-8`.修改已有文件时沿用它原来的编码,包括有没有 `BOM`,行尾是什么风格,都不要擅自转换.转错了,轻则整个文件出现 diff,重则毁掉文件里已有的非 ASCII 字符.
2. 如果工具链只支持 `ASCII`,`Latin-1`,`Shift-JIS` 这类编码,就按工具链支持的编码和字符集来写,别因为写了非 `ASCII` 的文字,把编译或构建搞坏.
3. 用 MSVC 或 Visual Studio 编译 C/C++ 时,不带 `BOM` 的 `UTF-8` 源文件,里面的中文可能被当成系统代码页来解析,于是触发 `C4819` 警告,或者出现乱码.碰到这种情况,把源文件存成 `UTF-8 BOM`,或者给编译器加上 `/utf-8` 选项.

Windows 上的 shell 脚本(`.bat`/`.cmd`/`.ps1`)另有一套编码和行尾规则,写在 [命令行基本功](../../constitution/modules/command-shell.md) 里.普通源码文件仍按本节处理.

### 代码注释

注释是留给下一个接手的人看的.代码本身只能告诉他程序做了什么,至于为什么偏偏要这么写,当时又受了哪些限制,他光看代码是看不出来的,这部分要靠注释补上.程序做了什么,应该让函数名,变量名,类型和代码结构自己说清楚,不需要再用注释讲一遍.

拿不准某个地方要不要写注释时,可以这样设想:换一个完全没参与这次开发的人来改这段代码,他手里只有代码,会不会改出问题,或者踩进你刚踩过的坑?如果会,这条注释就必须写;如果不会,就不用写.

下面这几种情况最容易让后来的人改错,碰到了就要写注释:

- 写法看起来不合常理.比如这段代码看上去明明可以简化,实际上不行;这么写是为了绕开某个坑;或者几步操作的先后顺序不能调换.
- 代码受到外部条件的约束.比如要照顾不同平台的差异,要遵守某个协议的规定,要绕开第三方接口的某个毛病,要兼容老版本,或者是出于性能考虑才这么写.
- 代码依赖一个前提,但这个前提在代码里看不出来.比如它默认调用方不会传空值,资源必须按特定的顺序释放,出错以后要靠某个机制恢复,或者某处安全检查要依赖前面已经做过的校验.
- 这里是有意先做了简化.注释里要说明这种做法能撑到什么程度,撑不住的时候该换成什么,不然后来的人很可能把它当成疏漏,顺手"修"掉.

注释本身也是写给人读的中文.写的时候就像当面跟同事交代一件事,用完整通顺的句子.一条注释只讲一件事,一行能写完就写成一行.比如:

```cpp
// 现在所有账号共用一把全局锁，这样实现起来最简单。等并发量上来，这把锁会成为瓶颈，到那时再改成每个账号单独一把锁。
```

如果一条注释只是把代码换个说法重讲一遍,就不要写.常见的有这几种:命名已经说清楚了还要再解释一遍的,逐行翻译代码的,照着模板填的 docstring,还有"修复了某某问题""新增某某功能"这类改动记录.改动记录应该写进提交信息,不该留在代码里.

```cpp
// 下面这条注释没有提供任何新信息,只是把函数名念了一遍:
// 清理临时目录。
ScheduleTempDirectoryCleanup(tempPath);

// 下面这条注释说出了代码里看不到的原因:
// 卸载过程中 Windows Installer 可能还占用着这些文件，所以这里不马上删除，而是推迟到后面再清理。
ScheduleTempDirectoryCleanup(tempPath);
```

代码里不要留 TODO.项目有 issue 或工单的,就把它记到那里;没有的话,先看它是不是一处有意的简化,是的话就照上面的写法,写成一条说明简化的注释.

改代码的时候,顺便把这段代码上的注释也核对一遍,内容不对了就改,没用了就删.过时的注释会把接手的人带进沟里,比没有注释还要糟.这次没有改到的代码,上面的注释保持原样,这一点按「精准修改」来.

新写的注释用简体中文.已有的英文注释按「精准修改」处理,不要顺手去改,也不要顺手翻译成中文.如果工具链不支持中文,就按「文件编码」第 2 条处理.

还有一类注释是写给工具看的.读它的可能是编译器,检查器,测试工具,代码生成器,覆盖率工具,也可能是运行时.这类注释不按上面这些规则处理.碰到它,先查清楚是哪个工具在读它,读了以后会起什么作用,再决定怎么处理.

## 实现流程

### 开始前

动手之前,先弄清楚这次要做什么,不做什么,做到什么程度算验收通过.有规格说明或工单的,完整读一遍;是用户在对话里直接交代的,就从当前对话里把这些提炼出来.缺了关键信息,当场问清楚,千万不要自己脑补需求.

目标确认以后,用 Skill 工具加载 `codebase-design`,了解代码库在设计上怎么取舍,源码怎么组织.然后按下面几步做准备:

1. **先看已有代码.** 写代码之前,先想好这次的改动放在哪里合适,测试代码也一样.接着围绕这次要做的功能,把已有的实现和相关调用找出来.准备改的文件,先查一下有多少行,看看里面主要放了什么,这次会改到哪些地方.大文件先靠搜索和声明定位,再读相关的那部分代码,有疑点就继续往下查.

   如果之前的阅读结论和落点判断还成立,就直接沿用,不用重新评估一遍.

   查行数只是为了知道文件有多大,方便决定怎么读它.不要因为行数多,就自动认定要拆分或整理.这次整理多少,看这次任务的需要,按「精准修改」来判断.项目自己已有的规范和流程照常走,这一步不额外加报告或审批.
2. **安排改动放在哪.** 按 `codebase-design` 的原则来安排这次改动.原文件适合接着写的,就在原地改;新增的职责适合单独放的,就放进合适的新文件;原有结构确实会挡住这次实现的,先把相关的那部分整理好;如果是新项目,还没有可以接着写的文件和结构,就按当前需求来安排.

   等你知道了这次要改什么,放在哪,会牵扯到哪些直接相关的代码,这一步就算完成了.还有疑点就顺着它补查,不需要把整个项目摸透,也不用写评估报告或者预估新增多少行.

   写的过程中如果发现职责或者改动范围明显变了,可以回头重新安排.
3. **写入前防覆盖.** 沿用之前的判断准备写入文件时,先确认文件的最新内容,按 `constitution` 的「写入前防覆盖」执行.

### 写代码

1. 写测试或改测试时,用 Skill 工具加载 `tdd`.测试接缝(Seam)怎么定,测试策略怎么选,测试怎么写,都按它的规则来.
2. 写的过程中碰到疑难杂症,用 Skill 工具加载 `diagnosing-bugs`,按它的流程排查.
3. 开发过程中定期跑一跑类型检查和单个测试文件,问题越早发现越好.项目没有这些设施的,就把改到的功能实际运行一遍代替.

### 收尾

1. **跑全量测试.** 实现完成后,把全量测试套件完整跑一遍,有失败就修.项目没有测试设施的,就把主要路径实际运行一遍.
2. **确认真的做成了.** 测试全部通过,只说明代码层面没有问题,不等于任务完成了.还要对照任务的成功标准(见 constitution 的「目标驱动」),看用户要的事到底做成了没有.没做成,就不算完成.
3. **回头检查注释.** 把这次改动涉及的代码按「代码注释」再过一遍,写少了和写多了都要查.缺了注释会让人改错的地方,补上了没有;只是复述代码的注释和已经过时的注释,清掉了没有.写给工具看的那类注释,按「代码注释」最后一段单独核实.

### 评审

用 Skill 工具加载 `code-review`,检查这次任务最终改成了什么样.

**要交给评审的东西**

把任务要求,改动范围,从哪个提交开始比较,以及相关的提交,都交代清楚.再附上已有的验证结果,说明换掉了哪些旧入口,复用了哪些已有实现.任务过程中已经提交的部分也要算进去,不能只交剩下还没提交的改动.

**适用的规范也要一起交过去**

包括本 skill 的「开发规范」,这次用到的关联模块,`codebase-design` 的相关原则,以及项目自己的规范.给出能访问到的路径和对应的章节;评审方读不到文件的,就把需要的原文直接提供给它.交接里要包含精准修改,文件编码和代码注释这几节的要求,也要包含删除代码前怎么判断用途.会话或工具结果里已经有的信息可以直接引用,不用另外写交接文件.

**评审意见回来以后**

评审指出明确的问题后,在这次已经授权的实现范围内修正,再把受影响的部分复核一遍.

### 提交

评审完成,结果确认以后,把代码提交到当前分支.
