# 代码实现

按规格说明(spec),工单或用户直接交代的任务实现代码工作.无论任务来自哪种输入,规模多小,「开发规范」各节对全部代码产出一律生效.

## 开发规范

### 精准修改

**只改必须改的，只清理自己造成的混乱。**

1. 不加要求之外的功能.
2. 不顺手改相邻代码,注释或格式.
3. 不重构没有问题的代码,匹配现有风格,即使你更想换一种写法.
4. 发现无关的死代码时只报告,不要删除.
5. 这次加的 import、变量、函数,最后没用上就清掉.原有代码因为这次修改没用了,也要收尾,哪怕在别的文件里.该迁移的调用要接好,不再需要的旧实现、旧导出和专用辅助代码也一起处理.顺着这次删掉或换掉的调用、入口和导出去找,也留意改过的校验或状态转换会不会让旧分支再也走不到.

   删之前先确认真实用途.除了普通引用,还要看相关的配置注册、框架约定、动态调用和对外公开的使用约定.搜索没命中,只能说没找到引用;测试没覆盖,也不能证明这段代码没用.还需要支持的兼容、迁移和外部入口要留着.拿不准的先保留,把疑点交给评审.原来就没用、又和这次任务无关的代码,仍按上一条处理.
6. 每一行修改都必须能追溯到当前任务.

### 文件编码

**文件的编码和行尾由解析它的运行时决定，不由写文件工具的默认值决定。** 写文件前先确认:这个文件会被谁,按什么代码页和行尾约定解析.

1. 新建源文件默认 `UTF-8`;修改已有文件时跟随原编码,包括 `BOM` 的有无和行尾风格,不擅自转换,避免整文件 diff 或破坏已有非 ASCII 字符.
2. 工具链只支持 `ASCII`,`Latin-1`,`Shift-JIS` 等编码时,注释退回工具链支持的语言,不为中文注释引入编译或构建故障.
3. `MSVC` 或 Visual Studio 编译 C/C++ 时,不带 `BOM` 的 `UTF-8` 源文件可能按系统代码页解析中文并触发 `C4819` 或乱码.使用 `UTF-8 BOM`,或给编译器添加 `/utf-8`.

Windows shell 脚本(`.bat`/`.cmd`/`.ps1`)的编码与行尾规则属于命令行基本功,见 [命令行基本功](../../constitution/modules/command-shell.md);源码文件仍按本节原则处理.

### 代码注释

**注释默认使用简体中文，只写代码本身读不出来的信息，复述代码的注释一律不写。** 
什么时候必须写注释,什么时候禁止写注释,用户对项目所用语言不熟悉时怎么处理,注释的写法细则与旧注释同步,详见 [代码注释规则](./modules/zhushi.md).

## 实现流程

1. 明确要实现的范围,验收标准和超出范围的内容:有规格说明或工单就完整读取.
2. 用户直接交代的任务,从当前对话提炼,关键信息缺失时当场问清,不自行脑补.
3. 写代码前,先看这次改动放哪儿合适,测试代码也一样.用 skill 工具加载 `codebase-design`;当前上下文已经完整加载、内容仍有效的,直接沿用.

   围绕这次功能找已有实现和相关调用.对准备修改的已有文件,先查一下行数,再看里面主要放什么、这次会改到哪些部分.长文件先用搜索和声明定位,读相关代码,有疑点再往下查.已有的阅读结论和落点判断仍适用,就沿用,不用重做这轮评估.

   结合 `codebase-design` 的原则安排这次改动:原文件适合接着放,就原地改;新增职责适合分开,就放到合适的新文件;原有结构确实挡着这次实现,先整理相关部分.新项目还没有这些文件,就按当前需求安排.

   知道这次改什么、放哪儿、会牵动哪些直接相关的代码,就可以开工.还有疑点就顺着它补查,不用先摸清整个项目,也不用写评估报告或预测新增行数.写着发现职责或改动范围明显变了,再回头调整安排.

   加载的是 `codebase-design` 主文件,包括“简洁设计”“源码组织与复用”和其他适用原则.[DEEPENING](../codebase-design/modules/DEEPENING.md)、[DESIGN-IT-TWICE](../codebase-design/modules/DESIGN-IT-TWICE.md) 等关联模块,有实际设计问题再用.

   查行数是为了了解文件大小,不设写前硬上限;需要整理多少,仍按本次需要和“精准修改”判断.项目已有的材料要求照常执行,这一步不另加报告或审批.沿用有效判断时,写入前确认文件最新内容仍按 [constitution“写入前防覆盖”](../../constitution/SKILL.md#写入前防覆盖) 执行.
4. 编写或修改测试时,用 skill 工具加载 `tdd`,测试接缝(Seam),测试策略和测试实现按其规则执行.
5. 任务过程中如果遇到疑难杂症,用 skill 工具加载 `diagnosing-bugs`,按它的流程来.
6. 开发过程中定期运行类型检查和单个测试文件,及时发现问题,项目没有对应设施时,以实际运行代替.
7. 实现完成后,完整运行一次全量测试套件并处理失败结果.测试全绿只验证代码级断言,收尾仍要对照任务级成功标准(见 constitution「目标驱动」):测试绿了但没做成用户要的事,不算完成.
8. 没有测试设施的项目,实际运行验证主要路径.
9. 随后按「代码注释」的清单回扫本次新增和修改的注释.
10. 用 skill 工具加载 `code-review`,检查这次任务最后改成了什么.把任务要求、改动范围、已知的比较起点和相关提交交代清楚,再带上已有验证结果,说明换掉了哪些旧入口、复用了哪些实现.任务里已经提交的部分也算,别只交剩下没提交的改动.

    把适用规范一起交过去:本 skill 的“开发规范”和本次用到的关联模块、`codebase-design` 的相关原则,以及项目自己的规范.给出可访问的路径和对应部分;评审方读不到文件,就提供所需原文.精准修改、编码、注释和删除前的用途判断,都在这份交接里.会话或工具结果里已有的信息可以直接引用,不用另写交接文件.

    评审交回明确问题后,在本次已授权的实现范围内修正,再复核受影响的部分.
11. 评审完成并确认结果后,将代码提交到当前分支.
