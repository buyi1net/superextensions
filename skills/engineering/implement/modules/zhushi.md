# 代码注释规则

> 本模块只管工程判断:什么时候该写注释,写什么,什么时候禁止写,标记类注释怎么写,旧注释怎么处理.注释用什么语言写,遵循主文件的规定.

**注释只写代码本身看不出来的信息;复述代码的注释,一律不写.** 注释面向的读者是「熟悉这门语言惯用写法、但不了解项目来历的维护者」:语言本身他们熟,你的决策过程他们不熟,注释就是写给他们的.判断该不该写,看这条信息能不能从代码本身看出来,而不是看代码「清不清楚」:刚写完的代码,自己看永远是清楚的,用「清不清楚」当标准并不可靠.

写代码时不用惦记着写注释.等测试全跑通后、进入评审之前,把这次新增和改过的逻辑再过一遍,只要碰上下面任何一类,就必须补注释.

## 什么时候必须写注释

- **为什么这么做、为什么不选更直觉的做法.** 只要读者看到一段代码会问「为什么不直接 X」,就要用一条注释回答这个问题.绕弯的写法、看似多余的步骤、凭空冒出来的数字,出现这些情况,就说明这里需要一条注释.

- **外部约束.** 协议条款、上游 bug、平台怪癖、合规要求:这些从代码本身推不出来.

- **刻意做的简化或捷径.** 要写明它简化在哪儿,将来又该怎么改,免得后来的人分不清是漏了,还是故意这么写:

    ```cpp
    // 简化:所有账号共用一把全局锁,实现简单,但并发请求会排队;等并发压力大了,再改成每个账号一把锁.
    ```

- **代码里看不出来的来历.** 某个数字为什么取这个值、为什么这里重试三次、为什么顺序不能换.

- **公共接口要交代的事.** 调用方必须知道、但从签名和类型上看不出来的内容:返回值有没有歧义(空列表是没查到,还是查全了)、副作用(网络、文件、全局状态)、参数有什么限制、调用前要满足什么条件.这些写进 docstring,让调用方不看实现也能正确使用;简单的 getter、一眼就能看懂的单行代码,不用写.

- **声明处的细节.** 单位(毫秒还是秒)、边界含不含端点、null 或零值有没有特殊含义、资源所有权归谁、不变量:这些都是名字和类型说不清的地方.

## 什么时候禁止写注释

- 复述代码内容的注释.

- 讲语法本身的注释.判断方法:看它讲的是语言本身的知识,还是这个项目的知识.讲语言的,删;讲项目的,留.

    ```rust
    // ❌ 讲语言:Mutex 可以保护共享数据
    // ✅ 讲项目:这把锁只保护缓存,不保护数据库连接,别拿它当全局锁用
    ```

- 命名已经说清楚、逻辑又简单的代码,不要为了凑格式再补一条注释.

- 为了「显得规范」而写的套模板 docstring.docstring 里有约定就写,没有就不写,不要为了凑格式硬写.

    ```cpp
    // ❌ 只重复代码,无额外信息
    // 调用函数清理临时目录.
    ScheduleTempDirectoryCleanup(tempPath);
    
    // ✅ 提供了代码里没有的信息
    // Windows Installer 在卸载阶段可能仍持有文件句柄,这里延迟删除临时目录.
    ScheduleTempDirectoryCleanup(tempPath);
    ```

## 用户对项目所用语言不熟悉时怎么处理

用户声明对这门语言不熟时,语言本身的讲解要放到交付说明里,不能直接塞进代码注释里:交付时要把这次改动用到的进阶写法(新惯用写法、关键 trait、宏)讲清楚.注释里仍然只写项目自己的知识.

## 写法细则

- **注释要把数量、条件、边界说清楚,别用「处理了」「优化了」这种空话.** 比如「带 1 秒退避重试 3 次」,就比「处理了重试」有用.

- **注释里用常量名,别把值抄一遍.** 值改了,抄在注释里的那份就得跟着改.单位换算是例外:`1048576 // 1MB` 更清楚,不算重复.

- **会失效的注释要写清楚什么时候删.** 比如 workaround、只对某个版本适用的代码,都要注明什么条件下可以删,比如「Safari 14 停止支持后移除」.

## 标记类注释

TODO、HACK、FIXME 这类标记,只用来记这次不做、但以后要处理的事情.

光写一个标记不够,还得写清楚两件事:

1. **卡在哪儿**——为什么现在做不了,通常挂一个 issue 编号;
2. **什么时候能删**——满足什么条件就可以把这个标记去掉.

比如:

```text
// TODO: 抽成共享工具,等移动端 API 对齐(MOBILE-123)
// HACK: 绕过 Safari 14 的 flexbox bug,停止支持该版本后删除
```

## 自检与同步

- **反过来再查一遍**:删掉这条注释,如果你少掉的是这个项目自己的知识,就留;如果只是语言教程里的东西,或者什么也没少,就删.这其实就是开头那条总原则——注释只写代码本身看不出来的信息.

- **代码改了,旧注释也要跟着改**:发现旧注释和代码对不上,就更新或删掉.错的注释比没有注释更糟,因为读者会信它.
