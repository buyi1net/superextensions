# 规格落地

输入是一份规格说明和它的工单(由 `to-spec` 和 `to-tickets` 产出).目标是整份规格在一条集成分支上实现完毕:每个工单的验收标准全部勾选,实现证据填好,全量测试通过,评审发现的问题已修复.做不到全部完成时,把卡住的工单和原因如实写进执行报告.

你是主 agent,负责调度,集成和回写工单;具体工单交给子代理实现.单个工单或一个窗口就能做完的活,不走本 skill,直接用 Skill 工具加载 `implement`.

## 核心概念

- **任务图**:工单不是一串步骤,是带依赖关系的图.任何时刻都有一批前置依赖已满足,可以马上开工的工单,叫**就绪前沿(frontier)**.
- **以集成为准**:前置工单的成果提交进集成分支,并且你核对过验收,下游才算解锁.子代理口头说"做完了"不算.
- **上下文指针**:和子代理之间少传原文,多传指针:规格路径,工单路径,相关代码位置,前置工单的提交.指针能拿到的信息不再复述.
- **运行目录**:主工作区下的 `temp/implement-runs/<spec-slug>/`,存放评审报告,日志和 worktree.派工时一律给它的绝对路径,子代理在哪个工作目录干活,报告都落在同一处.

## 一,开工准备

1. 确认主工作区没有未提交的跟踪文件改动.有改动就停下问用户,不要替用户提交或丢弃.
2. 记下当前 `HEAD` 作为本次运行的起始提交,再在主工作区切出集成分支:`git switch -c integrate/<spec-slug>`.两种模式都用这条分支,主 agent 的合并,测试和工单回写都在主工作区进行.
3. 读完规格和全部工单,选定执行模式(见下一节),向用户汇报选了哪种模式,理由和初始并发数.汇报完直接开工;用户中途提出调整,按用户的来.

## 二,选择执行模式

一次运行只用一种模式,中途不切换.

- **原地模式**:子代理直接在主工作区干活,同一时刻只有一个子代理在写.依赖图基本是一条链,工单之间改的文件高度重叠,或者工单很依赖被 gitignore 忽略的内容(参考资料,本地依赖,构建产物)时,用这个模式.
- **worktree 模式**:为每个工单创建独立的 git worktree 和分支,多个子代理并发执行.就绪前沿经常有多个互不相干的工单时,用这个模式.

拿不准选哪个,选原地模式.串行慢一点,但不会出合并问题.

## 三,派工

每派一个工单,给子代理的任务说明里写清楚这些:

- 工单文件和规格的路径,前置工单的提交号.要加载的 skill,要读的参考资料和验证方式都在工单的 `**技能：**` `**参考：**` `**验证：**` 字段里,让子代理按工单执行,不在任务说明里重复交代.`**验证：**` 写明本单不要求全量测试通过时,以工单为准.
- 它的工作目录和分支.worktree 模式下,被 gitignore 忽略的依赖和构建产物不会出现在 worktree 里,需要用到时给出它们在主工作区的绝对路径.
- 只改工单需要改的文件.工单文件,规格文件由主 agent 回写,子代理不碰.验收记录,总结之类的文件一律不建,结论写进完工汇报.
- 交付前用 Skill 工具加载 `code-review` 评审自己的改动,按它的报告模板把报告写到 `<运行目录>/reviews/<ticket-id>.md`.Spec 和 Standards 两条轴上确认的问题全部修完,再复核一遍.报告的"结论"一节写明:评审范围(基线和交付版本),每条轴剩余的明确问题数.没有这份报告,交付会被打回.
- 完工汇报包括:交付版本(worktree 模式写提交号,原地模式写"工作区未提交,基线 <HEAD>"),改动文件,跑过的验证命令和退出码,评审报告路径,给下游工单的对接提示,以及工单"遗留问题"小节要求的内容.长日志写到 `<运行目录>/logs/` 下,汇报里只给路径.

### 原地模式

子代理只改文件,不提交.提交由你在验证通过后做,这样失败的改动不会进入集成分支.子代理的评审范围是当前工作区相对 `HEAD` 的改动.

### worktree 模式

1. 为工单建 worktree:`git worktree add -b implement/<spec-slug>/<ticket-id> <运行目录>/worktrees/<ticket-id> integrate/<spec-slug>`.
2. 如果需要安装依赖,让子代理在自己的 worktree 里安装,不和别的 worktree 共用可写的依赖目录或构建目录.
3. 子代理在自己的分支上提交.完工前,先把集成分支的最新提交合进自己的分支,解决冲突,验证通过后再汇报.
4. 并发数由你决定,依据是就绪前沿有多宽,模型配额,机器负载和测试成本.遇到 429,过载或超时,就降低并发.

## 四,集成与回写

每收到一份完工汇报,按顺序做:

1. 读评审报告的"结论"一节:评审范围对得上这次交付,两条轴剩余的明确问题都是 0.只读这一节,不自己重新评审,也不把整份 diff 读进上下文.报告缺失,范围对不上或还有剩余问题,把报告路径交回子代理处理.
2. 核对实际改动的文件,看有没有超出工单范围.以 diff 为准,不只看子代理自报的清单.原地模式用 `git status --porcelain`;worktree 模式用 `git diff --name-only integrate/<spec-slug>...<交付版本>`(三个点,只看工单分支自己的改动,不把它同步进来的别的工单算进去).
3. worktree 模式下,预检合并工单分支:`git merge --no-ff --no-commit implement/<spec-slug>/<ticket-id>`.一次只合一个.
4. 按工单的 `**验证：**` 跑验证.
   - 通过:worktree 模式 `git commit` 完成合并;原地模式提交子代理的改动.
   - 不通过或有冲突:worktree 模式 `git merge --abort` 退回干净状态;原地模式保持现场.然后把问题派回给该工单的子代理.集成分支上只留验证通过的成果.
5. 逐条核对工单的验收标准,满足的勾成 `[x]`,在工单预置的实现证据区填好交付,验证,对接和遗留问题,把状态改成 `已完成`,提交.有验收项没满足,工单就不算完成.
6. worktree 模式下,确认 worktree 干净后移除它,删除工单分支.
7. 重新计算就绪前沿,派发新解锁的工单.向用户输出一行进度:哪个工单完成了,还剩几个,正在做哪些.

## 五,失败处理

- 子代理拒绝执行或中途放弃,换一个模型重派一次.
- 同一个工单连续两次失败,或者失败原因在工单之外(规格有矛盾,缺依赖,凭据失效),就把它标成阻塞,继续推进其他能做的工单,不要自己改规格绕过去.标阻塞时做这几件事:
  1. 原地模式下,用 `git stash push -u -m "<ticket-id> 失败现场"` 收起改动,让工作区回到干净状态;worktree 模式下,worktree 和分支原样保留.
  2. 在工单状态里写 `阻塞: <原因>`,实现证据区写上已有的验证结果,现场位置(stash 名或 worktree 路径)和遗留问题,没满足的验收项保持不勾,提交.
- 失败影响全局(账号欠费,网络不通,主工作区状态异常),停下来向用户汇报.
- 没集成的 worktree 和分支一律保留,方便排查.不要执行 `git worktree prune`,也不要 `git worktree remove --force`.
- 运行中断后,先确认中断前的子代理都已停止,再检查主工作区和每个现存 worktree 的 `git status`,遇到没合完的合并(存在 `MERGE_HEAD`)就先 `git merge --abort`.然后按工单文件里的状态和集成分支上的提交恢复进度,复用已有的 worktree 和分支接着跑.

## 六,收尾

所有工单都已完成,或者剩下的工单都卡在阻塞上,没有能派的了,就进入收尾.

1. 在主工作区跑全量测试.
2. 派一个独立的子代理,用 Skill 工具加载 `code-review`,评审集成分支相对起始提交的整体 diff,报告写到 `<运行目录>/reviews/final.md`.主 agent 只读报告结论,把报告路径交给子代理修复,修完再跑一遍全量测试.
3. 清理剩下的已集成 worktree.
4. 在规格目录下生成 `执行报告.md`,内容从各工单的状态和实现证据里汇总,提交到集成分支.
5. 向用户汇报集成分支名和执行报告路径,并把阻塞工单和需要用户决定的遗留问题直接列出来.

整体结果只有在所有工单已完成,全量测试通过,最终评审没有剩余问题时,才算"全部完成";否则写"部分完成",并写明原因.

执行报告的骨架:

```md
# <规格名> 执行报告

**整体结果：** 全部完成 / 部分完成(<原因>)
**集成分支：** integrate/<spec-slug>(起始提交 <sha>)
**执行模式：** 原地 / worktree,并发 <n>

## 工单完成情况

| 工单 | 状态 | 提交 | 备注 |
|---|---|---|---|

## 阻塞工单

- <工单>:<阻塞原因>,现场位置,影响的下游工单,需要用户做什么

## 遗留问题

按类别汇总各工单报上来的遗留问题,每条注明来自哪个工单:规格或工单与实际不符,死代码,无关 bug,被跳过的检查,其他.

## 测试与评审

- 全量测试:<命令>,<结果>
- 最终评审:<结论>,已修复 <n> 条,未修复的列在遗留问题里
```

某一节没有内容,就写"无".

只有用户明确授权后,才能合进主干,推送远程或开 PR.
