# 原型验证

原型是**回答一个问题的一次性代码**。问题决定原型的形状。

## 挑分支

先弄清这次要回答哪个问题：看用户的原话和周边代码判断；拿不准、用户又在场，就问一句：

- **「这个逻辑 / 状态模型对不对？」** → [LOGIC.md](./modules/LOGIC.md)。做一个单文件可分享 HTML（自由玩按钮 + 分页引导走查），把状态机拉去跑那些纸上推理费劲的案例，非开发也能上手操作。
- **「这东西该长什么样？」** → [UI.md](./modules/UI.md)。在同一路由上生成几个截然不同的界面变体，用 URL 查询参数和底部悬浮条切换。

两个分支的产物完全不同，挑错了分支，整个原型白做。问题真模糊、用户又不在，就按周边代码选更贴合的分支（后端模块 → 逻辑；页面或组件 → UI），并把假设写在原型开头。

## 两个分支都守的规矩

1. **从第一天起就是一次性的，而且要让人一眼看出是一次性。** 命名要让人扫一眼就知道是原型、不是产线代码。独立文件的原型放哪，跟项目管理制度走，不自己定；长在源码里的 UI 变体挂项目既有路由，跟路由惯例，不发明新的顶层结构。
2. **启动零思考。** UI 原型从项目的任务 runner 一条命令就能跑起来：`pnpm <name>`、`python <path>`、`bun <path>`。逻辑 demo 是用户双击就能开的单个 HTML 文件。哪种都不许「先想一下怎么跑」。
3. **默认不持久化。** 状态放内存。持久化是原型要*验证*的东西，不是它该依赖的东西。问题真的涉及数据库，就起一个临时库或本地文件，名字里明写「PROTOTYPE，随删」。
4. **不抛光。** 不写测试，错误处理只留跑起来必需的，不上抽象。目的是快点学到东西。
5. **把状态亮出来。** 每次操作后（逻辑）或每次切变体（UI），打印或渲染完整的相关状态，让用户看见什么变了。
6. **做完就捕获。** 验证过的决策合进真代码；原型本体作为**一手材料**捕获：提交到一次性分支，不进主分支，在实施工单上留指向那个分支的指针。答案本身（结论 + 它解决了什么问题）也记下来，记在工单或提交说明里。主分支不收原型本体，只收决策。
