# UI 原型

在同一路由上生成**几个截然不同的界面变体**，底部悬浮条切换。用户在浏览器里翻着比，挑一个（或者从各变体上偷零件），剩下的扔掉。

问题要是在逻辑 / 状态而不是长相，走错分支了，去 [LOGIC.md](./LOGIC.md)。

## 什么时候是这个分支

- 「这个页面该长什么样？」
- 「定下来之前想看几个仪表盘的方案。」
- 「设置页换个布局试试。」
- 任何用户本来要在脑子里对着三张模糊草图耗一天的时刻。

## 两种做法：优先做法 A

UI 原型容不容易判断，很吃**它跟不跟应用其余部分贴在一起**：真的头部、真的侧栏、真的数据、真的密度。孤立的一次性路由是真空环境，变体单看都挺好，比不出高下。有现成页面能挂变体的，默认做法 A。原型旁边真没有现成页面可挂的，才用做法 B。

### 做法 A：挂在现有页面上（优先）

路由已经存在。变体渲染在**同一路由**上，用 `?variant=` URL 查询参数门控。既有的取数、参数、鉴权全保留，只换渲染。这是默认，没有具体理由不选它。

原型做的东西还没有页面、但*天然住得进某个现有页面*（仪表盘的新区块、设置页的新卡片、现有流程的新步骤），也算做法 A：把变体挂进宿主页里。

### 做法 B：新页面（最后手段）

只在原型做的东西真的没有任何现有页面能收留时用（全新的顶层界面，或哪都嵌不进去的流程）。

按项目既有的路由惯例建**一次性路由**，不发明新的顶层结构。命名一眼可辨是原型（路径或文件名里带 `prototype`）。同一个 `?variant=` 模式。

定做法 B 之前先自查：真的没有现成页面能嵌吗？空路由会藏住设计问题，那些问题要页面填满了内容才暴露。

两种做法的底部悬浮条是同一个。

## 流程

### 1. 写下问题和变体数

默认 **3 个变体**。超过 5 个就不是截然不同，是噪音了；5 个封顶。

计划写成一行，放在原型位置或文件头注释：

> 「设置页三个变体，`?variant=` 切换，挂在现有 `/settings` 路由上。」

用户在场能当场反对，不在场回头也能核对。

### 2. 生成截然不同的变体

逐个起草。每个变体守住：

- 页面的目的和它拿得到的数据。
- 项目的组件库 / 样式体系（TailwindCSS、shadcn、MUI、裸 CSS，什么都行）。
- 导出组件名清晰，如 `VariantA`、`VariantB`、`VariantC`。

变体必须**结构上不同**：布局不同、信息层次不同、主要操作不同，不是换个颜色。三张微调过的卡片网格不是 UI 原型，是换壁纸。两稿出来太像，就带着「不许用卡片网格」的明确指令重做其中一稿。

### 3. 接线

在路由上建一个统一的切换器：

```tsx
// 伪代码，按项目框架适配
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

做法 A（现有页）：既有的取数全留在切换器上游，每个变体只换渲染的子树。

做法 B（新页）：`/prototype/<name>` 下的一次性路由挂同一个切换器。

### 4. 做悬浮切换条

屏幕底部居中放一条小的固定定位条，三件套：

- **左箭头**：切到上一个变体（循环）。
- **变体标签**：当前变体的键，变体导出了名字就连名字一起显示，如 `B (Sidebar layout)`。
- **右箭头**：切下一个（循环）。

行为：

- 点箭头更新 URL 查询参数（用框架的路由器，Next 用 `router.replace`、React Router 用 `navigate` 等），变体可分享、刷新不丢。
- 键盘：`←` `→` 也能切。`<input>`、`<textarea>`、`[contenteditable]` 聚焦时不拦截。
- 视觉上跟页面明显区分（高对比胶囊、轻阴影），一看就知道不是要评审的设计的一部分。
- 生产构建里隐藏：`process.env.NODE_ENV !== 'production'` 之类的检查门控，防止原型误合进主干、把切换条带到用户面前。

切换器做成一个共享组件，两种做法都能复用。搁在项目收纳共享 UI 的地方。

### 5. 交付

把 URL（和 `?variant=` 的键）亮给用户。用户有空自己翻。有价值的反馈通常是**「我要 B 的头部配 C 的侧栏」**，那才是他们真正想要的设计。

### 6. 捕获答案并清理

变体选出赢家后，捕获答案（哪个变体、为什么），再按 [SKILL](../SKILL.md) 说的方式捕获原型。赢家合进真代码，其余挪上一次性分支，不进主分支：

- **做法 A**：赢家合进现有页面；输的变体和切换器从主分支删掉。
- **做法 B**：赢家升格成正式路由；一次性路由和切换器从主分支删掉。

全套变体是一手材料，所以进一次性分支，不是直接删掉：留在主分支的变体组件和切换器烂得快，还迷惑下一个读者。

## 反模式

- **只差颜色或文案的变体。** 那是微调，不是原型。真变体连结构都不一样。
- **变体之间共享太多代码。** 共享一个 `<Header>` 可以；共享 `<Layout>` 就废了。每个变体要自由到能推翻整个布局。
- **把变体接到真实的写操作上。** 只读原型没问题。变体要写，就指向 stub：问题是「该长什么样」，不是「后端行不行」。
- **把原型直接提上产线。** 变体代码是在原型约束下写的（无测试、错误处理最小），合进去时正经重写。
