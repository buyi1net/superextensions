# 逻辑原型

一个自包含的单 HTML 文件（**可分享 demo**），让任何人点按钮就能驱动一个状态模型。问题涉及**业务逻辑、状态流转或数据形状**时用它：这类东西纸上看着挺对，拿真实案例跑一遍才知道哪里别扭。

因为它是单文件、零安装，你可以直接发给非开发（设计师、产品、领域专家），让他们自己摸出感觉。所以 demo 要说他们的语言，不是代码的语言。

## 什么时候是这个分支

- 「不确定这个状态机扛不扛得住先 X 再 Y 的边界情况。」
- 「这个数据模型真能表达那种情况吗……」
- 「写 API 之前想先摸一下它该长什么样。」
- 任何想**按按钮、看状态变**的场合。

问题要是「这东西该长什么样」，走错分支了，去 [UI.md](./UI.md)。

## 流程

### 1. 写下问题

写代码前，先写下这次原型要验证什么：哪个状态模型、哪个问题。一段话，放在 demo 顶部的可见说明区，不能只写在注释里。答错问题的逻辑原型纯属浪费，把问题写明白才能事后核对，不管用户现在盯着还是回头再看。

### 2. 把逻辑隔离成可搬走的模块

真正回答问题的那段逻辑，放进单个 `<script>` 块，写成一个小的纯模块，将来能整体拎出来、放进真代码。页面是一次性的，这个模块不是。

形状跟着问题走：

- **纯 reducer**：`(state, action) => state`。动作是离散事件、状态是单值时合适。
- **状态机**：显式的状态和流转。「哪些动作现在根本不合法」本身是问题的一部分时合适。
- **一组纯函数**，作用在朴素的数据类型上。没有隐含的「当前状态」，状态只是一连串变换时合适。
- **接口清晰的类或模块**，逻辑确实持有持续的内部状态时用。

选最贴合问题的形状，不选最好接页面的形状。保持纯净：不碰 DOM、不碰 `document`、不挂按钮处理函数。页面调它，它不回调页面。这是那个纯模块能活得比页面久的关键：问题一有答案，验证过的 reducer / 状态机 / 函数集自己就能拎进真模块。

### 3. 搭可分享的 HTML 文件

一个文件，纯 HTML/CSS/JS：无框架、无打包器、无服务器，全部内联，双击就能打开，邮件转手几次照样能跑。任何人打开就能跑。

写给非开发看。每个标签用**领域语言**，不用代码语言：按钮和状态读起来像业务用语，不像 reducer。用大白话解释正在发生什么。

从上到下，干净的层次：

1. **标题加一行说明**：这个 demo 让你探索什么（第 1 步的那个问题）。
2. **当前状态**：完整的相关状态，渲染成可读的面板（带标签的字段，不是原始 JSON 倾倒），每次点击后重渲染，变化看得见。非开发跟得上的地方，顺手指出刚变了什么。
3. **自由玩按钮**：一个动作一个按钮，永远全部可用，谁都能以任意顺序戳。点一下派发动作、重渲染状态。
4. **引导走查**：一组**场景**，一页一景。每页放一小段白话场景说明（它搭的局、要盯什么），下面是这一景要**依次按的按钮**。每一步是真按钮：点了就执行那个动作、走到下一步。开始走查先重置到已知的初始状态，场景每次跑一个样。

场景挑那些别扭的、纸上推理费劲的：主路径、刁钻边界、一个该被拒绝的操作。

好看但克制：干净的排版、大方的留白、一个强调色。不上动画、不搞花活，不跟状态和按钮抢注意力。

### 4. 交付

把文件发给用户，或者帮他打开。用户有空了自己会点着走；有价值的瞬间是他们说「等等，这不该发生」或「咦，我以为 X 会不一样」，那是**想法里的 bug**，正是原型存在的全部意义。他们要新动作或新场景，就加。原型会长。

### 5. 捕获答案和原型

原型答完自己的问题，先捕获答案，再按 [SKILL](../SKILL.md) 说的方式捕获原型。拆到逻辑分支：验证过的 reducer / 状态机 / 函数集拎进真模块，这就是被吸收的决策；HTML 壳进一次性分支，原型作为一手材料留在那里。单文件自包含，在那儿也随时能重跑。

## 反模式

- **不加测试。** 需要测试的原型已经不是原型。
- **不接真数据库。** 内存状态，除非问题问的就是持久化。
- **不做泛化。** 不想「以后要是想支持 X 呢」。原型只答一个问题。
- **不把逻辑和页面搅在一起。** 纯模块一旦引用 DOM、`document` 或按钮处理函数，就拎不走了。页面只是纯模块外面的一层薄壳。
- **不上框架、打包器、服务器。** 一个收件人双击就开的文件；React 应用或 dev server 直接毁掉「可分享」。
- **不把 HTML 壳发上产线。** 页面是给人挨个点着玩的，背后那个逻辑模块才是值得留的。
