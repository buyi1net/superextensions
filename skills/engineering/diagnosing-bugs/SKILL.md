这是为**顽固 bug** 准备的流程。除非有明确理由，否则不要跳过任何阶段

在探索代码库时，先看 `docs/` 下有没有 `GLOSSARY.md`（多领域项目则是 `GLOSSARY-INDEX.md` 及其指向的领域术语表），有就读，以建立相关模块的清晰心智模型，并检查你所涉及区域的 ADR。

## 脱敏

使用本 skill 时，需要展示命令、输出结果以及捕获的产物。**但在此之前，务必先脱敏所有敏感信息**，凡涉及密钥、密码、token 的地方，一律用 `<REDACTED>` 替代。操作上，应针对环境变量来构建调试循环，这样凭证只存在于环境里，不会出现在你展示的任何内容中。另外，捕获的产物（如 HAR 文件、日志等）可能携带认证头信息，引用时只摘取那些能说明问题的关键行即可。如果脱敏后的输出仍不足以定位问题，请直接说明情况，并向用户索要更多信息。

## 第一阶段：构建反馈循环

**这才是核心技能。其余的都只是机械操作。** 关键在于拿到一个**精炼的通过/失败信号**：这个信号对着当前 bug 跑，必须明确报红。有了它，根因就跑不掉；不论是二分法、假设检验还是埋点，都只是消耗这个信号的手段。没有这个信号，盯着代码看再多也没用。

**在这件事上要投入远超平时的精力。大胆下手，思路放开，死磕到底。**

### 构建反馈循环的方法（大致按此顺序）

1. **写失败测试**：在能触及 bug 的任意接缝处写测试，单元、集成、端到端都行。
2. **Curl/HTTP 脚本**：对着运行中的开发服务器（`dev server`）发请求。
3. **CLI 调用**：用固定输入执行，把 `stdout` 和已知良好的快照做 `diff`。
4. **无头浏览器脚本**：使用 Playwright 或 Puppeteer 驱动 UI，对 DOM/控制台/网络做断言。
5. **重放捕获的 trace**：把真实的网络请求 / payload / 事件日志存到磁盘，把捕获的请求在测试环境里单独重放，让代码重新走一遍当时的执行路径。
6. **一次性 harness**：启动一个最小化系统（一个服务，以及一些 mock 掉的依赖项），这样你就能用一个函数调用直接触发 bug 的代码路径。
7. **Property / fuzz 循环**：如果 bug 是“偶尔输出错误”，就跑 1000 个随机输入，寻找失败模式。
8. **二分法 harness**：如果 bug 出现在两个已知状态之间（比如 `commit`、`dataset`、`version`），就自动化执行“boot at state X, check, repeat”，让你能 `git bisect run`。
9. **差分循环**：用旧版本和新版本（或两份配置）跑同一输入，对输出做 diff。
10. **人机交互脚本**：最后手段。如果必须有人点击，就用 `scripts/hitl-loop.template.sh` 来驱动操作者，这样循环仍然结构化。捕获的输出会回传给你。

**反馈循环建对了，问题就解决了 90%。**

### 收紧循环

把调试循环当作一个产品来打磨。一旦你跑通了一个循环，就要对它**精炼收紧**：

- 能不能让它跑得更快？（缓存提前设置好，跳过无关的初始化，缩小测试范围。）
- 能不能让它的反馈信号更精准？（断言要针对具体的可观察现象，而不是笼统地断言“没崩溃”。）
- 能不能让它更稳定可复现？（固定时间、设定随机数种子、隔离文件系统、冻结网络环境。）

一个 30 秒还不稳定的循环，跟没有循环几乎没什么两样；而一个 2 秒就能稳定复现的循环，那就是精炼扎实的调试利器，堪称开发者的超能力。

### 非确定性 bug

目标不是“完美复现”，而是**提高复现率**。把触发条件循环跑上 100 遍、并行跑、加负载、压缩时间窗口、插入延时。50% 复现率的 bug 就能调试，1% 的基本没戏。所以一直往上提，提到可以调试为止。

### 实在建不出循环怎么办

**建不出循环就说建不出。** 列清楚你试过什么。然后问用户要三样东西之一：（a）能复现的环境；（b）脱敏的捕获产物（HAR、日志、core dump、带时间戳的录屏）；（c）生产环境临时添加插桩的权限。**循环都没有，就别在那猜。**

### 完成标准：一个能报红的精炼循环

**第一阶段完成的标志：循环已经「精炼」且「能报红」。** 你要能说出一条**你已经实际跑过至少一次**的命令（脚本路径、测试命令或 curl 都可以），展示命令和输出，敏感信息脱敏。这条命令必须满足：

- [ ] **能报红**：真正触发 bug 的代码路径，并针对**用户描述的具体现象**做断言。对当前 bug 要报红，修好之后变绿。不是“没报错就行”，而是必须**能抓到当前这个具体的 bug**。
- [ ] **确定性强**：每次跑结果一致（不稳定复现的，按前面说的把复现率提到足够高并固定住）。
- [ ] **够快**：秒级，不是分钟级。
- [ ] **可无人值守**：能自动跑，人工介入只能通过 `scripts/hitl-loop.template.sh`。

如果这条命令还没出来你就开始读代码猜原因，**停下来。直接跳到假设，正是这个技能要防的。** 没有能报红的命令，就不要进第二阶段。

## 第二阶段：复现 + 精简

跑循环，看着它变红。

确认：

- [ ] 循环复现出来的现象和**用户**描述的一致，不是隔壁另一个无关的失败。搞错 bug = 修错地方。
- [ ] 失败能稳定复现（偶发 bug 则要确保复现率高到足以用来调试）。
- [ ] 已经抓到了精确的现象（报错、错误输出、变慢等），后续阶段能据此验证修复是否真管用。

### 精简

跑红了之后，把复现场景精简到**还能红的最小规模**。输入、调用方、配置、数据、操作步骤这些，一样一样砍，每砍一刀跑一次循环，只留那些对失败至关重要的部分。

**至于为什么要费这个劲？**最小的复现场景在第三阶段需要排查的变量最少，到第五阶段直接拿来当回归测试用例。

精简到**每个留存元素都不可或缺**为止，删掉任意一个，循环都会变绿。

**没复现完、没精简完，就别往下走。**

## 第三阶段：提出假设

先列出 **3-5 个假设并排好优先级**，再动手验证。只提一个的话，很容易锚死在第一个看似合理的想法上。

每个假设必须**可证伪**：说清楚它对应的预测。

> 格式："如果根因是 <X>，那么 <改动 Y> 会让 bug 消失 / <改动 Z> 会让 bug 更严重。"

如果连预测都写不出来，那这个假设只是个直觉，要么丢掉，要么打磨到可验证为止。

**动手之前先把排序后的列表发给用户看。** 用户通常有领域知识，能瞬间重排优先级（比如"我们刚给 #3 对应的模块发了个变更"），或者告诉你哪些假设已经排除了。这一步成本很低，但能节省大量时间。当然，不用死等，如果用户不在的话，按你的排序继续推进就行。

## 第四阶段：插桩验证

每次验证必须对应第三阶段的某个具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 交互式检查**：环境支持的话优先用。一个断点顶十行日志。
2. **在能区分不同假设的边界处加定向日志**。
3. 不要搞"全量打日志再 grep"那套。

**给每条调试日志加唯一前缀**，比如 `[DEBUG-a4f2]`。收尾时一个 `grep` 就能清理干净。带标签的删掉，不带标签的保留。

**性能类问题要特别处理。** 排查性能回退时，日志基本靠不住。正确做法：先建基准测量（计时工具、`performance.now()`、性能分析器、查询执行计划），再用二分法定位。先测准，再修复。

## 第五阶段：修复+回归测试

**先写回归测试再修复**，但前提是存在**正确的接缝（seam）**。

所谓正确的接缝，是指测试能够复现**真实的 bug 模式**，就像它在实际调用现场发生的那样。如果唯一可用的接缝太浅（比如只能测单调用者，但 bug 需要多调用者才能触发；或者单元测试无法复现触发 bug 的完整调用链），那在这个接缝上写回归测试就是自我欺骗。

**如果压根找不到正确的接缝，那这本身就是个重要发现。** 记下来。说明代码架构目前无法锁住这个 bug，标记它，留到后续阶段处理。

如果存在正确的接缝：

1. 把精简后的复现场景转化成该接缝上的一个失败测试。
2. 跑一下，看着它失败。
3. 动手修代码。
4. 再跑，确认它通过。
5. 用原始未精简的场景重新跑第一阶段的反馈循环。

## 第六阶段：清理

宣布完成前必须做到：

- [ ] 原始的复现步骤再也复现不出来了（重新跑一遍第一阶段的循环确认）
- [ ] 回归测试通过了（或者已经记录下"没有合适的接缝"这个事实）
- [ ] 所有 `[DEBUG-...]` 开头的调试日志已删除（用 `grep` 查一遍）
- [ ] 临时写的测试工具/原型代码已经删了（要留的话，放哪按项目管理制度走）
- [ ] 最终确认正确的那个假设，写进 `commit` 或 `PR` 的描述里，让下一个来看这段代码的人能学到经验
