# 深化模块

找出架构上的摩擦,挖出**深化机会(deepening opportunity)**:把大接口,薄实现的浅模块,改造成小接口,厚实现的**深模块(deep module)**,让代码更好测,也让 AI 更容易导航.

这套流程靠两样东西打底:项目自己的领域模型,一套统一的设计词汇.

- 用 Skill 工具加载 `codebase-design`,拿到架构词汇表(模块,接口,深度,接缝,适配器,杠杆效应,局部性)和配套原则(「假想删除」,「接口就是测试面」,「一个适配器 = 假接缝,两个 = 真接缝」).后面每条建议都用这套术语说话,别换成「组件」「服务」「API」或「边界」;项目里的业务名词和代码标识按原名引用.
- 好接缝的名字要从 `GLOSSARY.md` 的领域语言里找;`docs/adr/` 里的 ADR 记的是已经拍板的决策,这套流程不翻这个旧账.

## 流程

### 1. 探索

**先圈定范围再扫:YAGNI.** 深化一个模块,图的是以后改它更省事,所以近期常改的代码优先看.先定好看哪块,再动手扫:

- 用户点了方向(某个模块,某个子系统,某处痛点),就照着这块看,翻提交历史找热点那步省掉.
- 没指方向,就用 `git log --oneline --name-only` 往回翻一段提交历史(比如一两百条),结合实际改动路径找代码库的热点:哪些文件,哪些区域总在提交里冒头,就先看哪里.要是改动很散,看不出热点,就把历史再往回拉长一截;还是散,就别硬圈,请用户点个方向.

动手前先读 `GLOSSARY.md`,再把目标区域涉及的所有 ADR 读一遍;项目还没有的,跳过这步.

然后派一个子代理去逛代码库.别拿死板清单挨个打勾,凭手感逛,撞到下面这类摩擦就记下来:

- 理解一个概念,要在一堆小模块之间来回跳?
- 哪里是浅模块:接口复杂得几乎跟实现一样?
- 哪里为了可测试性抽出了纯函数,但真正的 bug 藏在调用方式里(那里恰恰没了局部性)?
- 哪里有模块把内部细节从接缝往外漏?
- 哪些关键流程没有测试,或者隔着现有接口很难测?

看着像浅模块的,先用「假想删除」验这层封装值不值得留.复杂度跟着消失,这层白包了,出路是删掉,不算深化;散回调用方手里的,再问深化方向:这些复杂度能不能收拢进一个深模块?能收拢,记进候选;收不拢,复杂度只是换个地方继续散着,不记.

### 2. 用 HTML 报告摆出候选

报告用单个 HTML 文件交付,写进项目的临时目录(`temp/`,没有就新建,内容可随时整体删除),不碰产线代码.文件名带时间戳(`architecture-review-<timestamp>.html`),每次运行写各自的文件,互不覆盖.

- 把同一根因,能靠同一次深化一并解决的发现打包成一条;不同改法之间的取舍要留着,候选之间的前置或替代关系也要标清楚.
- 生成前完整读取 [HTML-REPORT.md](./modules/HTML-REPORT.md),按其中的内容,布局,交互和图示规则生成.该文档是报告规范的唯一来源,配套的 HTML 示例只作为可选参考实现.
- 业务领域用 `GLOSSARY.md` 的词汇,拿项目已有的领域名说候选.比如 `GLOSSARY.md` 定义了「订单(Order)」,就说「订单接入模块」,不说「FooBarHandler」.架构概念用 `codebase-design` 的词汇.
- 候选撞上现有 ADR 时,只有摩擦真实到值得重开这条 ADR,才摆出来说.ADR 已经否掉的重构,和只在理论上成立的重构,别一个个翻出来列.

### 3. 交叉审查与验收

初稿出来后,另找一个没参与前面探索和写报告的子代理来交叉审查.给它这几样:本轮探索范围,HTML 报告路径,[报告规范](./modules/HTML-REPORT.md),项目源码,`GLOSSARY.md`,相关 ADR.

1. 逐项审查:首轮把全部候选和它们的前后图都过一遍.子代理自己去核对支撑候选结论的源码或记录:数量,统计范围和口径对不对得上;证据够不够支撑结论;图和正文一致不一致;建议和收益有没有保留前提条件.图例和架构概念按报告规范核对.审查结果要列出具体问题,对应哪个候选或哪张图,依据是什么,怎么改,还要说明实际审了哪些,哪些没核验.
2. 修正与复核:主代理逐条核实意见,合理的就改,不采纳的说明依据.影响候选成立的证据缺口,要么补核验,要么把结论收窄;还需要确认的条件写进待确认项,对应的建议和收益要带上这个前提.改完后,让审查者复核改过的地方和受影响的结论.审查指出的问题和关键证据缺口都处理完,修改也通过复核,内容审查才算完成.
3. 页面验收:内容审查完成后,主代理按[交付验收](./modules/HTML-REPORT.md#交付验收)逐项检查最终 HTML.验收中如果改了候选内容或图示含义,交回审查者复核,再重验受影响的验收项.每项验收结论对应实际检查结果;没完成的说明缺口,要是卡在能力或环境上,就按总纲的诚实协议如实说.
4. 交付呈现:内容审查和页面验收都过了,用系统命令打开报告(Linux: `xdg-open` / macOS: `open` / Windows: `start`),并在最终回复里给出报告绝对路径:
   - 有候选:问用户「这几个深化候选方案里,你想深挖哪一个?」
   - 没有候选:说明本次探索范围内未发现深化机会,结束当前流程.

### 4. 追问循环

用户选定某个候选后,用 Skill 工具加载 `grilling`,陪用户走一遍决策树:理清技术约束,外部依赖,改造后深模块长什么样,接缝后面适配器怎么分工,既有测试用例怎么承接.

追问过程中,用 Skill 工具加载 `domain-modeling`,按它的规范记录新概念,概念澄清和符合条件的 ADR:

- 引入了新领域名词?把新概念补进 `GLOSSARY.md`;文件还没建,就按 `domain-modeling` 的约定建一个.
- 聊着聊着把某个模糊的说法敲定了?当场更新 `GLOSSARY.md`,把语义边界定死.
- 用户因为某个硬理由把这个方案否了?主动问一句要不要记成 ADR,可以这么说:「要我把这条记下来吗?以后做架构评审时,省得别人再提一遍.」但这个理由得是真的值得后人知道,才记;临时性的(比如「现在顾不上」)或不说也明白的,就算了.
- 想给深化后的模块另找接口方案?用 Skill 工具加载 `codebase-design`,用它的「Design It Twice」模式:并行拉起多个子代理,给每个发不同的设计约束,各出一版,然后从深度(杠杆有多大),局部性(改动集中还是散落),接缝位置(接口开在哪最顺)三个维度横向比,挑一个.
