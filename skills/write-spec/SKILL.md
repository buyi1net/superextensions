该 skill 利用当前 sessions 上下文和代码库理解来生成一个规范文档（spec），不要重新询问用户来补齐需求，也不要引入当前对话中没有讨论过的新要求。只整理你已经掌握的内容。issue 系统和标签系统应该已经提供给你，如果没有，请告知用户运行`/setup-superextensions`。

## 执行流程

**第一步：了解代码库现状**

如果你还没有了解当前代码库的状态，请先探索代码库。在整个规范中使用项目的领域术语词汇表，并尊重你所要修改的区域中已有的架构决策记录（ADR）。

**第二步：确定功能验证入口**

先确定你打算从哪个入口验证该功能（test seam），应优先考虑现有的测试入口，而不是新建一个测试入口。如果必须新增入口，选择离用户更近、层级更高的入口，代码库中test seam越少，整体效果越好。理想状态下的test seam应该是1个。

**第三步：编写规范文档**

使用下方模板编写规范文档，完成后，将文档发布到项目的 issue 跟踪系统，并添加`ready-for-agent`标签，而不是继续追问需求。

<spec-template>

## 问题陈述

从用户的角度描述用户正在面对的问题。

## 解决方案

从用户的角度描述解决该问题的方案。

## 场景需求

编写一份内容**非常详尽**的、带编号的用户使用场景与需求清单，覆盖该功能的所有方面。

每一项都必须说明：谁在使用、希望获得什么功能，以及获得该功能后能解决什么问题或得到什么收益。

每一项必须使用以下格式：

```text
1. 作为一名 <角色>，我希望拥有 <功能>，以便获得 <收益>
```

示例：

```text
1. 作为一名移动银行客户，我希望查看账户余额，以便更明智地决定如何消费
```

## 实现决策

列出已经确定的实现决策，包括：

- 将要构建或修改的模块；
- 将要修改的模块接口；
- 开发者给出的技术澄清；
- 架构决策；
- Schema 变更；
- API 契约；
- 具体交互方式。

**禁止写入具体文件路径或代码片段。** 这些内容可能很快过时。

唯一例外：原型生成的片段如果比普通文字更准确地表达某项决策，可以将其嵌入相应的实现决策中,（比如：state machine、reducer、schema、type shape），嵌入时简短注明该片段来自原型。只保留能够表达决策的部分，而非可运行的演示。

## 测试决策

列出已经确定的测试决策，包括：

- 描述什么是好的测试。（只测试外部行为，不测试实现细节）
- 将要测试的模块。
- 测试方面的既有实践。（即代码库中类似类型的测试方法）

## 超出范围

描述这份规格书明确不包含的内容。

## 补充说明

记录关于该功能的任何进一步说明。

</spec-template>
